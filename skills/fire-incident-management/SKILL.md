# 火情事件处置流程

> 状态：草稿，待专家按本矿火灾专项应急预案审定。本技能只规定**顺序和职责**，不含任何阈值、数值或判据：判据在 `fire-assessment`、`emergency-escalation`、`effect-review`、`sealing-plan`、`plan-compliance` 的脚本和 references 里，数值一律来自工具。

## 谁决定什么

- **你（智能体）决定**：下一步调哪个工具、结果之间怎么关联、要不要建议升级、选哪种处置、效果不好时怎么调整。这些不要问人，直接做并说明依据。
- **代码决定**：所有数值、等级、阶段、用量、红线结论。照抄工具结果，不自己数、不自己算、不自己归纳界限。
- **人决定**：对外动作（预警广播、撤人通知、方案和调度下发、升级、启封审批）。你提交，由人确认；被拒绝就如实说明，不换名目再提交。

## 只有四种情况可以向人提问

1. **批准**：对外动作需要人确认（走提交流程，弹窗就是提问，不要另外再问一遍“要不要提交”）。
2. **缺信息**：矿井接口取不到、必须现场确认的信息（化验单、现场目击、人员实际位置、方案需要的人工确认项——封闭方案的现场条件用 `get_field_conditions` 给的卡片问，不自己编问题）。
3. **事实冲突**：关键事实互相矛盾，且无法用其他数据验证。
4. **选处置**（橙色预警研判之后）：处置选项由代码给出（`get_response_options`），返回有 `card` 才用 `ask_user` 原样问给操作员（本级已选过、复评没恶化时代码不给卡片，就不问），每次研判最多问一次；选项、标签、多选设置都照抄，不自己增删改。操作员选的就是要做的处置，你不替他选，也不再追问“确定吗”（下发时弹窗就是确认）。

其余一律自己决定。尤其不要问“要不要研判”“要不要继续检测”“需要我做什么吗”。

## 收到值守事件之后

1. 用 `get_incident` 读事件：时间线、待确认告警、跟踪计划。消息里的告警编号如果标注了“重复投递”，或 `get_incident` 返回的 `alert_status` 里该告警 `state` 为 `handled`（代码按时间线判断：之后已有依据数据不早于该告警的研判、复评、方案或对外动作记录），就是重复投递：用一两句话告知操作员“已处理”并指出最近的研判记录，不要重新研判、不要重复提交对外动作。
2. 按告警原因处理：
   - 异常（anomaly）、矿井报警（mine_alarm）：立即对该工作面做完整研判（`run_fire_assessment`）；
   - 跟踪计划到点（followup_due）：做效果复评（`review_effect`）；
   - 监听降级（degraded）：见下面“数据不可信”。

   告警的矿井时间离现在较久、想先看矿井最新状态时，可以先 `check_mine(mode=once)`；它没有事件的基线，结论是与正常状态比较的（“由 无 升为…”不是新变化），研判结论以 `run_fire_assessment` 为准。
3. 研判结果出来后，把工具给的要点告诉操作员。结果建议升级、需要预警或需要处置方案时，直接准备并提交相应的对外动作，由人确认；不要先问“要不要”。
4. 开始处置后用 `set_incident_status` 标为处置中；处置动作下发后、每次复评之后用 `add_followup` 登记复评（不给 after_h，到点时间由系统定：刚下发新处置用默认间隔，否则按复评给出的下次复评时刻）。
5. 复评做完用 `complete_followup` 记结论。效果不达预期：调整方案（重新起草、必要时升级），仍按第三节的规则由人确认；达标且监测稳定：`set_incident_status` 标已稳定。
6. 没有未完成的跟踪计划、没有未确认告警、操作员确认可以结束时，才 `close_incident`。
7. 事件稳定或关闭后，操作员要复盘时调 `review_timeline`（技能 `incident-review`）：次数和响应时长由代码算，照抄要点，不要自己数。

## 按预警等级处理（占位，待专家审定）

等级、阶段、是否建议升级一律取研判结果（`run_fire_assessment`），不自己判断。研判之后按等级这样做，不先问人“要不要”：

| 研判的预警等级 | 你做的事 |
| --- | --- |
| 黄色（及蓝色） | 告知操作员研判要点；提交加密监测（`start_monitoring`，观察跟进；record_id 照抄 `run_fire_assessment` 返回的 `record_ids.warning`）；用 `add_followup` 登记复评；**除加密监测外不提交对外动作**（预警广播、方案下发都不提交）。加密监测只增加观察、不改变现场，系统直接执行、不弹确认；同一事件里已经开始过就不用再提交（再提交系统也只返回原来那次）。 |
| 橙色 | 先 `get_response_options('orange', panel)`，返回有 `card` 就用 `ask_user` 把它原样问给操作员（多选追加哪些处置；必做的注氮已包含；选项照抄，“不追加”那一项卡片里已经有，不要自己再加选项或说明）；按答案（标签按 `label_to_id` 换成编号）编制**防灭火处置方案**（`draft_firefighting_plan(panel, selected_options=[编号…])`：不封闭火区、不安排人员进入灾区，没有人工确认项；方案的可选步骤正好是操作员选的，不自己增减）经合规审核后用 `issue_firefighting_plan` 提交；同时提交预警（`publish_warning`）；登记复评。操作员选了“不追加（只做必做项）”或点了“跳过”时 `selected_options` 传空列表，不再追问。返回没有 `card`（本级方案已下发、之后复评没有恶化）就不问、不重新下发方案，登记复评即可；复评恶化后再调时会给追加卡片，这时选“不追加”或点“跳过”就是不追加，不重新下发已有的方案。 |
| 红色 | 红色的处置是**撤人和封闭火区**（`get_response_options('red')` 的两项，都由你落实，不问“要不要封闭”），在同一轮里做完：提交预警；研判建议升级就提交升级（`escalate_emergency`）；提交撤人通知（`notify_evacuation`，`record_id` 照抄研判返回的 `record_ids.personnel`，`persons` 留空：名单和避灾路线由系统按记录的受威胁人员填写；只有指挥人员另外点名时才填人员编号）；编制封闭方案（先 `get_field_conditions`，用 `ask_user` 把返回的 `questions` 原样问给操作员；再 `draft_sealing_plan(panel, field_choices, confirmed_by)`，题被跳过就不传那一项，不替人填），合规审核通过就用 `issue_sealing_plan` 提交——是否封闭由确认人在确认弹窗上决定，弹窗就是请示，不要停下来问“是否下发”；登记复评。物资缺口不是不提交的理由。方案有“需调运”时，下发方案后提交调度单（`issue_dispatch_order`，`record_id` 照抄同一个审核记录，编号、用途、明细都留空，由系统按方案填）；台账里没有的缺口物资需人工联系外部来源。 |
| 稳定后 | 启封评估（`assess_unsealing`）只在指挥人员要求时做（封闭后火区要长期观测，复评“已受控”不等于可以启封，不要自己发起）；评估具备条件才提交启封审批；事件稳定后复盘。 |

- 以上对外动作（加密监测除外：它只增加观察，系统直接执行、不弹确认）下发前都要人确认；被拒绝就如实说明，不换名目再提交。批准超时没人回应时怎么办由系统的动作分级表决定（不自动执行，只升级提醒），你不要因为“没人确认”而自行改做别的动作或重复提交。
- 红色、橙色阶段**除橙色选处置外，这些都是你自己决定，不向人请示**：要不要升级（看研判结果，建议升级就直接提交 `escalate_emergency`，弹窗就是请示）、要不要撤人、红色时要不要封闭（要，见上表）、要不要加强注入或注浆、复评从什么时候算起（取最近一次下发时间，`review_effect` 不给 since 即可）。方案审核出现物资缺口时，调运、先用现有库存还是等补给也由你按工具给出的缺口和调度结果决定并说明，需要下发调度单就提交（弹窗就是请示），不要问“要不要调运”。拿不准时选更保守的做法并说明依据，仍不要问“是否升级”“是否加强”。
- 等级升高（如黄变橙）时按新等级再做一遍，已经提交过且仍有效的不重复提交。
- 研判是红色时只做红色那一行，不再提交防灭火处置方案（那是橙色的做法；红色靠封闭，不是在防灭火方案上加码）。
- 防灭火方案和封闭方案都不是自动升级关系：复评后效果不佳、火情恶化时，才按更高一级的做法处理。

## 启封后复燃

研判结果（或要点）里 `reseal_indicated` 为真，表示火区已启封且出现复燃征兆（第164条），应重新封闭：

1. 不先问人“要不要重新封闭”，直接调 `draft_sealing_plan(panel)` 起草重新封闭方案，经合规审核后用 `issue_sealing_plan` 提交，由人确认；方案的步骤、材料和红线与首次封闭相同，现场条件里的“封闭时间”可能为空，照抄，不要自己补。
2. 撤人不等待方案；是否另行提交撤人通知，按当前的对外动作规则处理，不要自己扩大范围。
3. 提交后照常 `set_incident_status` 标为处置中，并 `add_followup` 登记复评。
4. 只有 `reseal_indicated` 为真才这样处理。火区仍处于封闭状态时 CO 上升的复燃报警，按普通研判结果处理，不要自行认定“应重新封闭”。

## 数据不可信时

传感器故障、数据中断、矿井接口不通、监听降级：

- 如实告诉操作员**缺什么、对结论有什么影响**，不要把“没有数据”说成“没有异常”；
- 保守处理：不用不可信的数据去支撑对外动作；工具报“数据不足”“无法判定”时照抄；
- 需要现场确认就按“缺信息”问人，问清楚要什么、由谁确认。

## 研判与处置之间的顺序

升级判断来自研判记录；封闭方案来自 `draft_sealing_plan`（含合规审核）；效果评估来自 `review_effect`。顺序由事态决定，但对外动作都必须引用工具返回的记录编号，不能引用你自己在沙箱里算的结果。

## 边界

- 你提供辅助决策建议，不声称已经执行了任何处置；下发是否成功以工具回执为准。
- 不绕过人工确认，不改写工具给的等级、红线结论或条文。
- 事件时间线里的研判、复评、封闭方案、对外动作结果由系统自动记录，不需要你转抄。
