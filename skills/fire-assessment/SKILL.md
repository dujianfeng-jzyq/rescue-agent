# 采空区自燃研判

> 状态：草稿，待通风/防灭火专家审定。阈值和判据在 `references/`，全部是开发占位值，以客户矿井《自然发火预测预报制度》为准。
> 由第一版的 `fire-warning-assessment` 草稿和上一版的 `mine-fire-assessment` 合并而来。

## 什么时候用哪个工具

| 指挥人员的要求 | 做法 |
| --- | --- |
| “看一下现在矿井是否有异常” | `check_mine(mode=once)`：几秒内返回各工作面的检测结果卡片 |
| “研判一下 1201”“预警等级是多少”“要不要升级” | `run_fire_assessment(panel)`：固定流程，依次算实时报警、预警等级、自燃阶段、趋势、各束管测点的爆炸三角形、升级建议，等级达到阈值时算受威胁人员，生成研判报告和风险图 |
| 在已有记录上追问（“如果再看 12 小时的趋势会怎样”） | `export_record` 把证据记录导出到工作区，在沙箱里运行本技能的脚本试算；结果只作参考，回答里注明“试算，仅供参考”，不能作为指令依据 |

持续检测（`check_mine(mode=watch)`）只在指挥人员明确要求时启动（以后的阶段提供）。

## 回答怎么写

1. 有实时红线报警时（检测结果或报告的“实时报警”不是“无”），回答第一句就写报警，并提醒调度员按预案立即撤人，撤人不等待任何研判结果。
2. 固定流程返回的报告事实部分**原样**放进回答（含风险图），不改写、不删减、不重排；之后另起“分析与建议”。
3. “分析与建议”只引用报告和记录里已有的数值：等级、阶段、分区都照抄，不要自己升降级、推断阶段或煤温、判断分区，
   不要自己数人数或测点、相减算变化、合并区间、归纳界限。需要汇总时用报告里的汇总字段（如受威胁人数合计）。
4. II 区、III 区不是“安全”，要照实说明哪种变化（减风积聚或混入空气）会进入爆炸范围。
5. 引用记录编号（RS-…、RP-…），发布预警、升级响应时也引用它们。

## 解读要点

- **CO**：自燃最早出现的标志气体，但单独升高也可能来自爆破、设备尾气。看趋势比看单点重要。
- **乙烯（C₂H₄）**：首次检出是自燃进入加速阶段的重要标志。只按结果说明乙烯是否检出，不要据此推算煤温。
- **乙炔（C₂H₂）**：意味着可能已接近或进入明火阶段。
- **格雷哈姆系数**：CO 生成量与耗氧量之比。注氮期间氮气浓度高，系数会失真偏低——结果的“说明”里会提示，照实转述。
- **数据质量**：脚本已排除卡值、尖峰、漂移等可疑数据。被排除的测点要在结论中列出，并说明“该测点数据不可信，相应判断依赖其他测点”。
- **预警等级与实时报警独立判定**：报警不会抬高等级；有报警时以报警为先。

## 风险检测

检测结果里的 `anomaly` 是与基线比较的结论（没有基线时与正常状态比较）：出现新的实时报警、等级升高、阶段推进、必需测点失效，任一项即为异常，原因在 `reasons`。
检测到异常时，建议指挥人员做完整研判（`run_fire_assessment`）；不要自行发布任何指令。

## 脚本

| 脚本 | 输入 | 说明 |
| --- | --- | --- |
| `check.py` | 证据（`collect.yaml` 的 check），可选基线 | 风险检测 |
| `alarms.py` | 证据 | 实时红线报警 |
| `warning.py` | 证据 | 预警等级、指标、来源测点、数据质量 |
| `stage.py` | warning 的结果 | 自燃发展阶段 |
| `trend.py` | 证据、warning 的结果 | 触发指标来源测点的趋势 |
| `personnel.py` | 证据（`collect.yaml` 的 assessment）、warning 的结果 | 受威胁人员与避灾路线 |

沙箱里试算（输入文件按上表组织成 JSON 对象，键名即输入名）：

```bash
python -E -s -B -X utf8 <技能目录>/scripts/warning.py --input-file input.json --output-file out.json
```

## 边界

- 结论用于辅助研判，不替代现场检测和指挥决策；决策和指令由人作出。
- 数据缺失或被判为可疑时，明确说明缺什么、对结论有什么影响；不确定时写“需人工判断”。
