# 第三版设计（草稿一）

> 状态：草稿，待评审（2026-11-04）。在第二版（`docs/design-v2.md`、`docs/architecture.md`）基础上改进，不推翻。
> 范围：**演示阶段只覆盖采空区煤自燃一个场景，全部对着模拟矿井**。阈值、参数、流程由我们按已有专业知识设计为合理的占位值，演示后再由专家审定。
> 不再兼容第一版：契约里的研判快照、`grade.py` 的第一版兼容在第三版清理掉。

## 1. 为什么要做第三版

第二版把“数值只来自代码”做稳了（端到端评测 23/24），但作为产品有五处不足：

| 不足 | 表现 |
| --- | --- |
| 智能体只是协调者 | 流程固定，多处向人提问（如检测到异常后问“要不要研判”），不像专家直接处置 |
| 接口分成两块、矿井细节写在技能里 | mine_data 管读数，actions 兼管校验和出口；采集清单写死 `SM-{panel}-UC` 这类测点，换矿要改技能 |
| 监听不是常驻的 | 持续检测只能由人触发、一个会话一个、随 DSH 进程消失 |
| 状态只存在于单次会话 | 没有“事件”概念；指令下发后的效果跟踪靠人再问一次 |
| 评测只查格式 | 自主度提高后，需要检查决策本身对不对 |

## 2. 目标（五条 + 补充）

1. **智能体是矿山应急救援专家**：自己决定下一步做什么，决策有依据；只在真正需要人时才提问。
2. **系统分为 rescue-agent（大脑）和 rescue-mine（接口）两部分**，rescue-agent 通过 rescue-mine 提供的工具取数和下发。
3. **rescue-mine 是唯一随矿井变化的部分**：开发阶段产生模拟数据，产品阶段对接传感器和平台；对接新矿井只改 rescue-mine。
4. **rescue-mine 提供全部与矿井相关的操作**：最新/历史数据、传感器实时数据、人员装备物资，以及通知和指令下发。
5. **常驻监听**：智能体运行期间持续监听，发现异常就通知操作员并进入处置流程。
6. 补充：**事件（Incident）对象**、**闭环跟踪**、**对外动作分级**、**降级策略**、**决策评测**、**完整演示故事线**。

## 3. 总体架构

```
 操作员 ── DSH 网页端 / 值班界面 ───────────────────────────────┐
                                                               │
 ┌──────────────────────── rescue-agent（大脑）──────────────────┴────────────┐
 │  rescue-commander（专家智能体，DSH 预设）                                    │
 │    │ 调用                                                                    │
 │  DSH 插件（TS）：evidence 证据 · fire-loop 研判工具 · knowledge 知识库        │
 │                   incident 事件 · approval 审批 · audit 审计                │
 │    │ 运行                                                                    │
 │  skills/（技能：判据、算法、模板、参数、自检样例）                            │
 │                                                                             │
 │  sentinel 监听器（Python 常驻进程，不经模型）──写事件──▶ 事件库               │
 │  guard 守卫服务（Python 独立进程）：红线、记录核对、指令台账                  │
 └──────────────┬──────────────────────────────────────────────┬──────────────┘
                │ 读：rescue-mine 数据类工具                      │ 写：仅经 guard
                ▼                                               ▼
 ┌──────────────────────────── rescue-mine（接口）────────────────────────────┐
 │  统一 MCP 接口（版本化）：自描述 · 数据 · 设备 · 人员物资 · 通知与指令        │
 │  实现 A：mine-sim（模拟矿井 + 演示控制台）    实现 B：真实矿井适配器（以后）   │
 └─────────────────────────────────────────────────────────────────────────────┘
```

**边界规则**

- rescue-mine **只有“读数据”和“执行动作”，不含策略**：不做红线校验，不做研判，不存指令台账。
- rescue-agent 是**唯一的安全逻辑所在**：红线、记录核对、批准、台账都在这一侧，换矿不用重审。
- 智能体读矿井数据只经证据插件（留记录）；写矿井只经 guard（不能绕过）。
- 模拟器的真值、读数设置、倍速、事故注入属于 mine-sim 的**控制接口**（`/sim`），**不是 rescue-mine 接口的一部分**，智能体和 DSH 看不到。

## 4. rescue-mine 接口

一份版本化的接口说明（`docs/rescue-mine-interface.md`，由契约导出），一致性检查 `python -m rescue_contract.conformance` 覆盖全部工具。第二版 mine_data 的现有工具（时钟、巷道网络、测点清单、读数、最新值、事件、火区、人员、物资、救援队）保留并归入下面的分组。

| 分组 | 工具 | 说明 |
| --- | --- | --- |
| 自描述（新增） | `get_capabilities`、`describe_mine` | 接口版本、本矿支持哪些工具/数据；工作面与火区拓扑；**测点的语义角色**（如“上隅角 CO”“回风 CO”“采空区束管点”）、单位、采样周期 |
| 时间 | `get_clock` | 矿井时钟（模拟加速时即模拟时间） |
| 监测数据 | `list_sensors`、`get_latest`、`get_readings(历史)`、`get_events` | 最新值、历史区间、传感器实时值；矿井自带事件/报警 |
| 矿井自带报警（新增） | `get_alarms`（拉取，含确认状态） | 真矿井有自己的报警平台，不只靠我们重算 |
| 设备（新增） | `get_equipment_status` | 风机、水泵、注氮/注浆设备的运行状态 |
| 人员物资 | `get_personnel`、`get_inventory`、`get_rescue_teams` | 同第二版 |
| 通风网络 | `get_network` | 同第二版 |
| 通知与指令（新增，取代 actions 的出口部分） | `send_notice`（预警/撤人通知）、`dispatch_order`（调度）、`submit_treatment`（处置动作：注惰、灌浆、封闭等）、`get_action_status` | 只执行不判断；返回**回执**，真实矿井异步生效时可查状态 |

**自描述的作用**：技能按**角色**取数而不是按测点 ID。采集清单从 `select: {ids: ["SM-{panel}-UC"]}` 改为 `select: {role: "upper_corner_co", panel: ...}`。换矿只要 `describe_mine` 如实回答，技能不改。角色词表由契约定义（占位，演示后由专家补全）。

**mine-sim 的拆分**：同一进程里，`/mcp` 提供上面的接口，`/sim` 提供控制接口和演示控制台，用不同令牌。`submit_treatment` 等写入类工具在 mine-sim 里作用于物理模型。

## 5. rescue-agent

### 5.1 守卫服务 guard（Python，独立进程）

由第二版 `mcp/actions` 演变而来，**不再是矿井出口**，而是智能体所有对外动作的唯一通道：

- 对外动作工具仍是 `publish_warning`、`issue_sealing_plan` 等，智能体调用它们；guard 校验后**再调用 rescue-mine 的执行类工具**。
- 校验：红线引擎（`rescue_contract.redlines`，只实现一次）、记录核对（现场条件、预警等级、升级建议、方案审核结论）、时效、动作分级（见 6.3）。
- 指令台账（含 Origin、回执、事件编号）和 `precheck_*` 只读预检。
- 与 DSH 分进程，模型的 bash 沙箱碰不到：第二道校验才有意义。DSH 的 approval 插件仍在执行前预检并弹确认（第一道 + 人工确认），guard 在执行时再校验一次（第三道）。
- 对外动作的执行回执写回事件时间线。

### 5.2 DSH 插件

| 插件 | 变化 |
| --- | --- |
| `evidence` | 采集改按角色；`check_mine(watch)` 不再由智能体登记，改为读监听器的事件；`get_record`、`export_record`、`review_timeline`（本版迁完） |
| `fire-loop` → `assess` | 固定流程拆成**可组合工具**：`assess_fire`（研判）、`assess_explosion`（爆炸风险）、`review_effect`（效果评估）、`recommend_escalation`、`draft_sealing_plan`（含合规审核）。每个工具仍是“采集 → 脚本 → 模板 → 必要时的模型阶段”，**步骤由代码决定**；由智能体决定调哪个、何时调 |
| `knowledge` | 不变 |
| `incident`（新增） | 事件库读写、时间线、待确认项、跟踪计划；给智能体 `get_incident`、`open_incident`、`add_followup`、`close_incident` |
| `approval` / `audit` | 按动作分级放行；批准人按角色限定；审计带事件编号 |

### 5.3 技能

保留第二版 6 个技能和“脚本是纯函数、数值只来自脚本”的规则。新增/调整：

- 技能的采集清单按角色取数。
- `fire-assessment` 的 `check.py` 同时供监听器使用（监听器、一次性检测、研判用同一套判据）。
- 新增 `fire-incident-management` 技能（SKILL.md 为主）：专家处置的**流程知识**——异常确认、研判、处置选择、对外动作、效果跟踪、升级/封闭/启封的条件与顺序。其中的判据和阈值仍在 `references/` 和脚本里，SKILL.md 正文不写数值。
- 参数按已有专业知识重新设计一遍（分级、阶段、效果、封闭必备步骤、升级条件、值守周期），标注占位，演示后专家审定。

### 5.4 预设

仍是单一预设 `rescue-commander`。人设改为**矿山应急救援专家**：先自己研判、自己选择处置，用证据说话；不向人请示可以自己判断的事。阶段子 Agent（研判说明、方案编写、合规审核）仍用 `tools.guard` 限制为只能提交结构化结果。

## 6. 智能体行为

### 6.1 专家定位：判断归智能体，数值归代码

- **智能体决定**：下一步做什么、调哪个评估、结果之间如何关联、是否建议升级、选哪种处置、效果不好时怎么调整。
- **代码计算**：所有数值、等级、阶段、用量、红线结论。智能体在回答里引用工具结果，不自己数、不自己算（第二版约定不变）。
- 每条建议带依据：记录编号、条文、关键数值，格式由技能模板固定。

### 6.2 提问规则：只有三种情况可以 ask_user

1. **批准**：对外动作（见 6.3）需要人批准。
2. **缺信息**：矿井接口取不到、需要现场确认的信息（化验单、现场目击、人员实际位置）。
3. **事实冲突**：关键事实互相矛盾，且无法用其他数据验证。

其余一律由智能体自己决定。**检测到异常后直接研判**，不再问“要不要研判”。persona 写明这三条；评测检查“多余提问”。

### 6.3 对外动作分级

| 级别 | 动作 | 处理 |
| --- | --- | --- |
| A 只读 | 取数、研判、检索、起草方案、预检 | 自动 |
| B 内部提示 | 给值班人员的告警、事件更新、报告交付 | 自动 |
| C 对外动作 | 预警广播、撤人通知、方案下发、调度下发、升级、启封审批 | **守卫校验 + 人工批准**；批准人按角色限定；弹窗显示依据 |

C 级动作**超时未批准**要有升级路径（提醒值班长/上一级，写进事件时间线），不能一直挂着。具体角色和时限是占位值。

### 6.4 闭环跟踪

下发处置后，智能体登记**跟踪计划**（`add_followup`）：评估时间点或触发条件、预期变化。到点由监听器/事件触发，智能体调 `review_effect`，效果不达预期则调整方案（再起草、必要时升级），仍遵守 6.3。这是第二版需要人再问一次的部分。

### 6.5 降级与失败策略

- 传感器故障、数据中断、矿井接口不通：**如实报告“数据不足”并说明影响**，按保守方向处理（沿用 fail closed）；不用不可信数据支撑 C 级动作。
- 监听器自身故障：值班界面显示“监听中断”，不静默。
- 模型接口错误：已有重试；仍失败时事件库保留未处理异常，界面可见。

## 7. 常驻监听与事件

### 7.1 监听器 sentinel（Python 常驻进程，不经模型）

- 启动后按矿井时钟循环：采集（按角色）→ 运行 `check.py` → 与上次状态比较 → 写事件。零 token 成本，DSH 重启不影响。
- **去重、滞回、分级**：同一异常持续存在不重复告警；等级升高、新异常类别、恢复才产生新事件；检测周期、连续次数、恢复条件在 `references/watch.yaml`（占位）。
- 还负责：跟踪计划到点触发、C 级动作超时升级、矿井自带报警（`get_alarms`）的接入。
- 取数连续失败 → 产生“监听降级”事件。

### 7.2 事件（Incident）

持久对象（事件库，`var/incidents/`，只由 incident 插件和 sentinel 写）：

```
incident_id, 状态（监测中/处置中/已稳定/已关闭）, 工作面/火区,
时间线[检测记录, 研判记录, 对外动作及回执, 批准/拒绝, 跟踪结果, 人工输入],
待确认项[], 跟踪计划[], 关联记录编号[]
```

- 异常 → 开事件（或并入同一火区的未关闭事件）；之后所有研判、指令、跟踪都挂在事件上。
- 事件在重启、换会话后能恢复；复盘时间线（`review_timeline`）直接读事件。
- 记录（Record）机制不变：证据可核对，指令引用 `record_id`，现在另带 `incident_id`。

### 7.3 唤醒值班会话（V1、V2 已验证通过，见验证清单 #24）

目标：异常事件到达后，**无人打开会话时自动唤醒智能体**开始研判，操作员打开界面即看到结论。第二版只验证了“会话内后台任务能唤醒智能体”（#20、#23），**没验证无人会话**。

- 验证通过：sentinel 通知 DSH 插件 → 插件在值班会话里投递事件 → 智能体直接研判并等待批准。
- **结果（2026-11-05）**：插件读事件库并用 `sessionController.create/resolveAgent` + `agent.followup` 在无人界面唤醒值班会话，冷、热、新建三条路径都通过，**退路不启用**。以下退路保留为失败时的兜底。
- **退路（已确认可接受）**：事件写入后，值班界面/演示控制台显示告警；操作员点开后，智能体接手并先读取事件，从已有记录继续。退路下“发现异常—通知操作员”仍由 sentinel 独立完成，只是研判在操作员打开后开始。

## 8. 评测

| 层 | 内容 |
| --- | --- |
| 确定性基线 | `eval/baseline.py` 保留：技能脚本逐小时扫描 6 个场景，查预警时效和误报 |
| 接口一致性 | rescue-mine 的 conformance；mine-sim 与（以后）真实适配器共用 |
| 监听器 | 场景驱动：给定读数序列，期望产生的事件（含去重、滞回、降级） |
| 智能体决策 | 每个用例写**决策期望**：此刻应判几级、应建议什么、**不应**做什么（如不应启封、不应超越批准）；检查多余提问、对外动作是否经守卫、数值是否有溯源、token 与耗时 |
| 端到端故事线 | 演示脚本整条走通（见 9） |

期望值是占位，随专家审定调整。`grade.py` 删除第一版兼容。

## 9. 演示故事线

围绕一条完整故事设计模拟场景和值班界面，而不是堆功能：

1. 常态：监听器运行，界面显示“监测中、一切正常”。
2. 注入事故：采空区气体缓慢异常 → sentinel 产生事件，界面告警。
3. 智能体自动研判：给出预警等级、自燃阶段、爆炸风险、受威胁人员，附依据。
4. 处置建议：注惰/灌浆/封闭方案，经合规审核；操作员批准下发。
5. 效果跟踪：智能体按跟踪计划复评；模拟推进几小时后展示变好或恶化。
6. 恶化分支：升级建议 → 批准 → 撤人通知。
7. 稳定后封闭、启封审批，事件关闭，生成复盘时间线。

另备一条“传感器故障/数据中断”的分支，展示降级策略。

## 11. 不做的事

- 不做多个面向用户的 Agent，不用 delegate；仍是单预设 + 固定步骤的阶段子 Agent。
- 不让智能体自由编排取数/算数：工具内部步骤由代码决定。
- 不在 rescue-mine 里放红线、研判或台账。
- 演示阶段不对接真实矿井，不做水灾/顶板等其他场景，不等专家审定。
