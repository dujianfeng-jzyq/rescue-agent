## 1. 背景

本项目（rescue-agent，下称“本项目”）和之前的 dsh-rescue-agent（下称“上一版”）都基于 DeepSeek Harness（DSH）。两者各有长处：

| | 上一版 | 本项目 |
| --- | --- | --- |
| 长处 | 尽量用 DSH 原生能力（一个预设，带 bash、文件、技能、子 Agent、workflow）；技能是标准格式，含专家资产（爆炸三角形、应急能力评估）；火灾研判做成**固定入口插件**（版本化脚本、模型只做选择、代码出报告）；知识库插件（检索 + 维护 + 设置页）；对外接口（rescue-api、SubAgent 接口）；Docker 发布 | 数值由代码计算并有测试；红线引擎只实现一次；研判快照 + 发布前核对 + 人工确认 + 审计；值守进程；模拟矿井（场景即演示、评测、回归）；真实模型端到端评测 |
| 不足 | 技能脚本的输入由模型手抄；阈值从知识库检索，由模型读出；没有指令发布、审批和留痕；权限宽，MCP 无鉴权 | 没用上 DSH 原生能力（技能只是草稿，不能运行脚本）；多步流程由模型编排，封闭方案流程不稳定、单次 170–340 万 token；专家要改算法得找开发；查条慢（15–65 秒） |

第二版取两边之长：**专家经验以技能（流程、脚本、模板）为载体，数据经 MCP 获取，知识经知识库插件检索，典型场景的多步流程由插件按固定步骤执行，对外生效的指令经人工确认。**

依据的验证记录：`docs/validation-checklist.md` #18（DSH 自带工作流）、#19（插件工具编排）；`docs/experiments/0001-skill-vs-workflow.md` 第 9.0 节（开放 bash、文件工具后的沙箱探测）。

## 2. 设计原则

1. **技能是专家经验和算法的唯一来源。** 流程写在 SKILL.md，算法写在技能的 `scripts/`，报告格式写在 `templates/`，参数和依据写在 `references/`。专家维护技能，修改经评审和 CI 后发布。
2. **数据不经模型转抄。** 证据由代码采集并存档，算法的输入是证据编号或证据文件，模型只传递编号和路径。规程条文同理：条文原文由代码查出并原样返回，不由模型拼接或改写。
3. **固定场景用固定流程。** 典型场景（本次为火灾研判、封闭方案、处置效果复评）做成插件工具：步骤由代码决定，模型只在指定阶段做选择和撰写说明，报告由代码按模板生成。
4. **权威结果只在服务端产生。** 进入正式记录、可被指令引用的计算结果，由证据插件在 DSH 进程里（不在沙箱里）运行技能脚本得到，并记录脚本版本和输入哈希。智能体在沙箱里自己运行脚本得到的结果只作参考，不能被指令引用。
5. **对外生效的动作只有一个出口。** 发布预警、下发方案、升级响应只能由主预设通过 actions 提交，经红线检查、按记录核对、人工确认，并记入审计。
6. **尽量用 DSH 原生能力**，不改 DSH；确实需要时按 DSH 的扩展点（插件、patch）实现。
7. **入口与表现分开。** 业务结果（报告、风险图、方案、回执）、人工问题、审批说明、流程进度都先形成结构化数据，再由各个入口（DSH 网页端，以后的对外接口）各自呈现。

### 4.2 技能

#### 同一份技能的两种用法

“技能”指 `skills/<技能名>/` 这个目录，它有两个使用方，读的是同一份文件：

| | DSH 技能（给模型） | 证据插件的 `runScript`（给系统） |
| --- | --- | --- |
| 读什么 | SKILL.md（由 DSH 的 skill-filesystem 加载，模型经 tool-skill 或 `/技能名` 调用） | `scripts/`、`templates/`、`references/` |
| 在哪里执行 | 模型在沙箱里用 bash 运行脚本 | 证据插件在 DSH 进程里起子进程运行脚本（不在沙箱里，结果写入沙箱不能写的记录目录） |
| 结果的地位 | 参考：用于开放问题、试算、解释，不能被指令引用 | 权威：存为记录（脚本哈希、输入哈希），可以被报告和指令引用 |
| 典型场景 | 指挥人员问“如果漏风量再加大一倍会怎样” | 风险检测、固定流程 |

固定流程的模型阶段也用 SKILL.md：插件把相应技能的正文作为阶段指令（4.4）。所以专家改一处 SKILL.md，对话里的模型、固定流程的阶段都会用上；改一处脚本，沙箱试算和权威计算也一致。

#### 目录与约定

```
skills/<技能名>/
  SKILL.md          # frontmatter：name、description、whenToUse、version；正文：何时用、步骤、解读要点、边界
  scripts/          # 算法脚本
  templates/        # 报告模板（Markdown + 占位符）
  references/       # 参数（yaml/csv，标注占位值）、方法说明、规程摘录
  tests/cases/      # 自检样例：<名>.input.json + <名>.expected.json
```

脚本约定：

1. **纯函数，文件进、文件出**：`python scripts/<名>.py --input-file <证据或上一步结果.json> --output-file <结果.json> [--svg-out <图.svg>]`。脚本不访问网络和数据库，不读环境变量里的凭据。所以沙箱里也能运行（输入文件由 `export_record` 提供），不需要给沙箱任何令牌（实验 0001 第 9.0 节结论 2 的问题由此避开）。注意：证据插件起的子进程不在沙箱里，以 DSH 进程的用户运行，能写技能目录、能出网（#22），“不访问网络”没有机制保证。所以脚本是**受信代码**，只靠评审和 CI 进入技能库；容器里技能目录只读挂载、出站白名单兜底（7.1）。
2. **输出可审计**：结果 JSON 包含算法版本、使用的参数、全部警告；数据缺失时输出明确的“无法判定”，不估算。
3. **只依赖运行镜像里已有的 Python 包**（清单写进技能规范），不在运行时安装依赖。DSH 镜像按这份清单安装。
4. **自检**：每个脚本至少有一组样例；CI 和镜像构建时运行全部样例，输出与期望不一致即失败。参数改动必须同时更新样例，提交说明里写明是占位值还是专家审定值。

#### 火灾闭环用到的技能

| 技能 | 脚本 | 模板 | 迁移来源 |

### 4.3 证据插件 rescue-evidence（DSH 插件，TS + Python 技能脚本）

由 `mcp/workflow`、快照存储和值守进程演变而来，放在 `dsh-bundle/src/evidence/`。负责：采集数据、运行技能脚本、存记录，以及风险检测（一次性、后台持续，4.9）。插件本身不含领域判据：采什么数据、怎么判断、什么算异常，都在技能目录里。

#### 为什么改为插件

第二稿把证据做成 MCP，理由是值守进程在 DSH 之外也要用它。风险检测改为由智能体在 DSH 里启动后（4.9），证据的使用方就全在 DSH 里了。按 4.5 的表应当做成插件，好处是：

- 与固定流程在同一进程里直接调用，结果卡片、流程事件、文件交付、写会话工作区都不用经过 MCP 转一道；
- 少一个服务、一个端口、一份令牌；
- 持续检测可以直接登记为 DSH 的后台任务，结束时由 DSH 唤醒智能体（4.9），不用自己做跨进程通知。

代价（已接受，列出供审）：

- 持续检测依赖 DSH 进程：DSH 重启后后台任务消失（4.9 的限制）。演示可以接受；生产的无人值守是否要独立于 DSH 见第 10 节；
- 不经 DSH 的确定性基线评测（`make eval`）要用 Python 的小工具，按同一份采集清单取数、运行同一批脚本。采集逻辑因此有 TS、Python 两份实现，用一致性测试约束（同一时刻两边采集的证据逐字段相同）。

#### 接入矿井数据

#19 已验证：插件用 `ctx.tools.execute` 只能调调用方 Agent 范围内的工具，而主预设不挂 mine_data；后台任务运行时也不在某次工具调用里。所以证据插件**自带 MCP 客户端**直接连 mine_data（只读令牌放 DSH 凭据服务，地址和测试连接在设置页），不经模型的工具范围。主预设仍不挂 mine_data。

#### 插件内部服务（不是模型工具）

| 方法 | 作用 |
| --- | --- |
| `collectEvidence(panel, kind, windowH?)` | 按 `kind`（check、assessment、effect、plan-context 等）读对应技能 `references/collect.yaml` 的采集清单，从 mine_data 取数，存为证据记录；Python 小工具读同一份清单 |
| `runScript(skill, script, inputs)` | 起子进程运行技能脚本（不在 bash 沙箱里）。只能运行技能清单里登记过的 `skills/*/scripts/` 下的脚本；把输入记录写成文件，输出存为结果记录。环境变量按白名单传（`PATH`、`LANG` 等，不继承 DSH 进程的模型、RAGFlow、MCP 密钥，#22）；设超时（先 SIGTERM，再 SIGKILL）；失败按超时、非零退出（带 stderr）、输出不是 JSON、输出不合 schema、启动失败分类（4.5 第 3 条） |
| `renderReport(skill, template, recordIds)` | 用技能模板和记录生成报告事实部分（数值原样填入，不取整），存为报告记录 |
| `getRecord(id)` / `exportRecord(id, workspace)` | 读取记录；把记录写进会话工作区，供智能体按技能在沙箱里做进一步分析。工作区由 `ctx.workingDirectory` 给出，**所有会话共用同一个目录**（#22），导出到 `records/<会话编号>/` 下 |

风险检测、固定流程都调这些方法，因此一次性检测、持续检测、完整研判用的是同一套采集和计算。

#### 给模型的工具

| 工具 | 作用 |
| --- | --- |
| `check_mine(mode, panels?)` | 风险检测（4.9）。`mode=once`：一次性检测，前台返回结果卡片；`mode=watch`：持续检测，登记为后台任务后立即返回任务编号，发现异常时任务结束并唤醒智能体。缺省检测全部工作面 |
| `get_record(id)` | 读取记录 |
| `export_record(id)` | 把记录写进会话工作区，返回路径 |
| `review_timeline(panel, since?)` | 复盘时间线（从 `mcp/workflow` 搬来） |

#### 记录

取代现在的 Snapshot，契约升级为 0.7.0。模型在 Python 契约里定义，导出 JSON Schema，插件按 schema 校验后写入：

```python
class Origin(_Model):           # 谁触发的（4.11）
    channel: Literal["web", "api", "subagent", "eval"]
    trigger: Literal["chat", "watch", "button", "flow"]  # 提问、持续检测、界面按钮（以后）、固定流程内部
    caller: str | None          # 用户、后台任务编号、appId
    conversation_id: str | None # 本系统的会话编号（不是 DSH 的内部编号）

class Record(_Model):
    record_id: str          # "EV-…"（证据）/ "RS-…"（结果）/ "RP-…"（报告），不可变
    kind: Literal["evidence", "result", "report"]
    panel: str
    as_of: MineTime         # 取数时的矿井时间
    created_at: datetime
    origin: Origin
    source: dict[str, Any]  # 证据：采集参数；结果：skill、skill_version、script、script_sha256、inputs、input_sha256；报告：template、template_sha256
    content: dict[str, Any] | str
    content_sha256: str     # actions 核对时重算
    files: list[RecordFile] # 风险图、报告文件等（名称、媒体类型、大小、sha256），按记录编号下载，不按路径
    parent_ids: list[str]
```

- 存储沿用现有 `SnapshotStore` 的做法：原子写、只增不改，目录 `RESCUE_RECORD_DIR`（Docker 里是一个数据卷）。**只有 DSH 进程能写**；bash 沙箱写不了（第 0 步探测：沙箱只能写会话工作区和 `/tmp`）；actions 容器只读挂载，发布前按记录核对并重算 `content_sha256`。
- **为什么不在沙箱里运行**：结果必须由智能体改不了的地方产生，才能被指令引用（原则 4）。插件起的子进程在 DSH 进程的权限下运行，不受模型控制，输入只能是记录。
- 文件下载按记录编号经会话交付取得，取代现在 fire_model `/charts/` 凭随机文件名下载、不校验令牌的做法。

### 4.4 固定流程插件（DSH 插件，TS）

照上一版 `run_fire_risk_assessment` 的模式实现，放在 `dsh-bundle/src/fire-loop/`，DSH 类型引用仍只放在 `src/adapter/dsh.ts`。

共同做法：

1. 工具参数只有工作面、人工确认项等少量字段；步骤由代码决定，模型不能改。
2. 进程内调用证据插件（采集、运行脚本、渲染报告）和知识库插件（查条）；调 actions（红线预检）用 `ctx.tools.execute`，经过 DSH 工具管道，审批和审计照常生效。
3. 需要模型判断的阶段，用 `ctx.workflowEngine.start` 运行插件里固定的脚本（带版本号），每个阶段一个 `agent()`：
   - 阶段指令 = 相应技能的 SKILL.md 正文（插件按技能名读取，每次运行时读当前版本，并把技能版本写进记录）+ 本阶段说明；
   - 输入 = 证据和结果记录的内容，以及代码事先查好的条文；
   - 输出 = 按 schema 的结构化结果：能用选择的地方只给选择（证据编号、条文编号、步骤类型、巷道编号来自给定清单）；说明类文字字段由代码检查，其中出现的数值必须能在本次记录里找到，否则该阶段判为失败；
   - 用 `tools.guard` 限制阶段子 Agent 只能提交结构化结果，不能调用其他工具。
4. 报告由证据插件按模板生成；插件用 `present` 交付完整报告文件（网页端交付卡片、右侧预览）。rc.4 用 `concludeTurn` 时网页端看不到报告，所以不结束本轮：工具另给代码生成的要点 `brief_markdown`（技能的 `templates/brief.md`），主预设原样贴出要点，不贴、不改写完整报告（2026-11-04，评测里模型照抄长报告常改写或漏行）。
5. 每个阶段开始、结束时发出流程事件（`FlowEvent`，4.11），写进运行记录；网页端通过工作流运行节点显示，以后的对外接口把它转成过程事件（#19：插件内部的工具调用不进会话日志，所以要自己记）。
6. 需要人确认的现场条件缺失、且影响红线时，流程结束并返回**结构化的问题**（`HumanInputRequest`：每项的说明、可选值、是否允许文字），由主预设用 `ask_user` 询问后带着人工输入重新运行（DSH 工作流不支持断点恢复）。无人值守的入口（以后的对外接口）收到同一份问题，可以原样转给调用方。
7. 工具返回**结果卡片**（`ResultCard`：标题、结论摘要、记录编号、交付文件、下一步可选操作），不只返回 Markdown（4.11）。

本次的三个入口：

| 工具 | 步骤 |
| --- | --- |
| `run_fire_assessment(panel)` | 采集证据 → 运行 alarms、warning、stage、trend、explosion_triangle（逐个束管测点）、escalation；等级 ≥ orange 时运行 personnel → 渲染研判报告（含风险图）→ 阶段“研判说明”：只从给定清单里选关注点和建议的下一步 → 交付 |
| `draft_sealing_plan(panel, human_inputs?, leak_m3_min?, target_o2_pct?)`（P3 实现见下方说明） | 采集证据 → 运行 skeleton、materials → 阶段“方案编写”（`sealing-plan` 技能）：选择可选步骤、巷道，填写步骤说明 → 调 actions 的红线预检 → 阶段“合规审核”（`plan-compliance` 技能，条文由代码按红线规则表和方案步骤查好后提供）：逐项给出人工复核结论和引用条文编号 → 不通过时把意见交回“方案编写”，最多 2 轮（占位）→ 生成方案记录和方案文本 → 交付，返回方案（含 `record_id`）给主预设提交 |

### 4.5 工具形式与统一约定

工具做成 DSH 插件还是 MCP，按它依赖什么决定，两种可以组合：

| 做成 DSH 插件 | 做成 MCP |
| --- | --- |
| 要读写会话工作区；要在设置页配置和测试连接、凭据放 DSH 凭据服务；要在内部调用其他工具或起子 Agent；要交付文件、结束本轮、自定义结果卡片；要挂在工具管道上（审批、审计）；只有 DSH 里的 Agent 使用 | DSH 之外也要用（模拟器、评测、其他系统）；数据或算法在外部、需靠近外部平台部署并隔离凭据；用 Python 等实现更合适；平台本身提供 MCP；长任务在服务端管理 |

按这张表：指令发布要被模拟器、评测和以后的其他系统使用，且必须与 DSH 进程分开持有台账（DSH 进程同时承载沙箱），做成 MCP；模拟矿井（以后是真实矿井适配器）在外部，做成 MCP；证据（含风险检测）、固定流程、知识库、会话入口只在 DSH 里使用，做成插件。

不论哪种形式都遵守：

1. 输入是记录编号或文件路径，不让模型把数据本身作为参数传入；
2. 结果存为记录，带算法或平台版本、输入输出哈希；
3. 失败分清“未配置、鉴权失败、不可用、业务拒绝、超时”，不悄悄改用别的方法（知识库的本地条文兜底是事先声明的降级，结果里标明 `source`）；
4. 凭据不进沙箱（DSH 凭据服务或 MCP 服务所在容器）；
5. 工具名表明用途，说明写清输入、输出、限制，技能按名称引用；
6. 只读与动作分开：对外生效的动作只走 actions。

长任务：DSH 0.2.1-rc.4 的 MCP 客户端不支持 MCP Tasks（`taskSupport: required` 的工具会被拒绝），进度通知也不会延长超时。几分钟内的任务用同步调用并调大该服务的 `toolCallTimeoutMs`；更长的任务用“提交 + 查询”，由固定流程插件或后台任务在代码里轮询，不让模型轮询。本次演示没有第三方算法平台。

### 4.7 知识库插件 rescue-knowledge

#### 为什么改为插件

上一稿沿用 kb MCP，理由只是“不动”。按 4.5 的表重新看，知识库应当是插件：

- **只有 DSH 里用**：证据插件、actions 都不检索知识库；唯一的程序调用方是固定流程插件，同在 DSH 里，进程内调用即可。
- **需要设置页**：RAGFlow 地址、数据集、凭据要能在 DSH 设置页里配置和测试连接，凭据放 DSH 凭据服务，不放 `.env`。上一版 `@rescue/knowledge` 已经做好（设置页、配置热更新、检索与“不可用”分开报告）。
- **维护工具**：上一版有上传、解析、写切片、查解析状态，专家补充资料不用找开发。这些工具不挂到 rescue-commander，放到单独的维护预设或设置页里。

现在 kb MCP 里的两样东西要先挪走：

- `check_plan_redlines`（红线自查）不属于知识库，移到 actions，作为只读工具 `precheck_plan`（固定流程本来就调 actions 做红线预检）。
- 本地留存条文 `local_articles.yaml`、红线规则所依据的条号由 Python 的红线规则表决定。`make schema` 时把规则表的条号一并导出成 JSON，插件读这份 JSON 和 yaml，不在 TS 里再写一遍规则（约定 3）。

#### 现在的 `get_article` 怎么实现

`mcp/kb/src/rescue_kb/server.py`：

1. 先查本地留存条文（红线相关的几条），命中直接返回；
2. 否则在 RAGFlow 里按文档名找文档 → 在该文档里用条号关键词（“第八十五条”“第85条”两种写法）找切片 → 逐个按切片编号取原文 → 用正则找条文标题，截取该条到下一条之前的文字；
3. 直接查找失败时，退回语义检索（查询词“文档名 + 条号”），在结果里同样按标题截取；
4. 都找不到返回 `not-found`。

问题：

- **慢**：一次查条是 4–6 个串行请求，每个 15 秒超时，RAGFlow 网关约 5 秒断开时还要重试，单次 15–65 秒；
- **可能不完整**：条文跨切片时，第 2 步只截取到切片末尾，后面的款、项丢失，且结果里不提示被截断；
- **一次只能查一条**：合规审核要引用多条时模型逐条调用。

#### 建议：按条建索引，组装由代码完成

赞成做成插件工具，但**不建议由 Agent 多次查询后组装条文**：条文是要照抄进方案、审核意见和台账的原文，交给模型拼接，可能漏款、改字、把两条拼错，和原则 2 冲突，且每次查条都要花模型调用的时间和 token。完整条文的问题是数据组织问题，应当在入库时解决：

1. **条文索引**：规程类文档入库时（维护工具或离线脚本），按“章—节—条—款—项”切分，生成条文索引：文档名、版本或施行日期、条号（数值）、章节路径、全文、对应的 RAGFlow 文档和切片编号。索引存为插件的本地数据（JSON 或 SQLite），随部署发布。切分规则由代码实现并有测试；切分结果由专家抽查（这里可以用模型辅助检查切分是否合理，但只在离线入库时，人工确认后才入索引）。
2. **查条走索引**：`kb_get_articles(document, articles[], parts?)` 一次查多条，从索引直接返回全文（毫秒级），`parts` 可以只取某几款、某几项；返回里带 `source`（index / local-fallback / not-found）和索引版本。RAGFlow 不参与查条。
3. **检索走 RAGFlow**：`kb_search(question, datasets?)` 语义检索，结果里凡是能对应到条文索引的，补上条号和“完整条文可用 `kb_get_articles` 获取”；模型从检索结果里**选条号**，原文由 `kb_get_articles` 给出。
4. **兜底**：RAGFlow 不可用时 `kb_search` 降级到本地条文关键词检索（现有做法）；`kb_get_articles` 不依赖 RAGFlow，不受影响。
5. **固定流程里**：合规审核需要的条文由插件按红线规则表、方案步骤类型查好，一次批量取出交给阶段；阶段只能引用给定的条号（#19 已验证）。

预设、案例类文档不按条切分，只走检索。

工具（rescue-commander 挂载只读的前三个）：

| 工具 | 说明 |
| --- | --- |
| `kb_search` | 语义检索（法规、预案、案例），结果标注条号和来源 |
| `kb_get_articles` | 按文档和条号批量取完整条文 |
| `kb_list_datasets` | 列出可检索的数据集 |
| `kb_upload_document`、`kb_parse_documents`、`kb_document_status`、`kb_add_chunks`、`kb_build_article_index` | 维护用，不挂到 rescue-commander |

### 4.8 指令发布与管控

沿用本项目的 actions、审批插件、审计插件和红线引擎，只改核对对象：

- `Plan.snapshot_id`、`WarningNotice.snapshot_id`、`Escalation.snapshot_id` 改为引用记录（字段改名为 `record_id`）。发布前按记录核对现场条件、预警等级、升级建议，并核对记录的时效（`CONTEXT_MAX_AGE`，占位 2 小时，按矿井时间；演示倍速下的处理见 4.10）。
- 红线引擎暂留在 `rescue_contract/redlines.py`，作为强制执行的规则，不迁入技能脚本（第 10 节待定）。合规技能引用它的规则表。
- 新增只读工具 `precheck_plan`（从 kb 的 `check_plan_redlines` 搬来）；`redlines_only=true` 只查方案类型和红线（固定流程用，方案还不在第一版快照里）。
- 封闭方案（P3，契约 0.9.0）：`issue_sealing_plan(record_id)` 只提交 `draft_sealing_plan` 的审核记录（plan-compliance/review）编号，不提交方案内容。actions 核对：审核结论为通过、审核记录里的方案与上游方案记录（sealing-plan/compose）一致、时效、工作面，再做方案类型和红线的强制校验；审核记录的人工确认项列进审批弹窗。方案不经模型转抄，也不在主预设的上下文里来回携带（第一版 token 高、笔误的来源）。
- 审批弹窗的内容由预检结果生成**结构化的审批说明**（`ApprovalSummary`：要做什么、引用哪些记录、核对结果、人工确认项），网页端渲染成文字；以后的对外接口直接用同一份数据，不透出工具原始参数（上一版 rescue-api 的要求）。
- 台账、审计里记录确认人和渠道（`Origin`）。本次只有网页端一个人，字段先留着，按角色限定确认人放到以后。
- 下发的封闭方案经 actions 转给模拟器执行（现有机制），之后可以复评效果，闭环在模拟矿井里真正跑通。

### 4.9 风险检测：一次性与持续检测

#### 标准放在技能里

风险检测是固定的标准，全部放在 `fire-assessment` 技能目录里，专家改这几个文件就改了标准，不用改插件：

| 文件 | 内容 |
| --- | --- |
| `references/collect.yaml` | 采集清单：读哪些测点（束管、上隅角、回风巷等）、多长的时间窗口 |
| `scripts/check.py` | 按固定顺序计算：整理数据（剔除故障、卡值测点，标注缺失）→ 实时报警 → 预警等级 → 自燃阶段 → 与基线比较。输出各工作面的等级、阶段、报警、相对基线的变化，以及 `anomaly`（是否异常）和异常原因。纯函数：证据文件进、结果文件出 |
| `references/watch.yaml` | 持续检测的参数：检测间隔（矿井时间，占位 10 分钟）、什么算异常（出现新报警、等级升高、阶段变化、数据中断超过若干分钟）、最长检测时长（占位） |
| `templates/check.md` | 检测结果的文字格式 |
| SKILL.md“风险检测”一节 | 什么时候做一次性检测、什么时候持续检测；发现异常后怎么做 |

`check.py` 复用 `alarms.py`、`warning.py`、`stage.py` 的同一批函数，与完整研判的结论一致。

**读数据由插件做，不由脚本自己做。** 如果脚本自己连矿井读数据，就要在 bash 沙箱里给它令牌（实验 0001 第 9.0 节结论 2），脚本要访问网络（违反 4.2 脚本约定 1），命令行由模型写、参数可能被改，结果也只在沙箱里、不能作为记录被引用。所以分工是：读什么由技能的采集清单定，读数据由证据插件按清单做，判断由 `check.py` 做，持续检测的循环由插件的后台任务做。

#### 一次性检测

指挥人员问“看一下现在矿井是否有异常”，主预设按技能调用 `check_mine(mode=once)`：采集 → `check.py` → 存检测记录 → 返回结果卡片（几秒）。主预设照结果卡片回答，不自己归纳数值。

#### 持续检测

指挥人员说“持续检测矿井动态，有异常的时候告诉我”，主预设调用 `check_mine(mode=watch)`：

1. 插件先做一次检测作为**基线**。如果此时已经异常，直接按下面第 4 步报告，不进入等待；
2. 否则用 DSH 的后台任务（`ctx.jobs.start`）登记一个任务，立即返回任务编号；主预设告诉指挥人员“已开始持续检测”，本轮结束；
3. 任务在 DSH 进程里循环：按矿井时钟每到检测间隔就采集 → `check.py`（与基线比较）→ 存检测记录。任务的进度行显示最近一次检测的矿井时间和结果，网页端任务列表里能看到，也能手动停止。不花模型 token；
4. `anomaly` 为真（或数据中断、达到最长时长）时任务结束，输出异常摘要和检测记录编号；
5. DSH 的完成通知唤醒智能体（会话空闲时开新一轮），主预设用 `job_output` 读结果，按技能用 `ask_user` 询问操作员：“检测到 1201 预警等级由 blue 升为 yellow（记录 RS-…）”，选项为**开始完整研判**（推荐）、**继续检测**、**暂不处理**，操作员也可以直接输入其他要求（DSH 提问卡片自带自由输入框）；
6. 智能体按回答处理：开始完整研判 → `run_fire_assessment`（4.4）；继续检测 → 以当前状态为新基线重新 `check_mine(mode=watch)`；暂不处理 → 确认后结束，并提醒此时没有持续检测在运行；自由回答 → 按要求处理。

约束：

- **只由人触发**：人设和 SKILL.md 规定，只有指挥人员要求时才启动持续检测；一个会话同时只能有一个持续检测任务（插件检查）；
- **唤醒上限**：`dsh-tool-jobs` 的 `maxConsecutiveWakes` 设为小值（占位 3），防止“唤醒 → 再启动 → 再唤醒”的循环；
- **不会自动发布任何指令**：发布仍需指挥人员要求并人工确认。

#### 检测判据（初稿，待专家评审）

以下是开发拟定的初稿，以现有值守进程的判据为基础，数值都是占位值，写进 `references/watch.yaml` 和 `references/collect.yaml`，整理后交专家评审。

**采集清单**（`collect.yaml`，按工作面）：

| 测点 | 指标 | 必需 | 用途 |
| --- | --- | --- | --- |
| 采空区束管（如 BT-1201-G1～G3） | CO、O₂、CH₄、C₂H₄、C₂H₂、H₂、CO₂、N₂ | 是 | 预警等级、自燃阶段、标志气体 |
| 上隅角（SM-1201-UC） | CO、CH₄、O₂、温度 | 是 | 实时报警、预警等级 |
| 回风巷（SM-1201-RET） | CO、CH₄、温度、风速 | 是 | 实时报警、趋势 |
| 进风巷、总回风 | CO、CH₄、风速 | 否 | 辅助 |
| 采空区测温点（TP-1201-G*） | 温度 | 否 | 辅助（煤温） |

时间窗口：最近 6 小时（趋势用），检测时取每个测点的最新值和窗口内序列。

**每次检测的顺序**（`check.py`）：

1. 数据整理：剔除故障、卡值测点（沿用现有卡值判据，恒为 0 且同测点 CO 仍在变化时按“未检出”处理）；列出缺失的必需测点；
2. 实时报警：甲烷超限、复燃（只对火区台账里已封闭或已启封的火区）等红线报警，沿用现有规则；
3. 预警等级：none / blue / yellow / orange / red，沿用 `thresholds.yaml`；
4. 自燃阶段：沿用 `thresholds.yaml` 的 stage 判据；
5. 与基线比较，判定是否异常。

**什么算异常**（相对基线；出现任一项即结束持续检测并报告）：

| 异常 | 判据（占位） |
| --- | --- |
| 新的实时报警 | 出现基线里没有的报警（按“规则编号 + 测点”区分） |
| 预警等级升高 | 等级高于基线（任何一级） |
| 自燃阶段推进 | 阶段序号大于基线 |
| 数据中断 | 必需参数的最新读数早于 `data_gap_h`（按测点组，占位：束管 3 小时、上隅角和回风巷 0.75 小时，约 3 个采样周期），或取数连续失败 3 次。（初稿是“连续 3 个检测周期没有新数据”，P4 实现时发现束管 1 小时、安全监控 15 分钟采一次，都长于 10 分钟的检测间隔，按周期会误报，改为按时长） |
| 必需测点失效 | 基线时正常的必需测点被判为故障或卡值 |

不算异常（只写进检测记录）：等级或阶段下降、等级不变时读数的波动、非必需测点故障。

**其他参数**：检测间隔 10 矿井分钟；最长检测时长 72 矿井小时（到时结束并报告“检测到期、未见异常”），另设真实时间 24 小时的硬上限；启动时基线里已经有实时报警的，不进入等待，直接按异常报告。

#### 为什么用后台任务，不用子 Agent 或定时任务

| 做法 | 问题 |
| --- | --- |
| 子 Agent 持续检测 | 每次检测都要模型调用一次工具，花 token；是否按时检测取决于模型；委派的子 Agent 审批策略为 never、有层数上限（#18、#19） |
| 智能体用 bash 在沙箱里后台运行脚本（`run_in_background`） | DSH 原生可行，但脚本要自己读数据，需要给沙箱令牌、访问网络；命令行由模型写；结果不能作为记录。作为后台任务插件不可用时的退路 |
| DSH 自带定时任务（`schedule`） | 每次触发都跑一轮模型；按真实时钟、最短 60 秒，与演示倍速下的矿井时间不一致；所有触发都进同一个会话 |
| **插件登记后台任务（本稿）** | 检测期间不经模型、不花 token；按矿井时钟；结果存为记录；结束时由 DSH 唤醒智能体。限制见下 |

#### 限制

#20 已在 DSH 0.2.1-rc.4 上验证（`docs/validation-checklist.md` #20）：登记、进度显示、网页上两击停止、模型 `job_kill`、唤醒、提问（三个选项加自由回答）都正常；网页关闭、空闲 20 分钟后任务仍在、照常唤醒，提问在会话列表里有“Waiting for answer”标记，重新打开后可以回答。限制有三条：

- **唤醒的这一轮失败时，异常会丢。** 验证中一次唤醒后模型请求卡住 178 秒，以 `STREAM_CLOSED`（stream ended before message_stop）结束，这个错误码不在 DSH 默认的可重试列表里：任务已结束，智能体没能提问，操作员不知道。#23 用故障注入复现了这个问题，并验证了两种补救，**两者都做**：
  1. **provider 重试**（第一道，P0 随主预设一起配）：`llm-deepseek` 的 `retryPolicy.retryableCodes` 在默认的 5 个之外加上 `STREAM_CLOSED`。验证中同一轮重试 2 次就恢复了，不多出轮次；重试发生在模型输出完整之前，不会重复执行工具。对所有轮次都有效，不只唤醒；
  2. **插件补发**（第二道，P4 实现）：证据插件在任务结束后监听拥有者的 `agent/error`、`agent/status`；被唤醒的这一轮以 error 结束时，用 `agent.followup()` 再投递同样的通知（来源沿用 `tool-jobs` 的 notice）。验证中补发后下一轮正常提问。要加退避（占位 1、5、15 分钟），最多 3 次；用完后在记录里标“唤醒失败”。
  都失败时，检测到异常的记录已经写进记录目录，演示控制台把它显示为“未确认的异常”，直到会话里出现对它的提问或回答。
- **DSH 重启、崩溃后任务消失，且不通知。** 正常关闭时会话日志记 `job/settled`（cause `teardown`），崩溃时只有 `job/registered`。缓解：检测记录带时间，演示控制台显示“持续检测：最近一次检测的矿井时间”，超过两个检测间隔没有新记录就标红；以后无人值守的恢复服务按会话日志的这两种情况判断并恢复。
- 唤醒后 `ask_user` 要有人在网页端回答；没人回答时问题一直挂着（阻塞模式，这正是以后要做无人值守的原因）。

实现时注意：`dsh-tool-jobs` 必须挂到 rescue-commander（正式预设里没有，否则 `ctx.jobs.start` 失败）；结束原因不要再写停止原因（DSH 会自动附加）；网页上停止任务也会唤醒智能体，人设里要说明“被用户停止时简要确认即可”。

#### 以后的扩展

- **界面按钮**：按钮经会话入口 `rescue-entry` 向会话发送同样的请求（或直接调用插件），`Origin.trigger=button`（4.11）；
- **无人值守**：发现异常后不询问，直接 `run_fire_assessment`，结果推送给值班人员。另加一个插件或服务，负责发现被中断的持续检测（DSH 重启、Agent 被释放）并恢复。为此本次的检测记录就要带上任务编号、会话、基线和最近一次检测时间，恢复时按记录重新登记；
- **按钟点复查**：需要“每天 8 点复查一次”时再挂 DSH 自带的定时任务。

### 4.10 模拟矿井的连续运行与演示控制台

现在的模拟矿井每次加载一个场景，从场景起点运行（或手动推进时钟）。演示需要“先正常运行、按下按钮后出事故”，并能临时改某个传感器的读数。

#### 模拟矿井的改动

1. **常态运行**：服务启动后默认运行常态（`s1-normal` 的参数），按实时（1 倍速）或设定倍速连续产生数据，没有终点。
2. **事故注入**：“开始演示”时，把一个事故场景（本次 `s4-escalation`）的事件脚本以**当前矿井时间为起点**接到常态上，物理状态连续（不清空历史，之前的读数仍是正常数据）。场景的 `at_h` 改为相对注入时刻。
3. **读数设置（观测层）**：控制台可以对单个测点设置：跟随模型（默认）、固定值、在模型值上加偏移、在若干分钟内线性变到某值、故障（无数据、卡死、跳变）。设置只改测点读数，不改物理模型；控制台同时显示“模型值”和“输出值”，并标明哪些测点被人工设置。人工设置记入模拟器日志，便于复盘时区分。
4. **倍速分段**：演示脚本可以给出倍速计划，例如常态 60 倍、注入后 600 倍，检测到异常后自动暂停（模拟矿井只读挂载记录目录，看到 `anomaly` 为真的检测记录就暂停，DSH 侧因此不需要持有 `/sim` 控制令牌）。理由：s4 的 `speed: 1200` 下，研判记录的 2 小时时效只合 6 秒真实时间，指挥人员来不及确认；暂停后时效检查照常有效，演示人员在控制台按需继续。读记录目录只为演示的自动暂停，不是矿井接口的一部分，真实矿井适配器不读记录。
5. 模拟器真值（`truth`）、读数设置、倍速只在 `/sim` 控制接口和控制台上，用单独的控制令牌；MCP 工具和智能体看不到（约定 4）。

#### 演示控制台（网页）

由模拟矿井服务提供（`/console`，控制令牌登录），只给演示人员用：

| 区域 | 内容 |
| --- | --- |
| 运行状态 | 矿井时间、倍速、当前阶段（常态 / 已注入事故名 / 已暂停）；开始演示、暂停、继续、调倍速、重置为常态 |
| 测点 | 按工作面分组的测点列表和最近若干小时曲线；每个测点可设置读数（见上） |
| 事件 | 场景脚本事件（何时漏风突增等）、检测记录与持续检测状态（读记录目录）、已下发并执行的处置（来自 actions） |
| 真值 | 模拟器内部状态（煤温、氧浓度场等），默认折叠，提示“智能体看不到” |

控制台复用现有 `scripts/sim.py` 的控制接口，不另起一套。评测仍用手动时钟（`manual_clock`），不受常态运行影响。

### 4.11 会话入口与接口扩展点

上一版有两套对外接口：rescue-api（`/api/v1`，REST + SSE，资源为 Conversation、Message、Run、Question、Approval、Attachment、Deliverable，18082 端口）和 SubAgent 接口（上游约定的 `POST /api/application/prompt/stream`，SSE 事件 `LLM_STREAM`、`CHAIN_OF_THOUGHT`、`TABLE_OUTPUT`、`CHART_OUTPUT` 等，18081 端口）。以后合并为一套并入本项目。本次不实现，但下面这些现在就按统一的方式做，以后加接口时只写协议层，不回头改业务：

| 扩展点 | 本次做什么 | 以后的接口怎么用 |
| --- | --- | --- |
| 会话入口 `rescue-entry` 插件 | 本次只定接口、不实现：`sendMessage(conversationId, origin, input)`、`startConversation(origin, preset, input)` | 界面按钮（“开始持续检测”）、rescue-api 的创建会话和发送消息、SubAgent 接口的一次请求，都调这个服务；DSH 类型仍只在 `src/adapter/dsh.ts` |
| 来源 `Origin` | 记录、台账、审计都带 `channel`、`trigger`、`caller`、`conversation_id` | 按渠道、调用方查询和限权 |
| 外部编号 | 记录编号、会话编号由本系统分配，不使用 DSH 的会话编号、工具调用编号、文件路径 | 对外接口的编号直接用 |
| 结果卡片 `ResultCard` | 固定流程工具返回结构化结果（标题、结论摘要、记录编号、文件、可选的下一步） | 转成 Deliverable、`TABLE_OUTPUT`、`CHART_OUTPUT` |
| 人工问题 `HumanInputRequest` | 固定流程缺人工输入时返回结构化问题（4.4 第 6 点），主预设转成 `ask_user` | 转成 rescue-api 的 Question；无人值守的 SubAgent 请求直接在回答里列出 |
| 审批说明 `ApprovalSummary` | 审批插件按预检结果生成（4.8） | 转成 rescue-api 的 Approval |
| 流程事件 `FlowEvent` | 固定流程每个阶段开始、结束、失败时发出（阶段名、状态、记录编号），写进运行记录 | 转成 `CHAIN_OF_THOUGHT` 或 rescue-api 的过程事件 |
| 文件 | 按记录编号取文件（4.3），不按路径 | Deliverable 下载 |
| 无人值守 | 固定流程不依赖 `ask_user` 也能结束（缺输入就返回问题清单）；持续检测发现异常后“询问操作员”写在技能里，换成“直接研判”只改技能和预设；发布动作必须人工确认，无人值守入口一律不能发布 | 以后的无人值守预设（上一版 `rescue-subagent` 去掉了 `ask_user` 和 `present`）直接复用固定流程 |
| 端口 | 13080 网页端；18081、18082 预留给以后的接口；Docker 里不映射 | 合并后用一个端口还是两个，到时定 |

这些结构定义在契约里（`rescue_contract`，导出 JSON Schema 给 TS 侧用），和 Record 一起进 0.7.0。

## 7. 安全与部署

### 7.1 沙箱探测的结论

依据实验 0001 第 0 步探测（DSH 0.2.1-rc.4，bash 沙箱 workspace-write）：生产配置下，沙箱里拿不到 MCP 令牌，写不了仓库、`var/`、技能目录；但**读不受限**、**确认框批准提权后可写任何文件**、**网络出站不受限**。另外本机开发配置下 `RESCUE_MCP_TOKEN` 实际为空，服务不校验令牌。

| 项目 | 演示（Docker）必须做 | 生产部署再做 |
| --- | --- | --- |
| 令牌 | 设置令牌；mine_data 只读令牌（证据插件用）、actions 令牌（主预设用）、`/sim` 控制令牌（只给控制台和 actions 的模拟执行）分开，DSH 不持有 `/sim` 控制令牌 | 每个服务、每个调用方单独令牌 |
| 密钥文件 | DSH 容器里不放 `.env`；各服务容器只拿自己需要的变量 | 同左，加上密钥服务 |
| 技能脚本子进程 | `runScript` 按白名单传环境变量、设超时；技能目录只读挂载（子进程能写 DSH 用户能写的任何地方，#22） | 评估用 DSH 的沙箱服务（`ctx.sandbox`）包住子进程：只许写本次运行目录、不许出网（未验证） |
| DSH 凭据文件 | `.dsh-home/.credentials.yaml` 与沙箱在同一容器，沙箱能读（探测结论）。演示前确认能否限制沙箱读取该目录；不能则至少保证其中只有模型、RAGFlow 凭据，没有其他服务的令牌 | 凭据放到沙箱读不到的位置或外部密钥服务 |
| 只读挂载 | 技能目录、代码只读；记录目录由 DSH 容器写，actions、模拟矿井只读；台账卷只挂到 actions；审计卷只挂到 DSH（审计插件写） | 同左 |
| 提权 | 预设说明里要求不申请提权；演示中出现提权确认一律拒绝 | 容器只读挂载兜底，不依赖确认框 |
| 网络 | compose 内部网络；只映射网页端和控制台端口 | 容器出站白名单（模型服务、RAGFlow） |

### 7.2 Docker 部署

参考上一版 `rescue/docker/`（DSH 镜像 + 插件包 + 技能挂载，镜像构建时跑技能自检）。

| 服务 | 镜像 | 端口（宿主） | 挂载 | 说明 |
| --- | --- | --- | --- | --- |
| `dsh` | DSH 0.2.1-rc.4 + 本项目 bundle + Python 运行时（技能脚本的依赖清单） | 13080（网页端） | 技能目录（只读）、DSH 数据卷、记录卷和审计卷（读写） | 预设、证据与风险检测、固定流程、知识库、后台任务、审批、审计；沙箱在容器内运行 |
| `mine-sim` | Python 服务镜像 | 13090（控制台） | 记录卷（只读） | MCP + `/sim` + 控制台；启动即常态运行 |
| `actions` | 同一个 Python 镜像 | 不映射 | 记录卷（只读）、台账卷（读写） | 指令发布 |
| RAGFlow | 外部 | — | — | 演示用现有的演示数据集；断开时知识库插件按 4.7 降级，查条不受影响 |

- Python 服务共用一个镜像、不同启动命令；现在 `make up` 的 7 个服务和值守进程减为 2 个（模拟矿井、actions），其余进 DSH。
- 健康检查：各服务 `/health`，DSH 等依赖健康后再启动；DSH 的健康检查包括证据插件连上模拟矿井；`make demo-up`、`make demo-down`、`make demo-reset`（清空 `var/demo` 卷、模拟矿井回到常态）。
- 演示数据写到单独的数据卷（`var/demo`），不混进开发的 `var/`（约定 9）。
- 本机开发方式（`make dev`）保留。

实现（P5，2026-11-04）：`docker/python.Dockerfile`（mine-sim、actions 共用，按 uv.lock 安装）、`docker/dsh.Dockerfile`（DSH 0.2.1-rc.4 + bundle + 技能脚本的 Python，构建时跑技能自检）、`docker/compose.yml`、`scripts/demo.sh`（`make demo-up` / `demo-down` / `demo-reset` / `demo-logs`）。数据卷都在 `var/demo/`（records、runs、ledger、audit、dsh-home、documents），令牌第一次启动时随机生成在 `var/demo/tokens.env`。容器间按服务名访问 MCP 要 `RESCUE_MCP_ALLOWED_HOSTS`（DNS 重绑定防护的白名单）；证据插件的脚本运行目录单独一个卷（`RESCUE_RUN_DIR`）。

验证清单 #21（2026-11-03）：容器里沙箱能工作，权限与本机一致。Docker 默认安全配置下 DSH 用 Landlock（部分强制）代替 bwrap；保持默认配置，不为 bwrap 放开容器的 seccomp、AppArmor 和 /proc 屏蔽。DSH 镜像要显式配置 `workspace-controller.documentsDirectory`（精简镜像没有 `xdg-user-dir`）。
