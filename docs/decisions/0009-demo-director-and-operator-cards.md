# 0009 演示由导演推进；处置选项和现场条件由代码给出卡片；批准超时只对低风险动作自动放行

状态：采纳（2026-11-09）；细化 [0008](0008-guard-and-rescue-mine.md) 的动作分级表。设计见 `docs/design-v5-demo-flow.md`，验证见验证清单 #37–#39。

## 背景

手动演示和故事线脚本都靠“推进多少小时、等告警”来走完各预警等级，时间推进和智能体处理不同步，容易冲过等级或卡住（故事线曾在黄色、红色阶段超时）。智能体对处置自己做主（橙色、红色不向人请示），操作员没有机会“选一选”，也看不出不同处置会走向哪里。批准超时目前只升级提醒，演示和正常运行的行为不统一。

## 决定

1. **暂停就是冻结矿井时钟，由导演推进。** 导演（模拟矿井里的状态机）先一次跳进、再按步推进，每步等监听器心跳追上再读事件库里的等级告警；到每一级暂停等操作员选择，按所选处置的累计个数走分支剧本（继续到下一级 / 跑一段后结束 / 追加处置）。导演不判断预警等级，只读监听器告警；分支参数是演示剧本的占位值，不是模型预测。
2. **操作员的选择通过 DSH 自带的提问卡片，批准仍走审批弹窗（点两次）。** 不做“点选即批准”的地图面板：批准始终由审批插件负责，模型伪造不了，全用 DSH 原生界面，任何环境都能用。
3. **“该问什么、选什么”由代码给出**：处置选项表（`response_options.py`）、封闭方案现场条件卡片（`field_conditions.py`），智能体用 `get_response_options`、`get_field_conditions` 取来原样问；答案由代码换成方案步骤或数值，换不了就报错重问；防灭火方案的可选步骤由代码强制成操作员所选。选项里的数值只是常用档位，不是阈值，红线仍按实际输入判定。
4. **导演按矿井实际执行的处置识别选择**（guard 经 rescue-mine 下发的处置，来源 `action`），不解析智能体的话；控制台复选框是没有智能体时的人工通道。
5. **动作分级表加 `on_timeout`（approve / reject / escalate，缺省 escalate）。** 批准超时（真实时间）后由审批插件按表处理；**只有加密监测 `start_monitoring`（只增加观察、不改变现场、可随时停止）设为 approve**，且放行后仍提醒上一级；影响现场或不可逆的动作（预警广播、撤人、升级、封闭、调度、防灭火方案、启封）一律 escalate，不自动执行，有测试固定。真实运行里没人批准时不应替人做决定。
6. **“告警是否已处理”由代码判断。** 唤醒消息对已处理的告警标注“重复投递”并换掉“立即研判”的要求（原来消息自相矛盾，智能体约三分之二照做重复研判）；评测里唤醒用例的提示词用同一个生成器生成。

## 后果

- 向人提问由三种情况变为四种（加“橙色研判后选处置”）；技能和主预设同步。
- 自动放行要在到点时中止请求的 signal，否则网页端的确认卡片和会话上的 “Approval” 标记残留；这依赖 DSH 0.2.1-rc.4 的请求对象可写，升级 DSH 要重核。
- 评测运行器要能代答卡片（用例 `operator_cards: true`）；`no_questions` 不计代码给出的卡片。
- 缺现场条件时封闭方案仍可下发（只在审批弹窗里提示），这是原有设计，本决定没有收紧；是否收紧是单独的安全策略决定。
