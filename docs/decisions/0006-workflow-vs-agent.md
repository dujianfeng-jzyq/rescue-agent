# 0006 确定性流程用代码工作流实现，智能体只做理解、开放问答、经验判断和异常处理；不采用 DSH 自带工作流

状态：采纳（2026-11-02）；部分被 [0007](0007-skills-plugins-fixed-flows.md) 取代（2026-11-03）：决定 4（工作流放在 `mcp/workflow` 服务）改为技能脚本 + DSH 插件；决定 5 和“考虑过的方案”里关于 DSH 插件、DSH 工作流的结论按 #19 更新。决定 1–3（确定性工作用代码、留给智能体的工作、用不可变记录串起指令发布）仍有效，“快照”改为“记录”。

## 背景

一期按“总指挥协调 Agent 委派专业 Agent、由大模型决定调用顺序”的方式搭建：计算在 MCP 服务里，编排、选测点、汇总结论、填写方案现场条件都由大模型完成。当时没有专门比较“固定流程”和“大模型编排”两种做法，而是顺着 DSH 的多 Agent 能力做下来的。

评测和指令台账暴露出以下问题：

1. **红线引擎的输入由模型填写。** `validation.py` 只检查方案类型、时效和红线，不核对 `plan.context` 是否与实测一致（验证清单 #10 已记）。`var/eval/actions-ledger.jsonl` 里同一场景、同一时刻的 5 份已发布封闭方案中，`explosion_risk` 有 3 份写 `may_become_explosive`、2 份写 `not_explosive`，而同期评测运行中 `assess_explosion_risk` 对各束管测点返回的都是 `not_explosive`；`fire_source_confirmed: true`、`methane_rising: false` 没有任何工具给出，是模型自己判断的。RL-075、RL-085 都依赖这几个字段，所以“模型变弱只影响建议质量、不会突破安全底线”的前提并不成立。`publish_warning` 的等级、`Escalation.recommended_level` 同样由模型填写，没有与计算结果核对。
2. **同一个研判，每次做法不一样，且重复。** `s2-assess-1201` 中，总指挥委派研判后自己又调了 `assess_warning_level`、10 次以上 `gas_trend` 和多次 `assess_explosion_risk`；研判 Agent 调 `gas_trend` 的次数在 6–16 次之间，选哪些测点每次不同。一次 `s4-escalate` 中，总指挥单个会话约 80 万 token。
3. **剩下的评测失败几乎都出在模型写结论的环节**：自己计数（“上述 7 条”）、归纳界限（“低于 12%”）、漏写自燃阶段、点名没调用的工具、笔误（1201 写成 1210）、中途向人提问而不收尾。在提示词里加约束只能一次堵一类问题，而且换一个模型可能又会出现。
4. **耗时。** `s4-sealing-plan` 一次 446–785 秒，`s4-escalate` 有一次超过 900 秒。主要花在 kb：合规 Agent 每次运行开 3 个会话，反复检索。2 批评测中 168 次 `get_article`，117 次来自本地留存（很快），32 次走 RAGFlow，19 次没找到（会重试）；另有大量 `search_regulations`、`search_mine_plans`。

## 决定

1. **满足以下任一条件的工作，用代码写成工作流（MCP 工具）**：
   - 步骤由规程或 SOP 规定，每次都应该一样；
   - 产出是数值、等级、计数、结论，或者会成为红线引擎的输入；
   - 需要在没人提问时运行（报警、定时复评）；
   - 复盘时需要逐步解释。
2. **留给智能体的工作**：
   - 理解提问并选择工作流；
   - 回答开放问题；
   - 在代码生成的方案骨架上补充需要经验判断的内容（可选措施、描述、现场确认项）；
   - 在代码生成的事实之外写解释；
   - 处理异常（数据缺失、工具报错、指令被拒、向人索取系统里没有的信息）；
   - 合规审核中需要人工判断的复核项。
3. **用“研判快照”把工作流和指令发布串起来。** 工作流生成不可变、带编号的快照；方案、预警、升级都引用快照编号；actions 发布前（以及审批插件预检时）按编号重算并核对现场条件和等级，不一致就拒绝。这样，“数值只来自代码”从提示词约束变成代码里的强制检查。
4. **工作流在新增的 `mcp/workflow` 服务里实现（Python，端口 8107）**，直接复用 `rescue_fire_model`、`rescue_ventnet`、`rescue_dispatch` 的计算函数，数据仍经 `MineData` 客户端读取。
5. **不采用 DSH 自带工作流**（`dsh-workflow-ptc` + `dsh-tool-workflow`）。理由见下文“考虑过的方案”。
6. 具体设计、实施顺序和验收标准曾写在 `docs/workflow-design.md`（第一版的工作流设计，随第一版 Python 服务一起于 2026-11-10 删除，需要时用提交历史查看）。

## 考虑过的方案

- **继续由大模型编排，靠提示词和技能约束。** 过去两周一直在这样做，每改一次只能消除一类错误；而且红线输入由模型填写这个问题，靠提示词解决不了。
- **DSH 自带工作流**（验证清单 #18，2026-11-02 实测）：
  - 脚本是模型现写的，每次运行的步骤不同；不能保存审定过的工作流，没有断点记录，也不能恢复。
    （2026-11-02 更正，见验证清单 #19：`workflow` 工具的参数就是脚本，可以要求模型原样提交固定脚本，不一定每次现写；DSH 没有“保存的工作流”，但插件可以用 `ctx.workflowEngine.start` 运行仓库里审定过的脚本。没有断点记录、不能恢复仍然成立。）
  - 脚本只能调 `agent()`，不能直接调用 MCP 工具，每一步仍要经过模型转写。
  - `agent()` 不能指定预设，子 Agent 只能用调用方的 rescue-commander 预设：有 actions，没有 kb，也不能再委派（层数上限 1）。所以“方案起草 → 合规审核”的循环无法用它编排。
  - 子 Agent 的审批策略被强制为 never。调用 actions 时没有弹确认就被拒，审计记成“用户拒绝”，复盘时会误判。
  - 优点：结构化输出可靠（5/5 符合 schema）；在 workspace-write 权限下能运行；网页端能显示运行阶段。
- **在 DSH 插件（TypeScript）里写固定流程。** 会把领域逻辑分散到 TS 和 Python 两处，违背“契约是边界、红线只实现一次”的约定；而且 rc.4 的 headless 入口不支持 Agent 预设，报警触发也绕不开这个限制。
  （2026-11-02 补充，见验证清单 #19：如果插件只做编排，即调用顺序、循环和分支，数值、判据和红线仍在 Python 的 MCP 服务里，就不存在领域逻辑分散的问题。插件可以用 `ctx.tools.execute` 调 MCP 工具，用 `ctx.subagents.startActivation` 按指定预设起子 Agent 并要求结构化输出，审批和审计照常。“方案 → 合规审核”循环可以按这种方式重新评估；报警触发的限制仍然成立。）

## 后果

- 契约升到 0.5.0：新增快照模型；`Plan`、`WarningNotice`、`Escalation` 增加 `snapshot_id`；改动后要运行 `make schema`。`validation.precheck` 增加快照核对，actions、审批预检和 kb 自查三处共用。
- 新增 `mcp/workflow` 服务和值守进程，`scripts/mcp-up.sh`、`.env.example`、预设的 MCP 挂载、`check_patches.py` 都要相应修改。workflow 服务只读（只写快照和值守事件，不对外发指令），不改变“只有 rescue-commander 挂载 actions”的约定。
- 新判据（升级建议、甲烷是否上升、区域甲烷取哪些测点、多测点爆炸危险性取最不利值）都放进配置文件，全部是开发占位值，待专家审定。
- 等 W1–W3、W7 上线、评测不退化后，移除 rescue-assessment、rescue-dispatch 预设，它们的职责改由工作流工具承担。保留 rescue-plan 和 rescue-compliance：独立审核有规程上的意义。
- 技能里的“调用顺序”部分改成“调用哪个工作流”，技能的重点转向解释和经验判断。
- 评测增加两项检查：“报告事实部分是否原样粘贴”和“指令是否引用了快照”。
