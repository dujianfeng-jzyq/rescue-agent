# 路径规划服务对接方案（mine-route-api）

日期：2026-11-17　状态：草案（2026-11-17 修订：改为以贵方路线为准），请贵方重点回复第 6 节第 1–6 条

## 1. 目标与边界

我方的煤矿应急救援智能体（一期场景：采空区煤自燃）在预警等级达到橙色及以上时，会为受威胁人员计算撤离路线（避灾路线），显示在通风图上。现有路线由我方的简化算法给出：完全避开受污染巷道，长度按巷道长度计算。

我们计划**以贵方路径规划服务 `mine-route-api` 的路线为准**：服务可用时，通风图和研判报告只显示贵方路线，下发到井下的撤人通知里的路线也取贵方结果；服务不可用时才改用我方路线，并在界面上标明“本系统计算（外部服务不可用）”。两种路线都会计算并存档，用于复盘和改进算法。先用模拟矿井和占位参数打通全流程，再随真实矿井数据到位逐步替换占位值。

因为贵方结果会直接显示给指挥人员并写进撤人通知，第 6 节第 1–6 条（空结果原因、结果含义、可用性等）请优先答复。

撤离路线只作辅助参考，不替代规程要求的避灾路线图和应急预案。撤人按预案立即执行，不等计算结果。

## 2. 分工

| 方 | 负责 |
| --- | --- |
| 贵方 | 部署和运行服务，保证可用性；提供稳定的地址、接口说明和版本号；接口变更和停机维护提前通知；说明计算方法和适用范围；答复第 6 节 |
| 我方 | 适配服务：生成输入、调用、校验、把结果换回我方巷道编号；保存每次调用的输入和输出（用于复盘）；按下面的规则显示和使用结果，服务不可用时用我方路线兜底 |
| 矿方 | 提供真实通风网络数据：坐标（或巷道长度和高差）、断面、风量和风向、烟雾传感器、出口和避难硐室位置、不可通行巷道 |

## 3. 调用方式

- 调用方只有我方适配服务一个（内网）：`POST /api/v1/routes`，健康检查 `GET /healthz`。
- 调用时机：预警等级达到橙色及以上、且有受威胁人员时调用。当前接口只支持单个终点，所以每组人员要对每个候选终点各调用一次。研判按小时进行，调用量很小。
- 每次调用超时 5 秒。

按每组人员分别判断显示哪种路线：

| 贵方服务的情况 | 显示和撤人通知用 | 界面标注 |
| --- | --- | --- |
| 返回路线，且通过我方校验（首尾正确、巷道连续） | 贵方路线 | “外部路径规划服务”，附当量距离、烟中时间、暂时脱险时间；穿过有烟巷道时写明 |
| 返回空结果（`routes: []`） | 贵方结果：无可行路线，需人工研判（不改用我方路线） | “外部路径规划服务：无可行路线”，贵方给出原因后照写 |
| 连不上、超时、返回非 200、格式不对或没通过校验 | 我方路线 | “本系统计算（外部服务不可用：原因）”，线型和颜色不同 |

## 4. 快速接入阶段的输入

模拟矿井缺少贵方服务需要的大部分数据，暂时按下表填写。所有占位值都会在结果里标为“试验性”，并交由专家审定。

| 字段 | 取值 |
| --- | --- |
| `nodes` | 我方生成的平面占位坐标：每条巷道的折线长度等于它的实际长度；z 一律取 0 |
| `height` / `width` | 统一取 3 m × 4 m |
| `windSpeed` | 设计风量 ÷ 断面，按巷道方向取正值 |
| `smokeConcentration` | 受污染巷道取一个固定占位值，其余巷道取 0 |
| `start` / `target` | 起点是人员所在巷道的中点；终点是地面出口或避难硐室，逐个调用 |
| `walkSpeed` / `maxSmokeTime` | 都是占位值；`maxSmokeTime` 暂取 900 s，待按自救器的额定防护时间确定 |

采空区漏风通道不作为可通行巷道传入。

## 5. 已做的验证（2026-11-17，192.168.0.200:8080）

健康检查正常；示例输入 `input.json` 返回 1 条路线 `[3,6,5,4,8,7,9]`；风速越界时返回 400；可以逆着巷道方向通行。下面几项会影响对接，对应第 6 节的请求：

- 终点不可达和烟中时间超限都只返回 `{"routes":[]}`，两种情况无法区分；
- 有两条可行路线时只返回 1 条；
- 巷道上的 `length` 等附加字段和未知的顶层字段都被静默忽略；长度只按坐标计算。例如一条巷道水平 100 m、高差 50 m（实际斜长 111.8 m），当量距离为 408.8 m。

## 6. 请贵方支持或说明

**必须确认（贵方结果为主后，影响能否使用）**

1. 结果为空时给出原因，如 `reason: "unreachable" | "smoke_time_exceeded"`。空结果时界面显示“无可行路线，需人工研判”，“没有路”和“有路但烟中时间超过上限”对指挥的意义完全不同，必须能区分。烟中时间超限时，能否同时返回那条路线和它的烟中时间？
2. 路线的含义和适用范围：路线能否直接作为撤人路线下发到井下？允许穿过有烟巷道（烟中时间不超过 `maxSmokeTime`）的依据是什么？计算方法是否经过验证或用于过实际矿井？哪些情况下结果不可信？
3. 可用性：是否 7×24 运行，重启后能否自动恢复，有没有计划停机、停机前怎样通知，出现故障时联系谁。
4. 响应时间：典型和最长响应时间，与节点数、巷道数的关系；节点数、巷道数的上限。我方超时 5 秒，超时即改用我方路线。
5. 错误的含义：哪些是输入问题（400）、哪些是服务内部问题（5xx，可以重试）；错误返回的格式是否固定。
6. 同一输入多次调用，结果是否总是相同（复盘时要能重算）。

**希望支持**

7. 巷道可以选填实际长度和高差（如 `edges[].length`、`edges[].rise`，单位米）。填了就优先于按坐标计算的结果，因为通风网络图通常是示意图，巷道也是弯的。
8. 支持多个终点（如 `targets: [...]`），一次调用就返回到最优终点的路线。
9. 结果里带上计算方法的版本号（如 `version`），便于复盘。
10. 遇到未知字段时返回 400，不要静默忽略。
11. 鉴权：固定令牌（`Authorization: Bearer <令牌>`）或 IP 白名单。

**请说明**

12. 返回几条路线、按什么规则筛选，能否指定返回前 K 条？
13. 当量距离的计算公式和系数表（逆风、顺风、坡度怎么折算）。
14. `smokeConcentration` 的单位和含义；它怎样影响通行速度和烟中时间；是否只要大于 0 就算“有烟”。
15. 巷道是否总能双向通行；能否标记不可通行的巷道（如已密闭、垮落），还是由调用方不传这些巷道？
16. 日志放在哪里，接口变更怎样通知。

## 7. 计划

| 阶段 | 内容 | 依赖 |
| --- | --- | --- |
| 一 | 我方适配服务和接口一致性检查（以贵方示例输入作为固定用例） | 现有服务可访问 |
