# 路径规划服务接口测试情况与配合事项（mine-route-api）

日期：2026-11-17　测试地址：内网 192.168.0.200:8080

我们对贵方的路径规划服务 `mine-route-api` 做了接口测试。服务的结果将作为井下人员撤离路线的参考，所以对结果含义、空结果原因和可用性要求较高。下面列出测试情况、发现的问题和需要贵方配合的事项，请优先答复第一节的第 1–6 条。

## 一、测试情况

示例输入返回的路线和指标稳定，接口可用。表的后半部分是需要贵方修改、支持或说明的地方，对应第二节的问题。

| 测试 | 结果 |
| --- | --- |
| `GET /healthz` | 200，`ok` |
| 示例输入 `input.json`（起点 3，终点 9） | 200，返回 1 条路线 `[3,6,5,4,8,7,9]`，当量距离约 1465 m，烟中时间约 236 s，暂时脱险时间约 601 s |
| 风速超出范围（99） | 400，`{"error":"风速超出系数表范围"}` |
| 逆着巷道 source→target 方向通行 | 可以（示例结果里 6→5→4 是逆向走的） |
| 终点不可达 | 200，`{"routes":[]}` |
| 烟中时间超过 `maxSmokeTime` | 200，`{"routes":[]}`，与不可达无法区分 |
| 有两条可行路线的小网络 | 只返回 1 条 |
| 巷道上附加 `length` / `length_m` / `distance` 字段 | 被忽略，长度只按节点坐标计算 |
| 未知的顶层字段 | 被忽略，不报错 |
| 100 m 水平 + 50 m 高差的巷道 | 当量距离 408.8 m（实际斜长 111.8 m），坡度影响很大 |
| 我方测试网络（部分巷道有烟，`maxSmokeTime` 900 s） | 一个起点正常返回路线；另一个起点返回空结果；`maxSmokeTime` 放宽到 5000 s 后返回穿烟路线（烟中约 2033 s） |

## 二、需要贵方配合的事项

### 必须确认（影响结果能否使用）

1. **结果为空时给出原因**，如 `reason: "unreachable" | "smoke_time_exceeded"`。“没有路”和“有路但烟中时间超过上限”对现场指挥的意义完全不同，目前两者都只返回 `{"routes":[]}`，无法区分。烟中时间超限时，能否同时返回那条路线和它的烟中时间？
2. **路线的含义和适用范围**：路线能否直接作为撤人路线下发到井下？允许穿过有烟巷道（烟中时间不超过 `maxSmokeTime`）的依据是什么？计算方法是否经过验证或用于过实际矿井？哪些情况下结果不可信？
3. **可用性**：是否 7×24 运行，重启后能否自动恢复，有没有计划停机、停机前怎样通知，出现故障时联系谁。
4. **响应时间**：典型和最长响应时间，与节点数、巷道数的关系；节点数、巷道数的上限。
5. **错误的含义**：哪些是输入问题（400）、哪些是服务内部问题（5xx，可以重试）；错误返回的格式是否固定（目前是 `{"error": "…"}`）。
6. **结果的确定性**：同一输入多次调用，结果是否总是相同（事后复盘时要能重算）。

### 希望支持

7. **巷道可选填实际长度和高差**（如 `edges[].length`、`edges[].rise`，单位米），填了就优先于按坐标计算的结果。通风网络图通常是示意图，巷道也是弯的，直线距离不等于巷道长度；没有可靠坐标时也能使用服务。
8. **多个终点**（如 `targets: [...]`）：一次调用返回到最优终点（按贵方的排序规则）的路线，不必逐个终点调用。
9. **结果里带计算方法版本号**（如 `version`，系数表变化时变化），复盘时能知道当时用的是哪一版。
10. **未知字段返回 400**，不要静默忽略，避免字段名写错却得到看似正常的结果。
11. **鉴权**：至少支持一个固定令牌（`Authorization: Bearer <令牌>`），或在服务器上按 IP 白名单限制访问。

### 请说明

12. 返回几条路线、按什么规则筛选，能否指定返回前 K 条？
13. 当量距离的计算公式和风速系数表（逆风、顺风、坡度怎么折算）。
14. `smokeConcentration` 的单位和含义（体积分数？遮光度？），它怎样影响通行速度和烟中时间；是否只要大于 0 就算“有烟”。
15. 巷道是否总能双向通行；能否标记不可通行的巷道（如已密闭、垮落），还是由调用方不传这些巷道？
16. 服务日志放在哪里，接口变更怎样通知。
