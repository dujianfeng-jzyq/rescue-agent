# 第五版设计（草案）：按预警等级的演示流程与统一的人工确认

状态：草案，2026-11-09。导演与分支表（第 7 节第 2 步）已实现，其余未做；进度见文末。所有阈值、时限、分支结果均为占位值，待专家审定。

## 1. 目标

1. 程序启动后处于常态：可以讲解设计思路、界面，点击地图让智能体研判。
2. 在矿井控制台点一次“开始演示”：注入事故，出现预警等级后矿井时间自动暂停；操作员选择处置后时间继续，**后续走向由所选操作决定**；故事线走完自动结束，不需要再点控制台。
3. 演示和正常运行用同一套规则：**对外动作下发前一律人工确认**，超时按动作分级表处理。

## 2. 流程

```
常态 ──[开始演示]──> 注入事故 ──> 出现某级预警 ──> 时间暂停
   ──> 智能体研判，给出推荐 ──> 操作员选处置类型（兼作确认）
   ──> 下发（guard → rescue-mine）──> 时间继续
   ──> 导演按“（等级，所选操作）”换剧本 ──> 下一级 / 回落 / 结束
```

分支表（占位，数据放 `scenarios/demo-flow.yaml`）：

| 等级 | 可选操作 | 走向 |
|---|---|---|
| 黄色 | 观察跟进（monitor） | 继续发展到橙色 |
| 橙色 | 注氮、注浆、…（按选项编号） | 只选 1 项 → 升红；选 3 项 → 回落黄色 |
| 红色 | 撤人、封闭、… | 封闭 → 复评 → 稳定，故事线结束 |

要点：

- 分支按**操作员选的选项编号**走，不解析智能体实际提交的步骤（智能体可能多做或少做，解析会让分支不确定）。
- 分支剧本沿用 `SimEngine.inject` 的做法：从该时刻起换一套过程参数，物理状态连续。参数要调到结果确定，并写明这是演示剧本，不是模型预测。

## 3. 时间

- **暂停就是时钟冻结**（沿用 `Clock.set_paused`）。冻结期间矿井时间不走，所以：监听器（按矿井时钟取数）不跑，不会重复告警；跟踪计划不会到点；复盘时长不被拉长。
- 代价：暂停时读数静止。可选改进（后做）：暂停期间噪声按真实时间换种子，只改读数、不动物理状态，数值保持在当前等级内。
- 批准超时按**真实时间**算，不受矿井时钟暂停影响。

## 4. 导演（演示驱动）

- 一个状态机服务，不依赖 Playwright：常态 → 注入 → 等某级告警（读事件库）→ 暂停 → 等所选操作 → 按分支表换剧本 → 恢复时钟 → … → 结束。
- 控制台只有“开始演示”（和“重置”）。
- 等“操作已下发”的信号：读矿井的 `action_log`（见第 5 节）。
- 前置：先查清故事线在黄色阶段卡住 15 分钟以上的原因（2026-11-09 Docker 里观察到，未查）。

## 5. 黄色的处置步骤

- 黄色的“观察跟进”由 guard 提交只含 `monitor` 步骤的处置方案（`submit_treatment`）。矿井已能执行 `monitor`，记进 `action_log`，所以矿井侧有记录，导演也据此判断黄色已处置。
- 待确认：guard 的预检允许只含 monitor 步骤的方案。
- `add_followup`（登记跟踪计划）仍在事件库，与矿井动作分开。

## 6. 人设与动作分级

- 人设（`commander.patch.yml`）：智能体研判后给出**推荐的处置选项**，由操作员选择；下发前一律人工确认。操作员在选项卡片上的选择同时作为确认，不再弹第二次审批。
- 动作分级表（`rescue_contract/action_policy.py`）为每个动作新增 `on_timeout`：

| 取值 | 含义 |
|---|---|
| `approve` | 批准超时后自动放行 |
| `reject` | 超时后自动拒绝 |
| `escalate` | 只升级提醒，不执行（现状） |

- 分级（占位）：**黄色（monitor、观察跟进）`approve`；橙色（注氮、注浆等）和红色（撤人、封闭等）`escalate`**。真实运行里，影响现场或不可逆的动作不应在没人批准时自动执行。
- 超时处理由审批插件按表执行，不是模型；时间线里标明“超时自动处理”，复盘会显示。
- 现有的批准超时升级（`approval_escalated`、`approval_timeout` 告警）保持不变，`escalate` 类动作走这条路径。
- 需要改动：`persona`、`skills/fire-incident-management` 的分级决策表、依赖“智能体自己决定”的评测用例和故事线（`story.py`）、控制台。

## 9. 实现进度（2026-11-09）

已做（模拟矿井侧，`mcp/mine-data-sim`）：

- 导演 `director.py`，流程配置 `scenarios/demo/flow.yaml`（放子目录，免得被当成场景加载）。路由：`GET /sim/demo/director`、`POST /sim/demo/start`、`POST /sim/demo/choose`；`/sim/state` 带 `director`；控制台新增“演示导演”区块（开始、选项复选框、确认）。
- 推进方式：暂停即冻结时钟，导演先一次跳过 `jump_h`，再按 `step_h` 一步一步推，**每步等监听器心跳的矿井时间追上再读事件库**（心跳在检测和写告警之后才写），所以不会冲过等级。等级只从监听器告警“升为 黄色/橙色/红色”读，导演不判断。
- 分支按**累计选中个数**走，支持 `goto`（下一级）、`end`（跑 `run_h` 后结束）、`again`（效果有限，停在本级追加）。`apply_options: true` 时导演自己把所选操作施加到模拟矿井（过渡期，来源记 `demo-operator`）；智能体经 guard 下发后改为 false。
- 引擎新增 `set_params`（按当前时刻换一套过程参数）。
- 测试：`tests/test_director.py`（假监听器驱动）；Docker 里用真监听器、不带智能体跑通三条路径（总共约 1 分 20 秒）。

调参结论（s3-accelerating，用基线评测的预警判据扫描，**占位值，演示剧本，不是模型预测**）：

- 橙色选 1 项（只注氮）：约 36 矿井小时后升红；加一次漏风突增（系数 3）约 24 小时升红。
- 橙色选 2 项（含注浆）：注浆把温度压住，**预警一直停在橙色，不会升红也不会回落**，所以 2 项设计成“效果有限，要求追加”，不是一个终局分支。
- 橙色 3 项全做：不加额外效果时仍停在橙色；`k_ox` 乘 0.64 时预警在黄色区间停留约 50 小时（再小就掉到蓝色/无，再大又回橙色，是窄带）。分支因此带了 `scale: {k_ox: 0.64}`。**这个窄带依赖场景参数，改 s3 要重扫。**
- 预警等级里有“蓝色”（关注），在黄色之前出现；导演只认黄、橙、红。

没做、下一步（第 2 项已做，见下）：

2. 动作分级表加 `on_timeout`，审批插件执行（黄色 `approve`，橙、红 `escalate`）；人设与分级决策表、评测用例、故事线随之改。
3. 暂停时读数的轻微浮动（可选）。

### 9.1 `on_timeout` 与加密监测（2026-11-09，已做）

- 动作分级表加 `on_timeout`（approve / reject / escalate，缺省 escalate）；审批插件到批准超时（真实时间）按表自动处理，时间线记 `auto: timeout`；监听器对自动处理的确认不重复升级（超过两倍超时仍未决才兜底）。真实 DSH 上验证，见验证清单 #37（含“卡片残留”的问题与处理）。
- 黄色的处置落成 guard 工具 `start_monitoring(record_id)`（C 级，确认人值班长，5 分钟，升级对象总工程师，`on_timeout: approve`）：引用 `run_fire_assessment` 的预警等级记录，经 rescue-mine `submit_treatment`（monitor 步骤）执行，矿井有记录。**唯一设为 approve 的动作**；橙、红的所有动作保持 escalate（测试固定）。
- 技能 `fire-incident-management`、主预设、用例 `v3-yellow-observe`、故事线黄色检查随之改为“提交加密监测并经确认下发”。
- 还没做：选项卡片接入 DSH、导演与 guard 下发的衔接（`apply_options: false`）、人设里“研判后给出推荐、操作员点选”。
