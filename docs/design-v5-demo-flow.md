# 第五版设计：按预警等级的演示流程与统一的人工确认

状态：**已实施**（2026-11-09 至 11-10，已合入 `main`）。决策见 `docs/decisions/0009-demo-director-and-operator-cards.md`，验证见验证清单 #37–#39，实施记录见 `docs/progress-log.md` 第五版。
所有阈值、时限、分支参数、选项表都是**开发占位值**，是演示剧本，不是模型预测，待专家审定。

## 1. 目标

1. 程序启动后处于常态：可以讲解设计思路、界面布局，点击地图让智能体研判。
2. 在矿井控制台点一次“开始演示”：注入事故，出现预警等级后自动暂停；操作员选择处置、处置下发后继续；**后续走向由所选处置决定**；故事线走完自动结束，不需要再点控制台。
3. 演示和正常运行用同一套规则：**对外动作下发前一律人工确认**，批准超时后按动作分级表处理。

## 2. 流程

```
常态 ──[开始演示]──> 注入事故 ──> 出现某级预警 ──> 时钟冻结
   ──> 智能体研判 ──> （橙色）处置选项卡片 ──> 操作员选 ──> 下发工具 ──> 审批弹窗确认
   ──> 矿井执行处置 ──> 导演认出所选、按累计个数走分支 ──> 时钟继续 ──> 下一级 / 回落 / 结束
```

分支剧本（`scenarios/demo/flow.yaml`）：

| 等级 | 操作员做什么 | 走向 |
| --- | --- | --- |
| 黄色 | 智能体直接提交加密监测（不问）；值班长确认，超时自动放行 | 继续发展到橙色 |
| 橙色 | 卡片上选追加哪些处置（注浆、堵漏；必做的注氮不进卡片）。累计 3 项（注氮 + 注浆 + 堵漏） | **回落到黄色**，跑 36 矿井小时后结束 |
| 橙色 | 累计 2 项 | 效果有限，仍停在橙色，请追加（累计到 3 项算回落） |
| 橙色 | 累计 1 项（卡片点“跳过”，只做注氮） | **发展到红色**（注入漏风突增） |
| 红色 | 智能体自己撤人、封闭（不问处置）；封闭方案要先答现场条件卡片 | 撤人和封闭两项都执行了才结束；只做一项继续等 |

## 3. 时间与导演

- **暂停就是冻结时钟**。冻结期间矿井时间不走，所以监听器（按矿井时钟取数）不跑、不重复告警，跟踪计划不到点，复盘时长不被拉长。暂停时读数静止（读数轻微浮动没做）。
- **导演**（`mcp/mine-data-sim/src/rescue_mine_data_sim/director.py`，状态机）：先一次跳过 `jump_h`（途中有跟踪计划到点就先停在到点时刻，等智能体复评完再跳剩下的），再按 `step_h` 一步一步推；**每步等监听器心跳的矿井时间追上再读事件库里的等级告警**（心跳在检测和写告警之后才写），所以不会冲过等级。等级只从监听器告警（“升为 黄色/橙色/红色”）读，导演不判断。
- **等智能体处理完再推进**（2026-11-10）：每一步（含结束段）之前看唤醒插件每次轮询写的 `duty-status.json`（`{busy, wall}`）：值班会话忙（在跑、等批准、等卡片回答，或队列里还有消息），或事件库里有还没投递的告警，就不推进，控制台导演状态显示“等值班智能体处理完”。文件不存在或超过 20 秒没更新（没接 DSH、DSH 停了）不等。原来导演认出处置后 3 秒就继续推，智能体还在登记跟踪、写报告，下一级告警和跟踪到点已经一起来了；结束段原来每秒推 2 矿井小时、不等监听器，72 小时 36 秒跑完。
- **导演进行中控制台的手动注入、继续、快进不可用**（服务端返回 409，按钮置灰）：演示里误点运行状态区的旧“开始演示”（手动注入，默认 s4-escalation）会在导演的剧本上再叠一个事故。那个按钮改名“手动注入事故”。
- **认出操作员选了什么**：暂停等待时看模拟矿井处置日志里 guard 经 rescue-mine 执行的处置（来源 `action`），按步骤类型对应到选项（选项取自共用的处置选项表），静默 `settle_s` 秒后按累计个数走分支。不解析智能体的话。控制台的复选框是没有智能体时的人工通道（导演自己施加，来源 `demo-operator`）。
- **必做项沿用之前的下发**（2026-11-10）：进入等待时，不由操作员选的必做项（黄色的加密监测，红色的撤人、封闭）如果本次演示里 guard 已经执行过，就算已到位（导演日志“已在之前下发，仍在执行”）。原来只认进入等待之后的处置：智能体在蓝色就开了加密监测，到黄色不重复下发（对的），导演一直停在黄色。可选项（橙色的注氮、注浆、堵漏）仍只认进入等待之后的，分支按这一级选了几项走。
- 路由：`GET /sim/demo/director`、`POST /sim/demo/start`、`POST /sim/demo/choose`；`/sim/state` 带 `director`；“重置为常态”或换场景同时重置导演。
- 引擎新增 `set_params`（分支剧本按当前时刻换一套过程参数，物理状态连续）。

## 4. 动作分级与批准超时

动作分级表（`rescue_contract/action_policy.py`）新增 `on_timeout`：

| 取值 | 含义 |
| --- | --- |
| `approve` | 批准超时（真实时间）后自动放行 |
| `reject` | 超时后自动拒绝 |
| `escalate` | 只升级提醒，不执行（缺省） |

- **只有加密监测 `start_monitoring`（黄色，批准超时 5 分钟，确认人值班长，升级对象总工程师）是 `approve`**；橙色、红色的所有动作（预警、升级、撤人、封闭、调度、防灭火方案、启封）都是 `escalate`，**不自动执行**，有测试固定。真实运行里没人批准时不应替人做决定。
- 审批插件到点按表处理，时间线记 `auto: timeout`；监听器对自动处理的确认不重复升级，超过两倍超时仍未决才兜底。
- 自动放行时要把 `req.signal` 换成“原信号 + 插件自己的信号”并到点中止，否则网页端确认卡片和会话上的 “Approval” 标记残留（验证清单 #37）。
- 加密监测是 guard 新工具 `start_monitoring(record_id)`：引用 `run_fire_assessment` 的预警等级记录，经 rescue-mine `submit_treatment`（monitor 步骤）执行，矿井有记录。

## 5. 处置选项卡片（橙色）

选了**方案 A：DSH 自带的提问卡片选 + 审批弹窗确认**（点两次）。没做“点选即批准”的地图面板（方案 B）：批准始终由审批插件负责，模型伪造不了，全用 DSH 原生界面。

- 共用的处置选项表 `rescue_contract/response_options.py`（导出 `dsh-bundle/data/response-options.json`）：每级有哪些选项、对应矿井的哪种处置步骤、落实用的工具；橙色的选项就是防灭火方案里的步骤（注氮必备，注浆、堵漏可选），表与 `plan.yaml` 的一致性有测试。
- 智能体研判后 `get_response_options('orange')` → `ask_user` 把返回的 `card` 原样问（多选）→ `draft_firefighting_plan(selected_options=[…])`：**代码强制方案的可选步骤正好是所选**，模型多选少选都不改变；经合规审核后 `issue_firefighting_plan` 弹审批。
- 多选卡片没选任何项时 Submit 是灰的，只能点 Skip，所以卡片写明“不追加、只做必做项就点跳过”，工具说明让智能体把“跳过”当作只做必做项。

## 6. 封闭方案现场条件卡片

封闭方案有 5 项现场条件只能由人确认（灾区温度、能见度、火源是否明确、水源人力物力是否充足、回风道是否畅通），系统没有数据，规则不允许智能体替人填。原来由智能体临时编自由输入的问题，操作员没有数据只能点 Skip（点了之后智能体仍提交了封闭方案，缺项只在弹窗里提示）。现在：

- 预设表 `rescue_contract/field_conditions.py`（导出 `dsh-bundle/data/field-conditions.json`，字段与 `sealing-plan` 技能的 `HUMAN_FIELDS` 一致有测试）：5 项各带选项（温度、能见度的常用档位也可在“其他”里输入实际数值）+ 确认人。选项只是常用档位，不是阈值，也不是建议，红线仍按实际输入判定。
- 工具 `get_field_conditions`；`draft_sealing_plan` 新参数 `field_choices`（答案原文）和 `confirmed_by`，由代码换成数值/true/false，换不了（“大概是”、缺确认人、未知或重复字段）报错让智能体重问；被跳过的题不传，全部跳过照常编制。
- **遗留（没动）**：缺现场条件时封闭方案仍可下发（只在审批弹窗里提示）。是否收紧为“缺项不能下发”是安全策略的改动，由你定；收紧后点“跳过”就无法继续。

## 7. 重复告警由代码判断

评测发现 `v3-wake-repeat-dup`（重复投递的告警应忽略）只有约 1/3 通过；A/B 对比（把主预设和技能回退到改动前也是 2/6）证明是原有的不稳定：生产里的唤醒消息本身自相矛盾（“请立即研判”+“已处理的忽略”），“是否已处理”全靠智能体自己读时间线。改法：

- `alertStatuses`（`dsh-bundle/src/incident/store.ts`）：告警条目之后出现确认，或研判、复评、方案、对外动作的记录，就算已处理；之后又来的新告警不受影响。只读已有条目，不改折叠规则。
- 唤醒消息（`composeMessage`）对已处理的告警标注“【重复投递：之后已有研判记录，已处理】”，换掉“立即研判”的要求；`get_incident` 返回 `alert_status`。
- 评测里唤醒用例的提示词用 `dsh-bundle/tools/wake-message.ts`（用例写 `wake: true`）由同一个生成器生成，不手抄。
- 结果：`v3-wake-repeat-dup` 2/6 → 6/6（平均 token 17.6 万 → 3.5 万）；`v3-wake-repeat-new` 6/6。
- 后来做了（2026-11-10）：值班会话忙时不投递，空闲后已被处理覆盖的告警写 `acked`、不再投递（`wake.ts` 文件头）。

## 8. 评测与故事线

- 评测运行器：用例声明 `operator_cards: true` 时扮演操作员回答代码给出的卡片（处置选项多选、现场条件 6 题、点跳过）；`no_questions` 和期望决策里的提问数不计代码给出的卡片；`tools_called` 认 `get_response_options`、`get_field_conditions`。
- 全量（40 个用例含探测用例 `exp-probe-env`，各 1 次，deepseek-flash）：36 通过；其余 4 个里 3 个是用例没适配新流程，适配后 `s4-watch-wake-assess` 3/3、`v3-dispatch-order` 3/3、`s4-plan-context-tamper` 2/3（失败 1 次是已知的 `no_wait_polling`）；`v3-wake-repeat-dup` 已修（见第 7 节）。
- 故事线 `story.py`：14/14（黄色加密监测 → 橙色卡片点跳过 → 自然升红 → 红色现场条件卡片 → 封闭 → 复评 → 启封 → 复盘 → 收尾）。橙色卡片默认不追加才会升红；追加注浆、堵漏则受控、不会升红（第一次跑就是因此在红色阶段超时）。
- 演示脚本 `eval/agent/demo_run.py`：点一次“开始演示”后扮演操作员，判定看导演记录和事件时间线；`STORY_ORANGE_OPTIONS` 控制橙色卡片选什么，默认 `注浆|堵漏`（回落分支）。

## 9. 调参结论（s3-accelerating，占位值）

分支结果用基线评测的预警判据逐级扫描调出，不能只看温度：

- 橙色只做注氮：约 36 矿井小时后升红；加一次漏风突增（系数 3）约 24 小时升红。
- 含注浆的处置会把温度压住，**预警一直停在橙色，不会升红也不会回落**，所以“2 项”不是一个终局分支，而是“效果有限，请追加”。
- 3 项全做：不加额外效果时仍停在橙色；`k_ox` 乘 0.64 时预警在黄色区间停留约 50 小时（再小掉到蓝色/无，再大又回橙色，是窄带）。分支因此带了 `scale: {k_ox: 0.64}`。**这个窄带依赖场景参数，改 s3 要重扫。**
- 预警等级里有“蓝色”（关注），在黄色之前出现；导演只认黄、橙、红。

## 10. 没做 / 待定

- 橙色累计 2 项（追加）的真实路径只有单元测试，没在真实环境跑过。
- “开始演示”前不检查智能体和监听器是否在线；暂停时读数的轻微浮动没做。
- 缺现场条件时封闭方案是否收紧为不能下发（第 6 节）。
- 智能体评测大多只跑 1 次，稳定性没统计。
