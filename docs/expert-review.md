# 待专家审定清单

阈值、判据、参数、选项表、流程规则目前都是**开发占位值**（CLAUDE.md 约定 6）。这里把要请通风、防灭火、救护专家审定的事项集中列出，便于评审时逐条过。
每条写：现在怎么做、参数在哪里、要专家回答什么。专家给出结论后，改对应文件的取值、把 `status: placeholder` 改为已审定并填 `reviewed_by`，再在本表标为“已审定”（见文末“审定后怎么落地”）。

2026-11-12 建立（24 项），同日整理补充为 46 项、重新编号：补上红线规则本身、规程条号、合规审核项、采集清单与测点角色、现场条件卡片、按等级的处置选项、流程规则、演示场景与剧本、评测期望和评审流程。

**“时机”列**：**演示前** = 演示中会直接看到、客户或专家可能当场追问，最好演示前至少过一遍；**接入前** = 换成真实矿井、真实数据前必须按本矿制度定，演示阶段可以先用占位值。

**建议评审顺序**：先请专家看一遍 `docs/architecture.md` 第 1、5 节（分层和一次指令的路径），知道“哪些由代码判、哪些由模型选、哪些由人确认”；再按 一（研判）→ 五（红线与条文）→ 二（处置）→ 三（封闭启封）→ 四（流程规则）的顺序过“演示前”的条目。

## 审定后怎么落地

1. 改对应文件的取值，文件头的 `status: placeholder` 改为 `reviewed`、填 `reviewed_by`（`skills/README.md`）；代码里的表（选项、卡片、动作分级）改后 `make schema`。
2. 改了判据要同时更新自检样例和测试：`make skills-check`、`make test`；红线规则另按 CLAUDE.md 约定 3 同步 `test_redlines.py` 和 `plan-compliance/SKILL.md`。
3. 重新生成评测期望（`eval/agent/gen_expected.py`）、跑 `make eval`，看各级首次到达时间和期望决策的变化；演示剧本的分支参数随之重调。
4. 提交说明写明哪些是专家审定值、审定人和日期；本表对应行标为“已审定”。
