# 第一部分：对接方案

## 1. 背景和目标

煤矿应急救援智能体（一期场景：采空区煤自燃）在预警等级达到橙色及以上时，自动计算受威胁人员和每组人员的撤离路线（避灾路线），显示在通风图上，供指挥人员参考。目前的撤离路线由我方的简化算法给出：在通风网络上找到最近的地面出口或避难硐室，**完全避开受污染巷道**，长度按巷道长度计。

提供方的路径规划服务（`mine-route-api`）考虑了巷道断面、风速、烟雾浓度、坡度和烟中通行时间，能给出“暂时脱险时间”等我方没有的指标。本方案的目标：

1. **以该服务的路线为准**：服务可用时，界面（通风图、研判报告）**只显示服务给出的路线**，撤人通知里的路线也取服务的结果；**服务不可用时才改用我方路线**，并明确标出“本系统计算（外部服务不可用：原因）”（显示规则见第 3.1 节）；
2. 先用占位参数**快速打通**全流程（演示用模拟矿井），再随真实矿井数据到位逐步替换；
3. 两种路线照常都计算并存档，借比较结果改进我方算法；
4. 明确需要提供方和矿方各自提供什么。

因为服务的结果会直接显示给指挥人员并写进下发到井下的撤人通知，第 6 节里关于**空结果原因、可用性和结果含义**的问题需要优先答复。

**边界**：撤离路线只是辅助参考，不替代规程要求的避灾路线图和应急预案；撤人按预案立即执行，不等待计算结果。界面上始终写明这一点。

## 2. 分工

| 方 | 负责 |
| --- | --- |
| 提供方 | 部署并运行路径规划服务，保证可用性；提供稳定的接口地址、接口说明和版本；接口变更和停机维护提前通知；说明计算方法和适用范围；回答第 6 节的问题 |
| 我方 | 编写适配服务，把我方通风网络和现场状态转换成服务的输入，调用服务，校验结果并换回我方巷道编号；保存每次调用的输入和输出（复盘依据）；按第 3.1 节的规则显示和使用结果，服务不可用时用我方路线兜底 |
| 矿方 | 提供真实通风网络数据（第 7 节），用于替换占位参数 |

## 3. 调用方式

```
救援智能体（研判流程）
   │  ① 我方技能脚本：通风网络 + 受污染巷道 + 参数 → 服务输入（我方编号）
   ▼
我方适配服务 route_planner（只读，内网）
   │  ② 编号 ↔ 数组下标转换、输入校验、超时、逐个终点调用
   ▼
提供方服务  POST http://<地址>:8080/api/v1/routes      健康检查 GET /healthz
   │  ③ 返回候选路线（节点下标序列）
   ▼
我方适配服务 → 换回巷道编号 → 我方技能脚本与我方路线比较、选定显示哪一种 → 保存结果，显示，并用于撤人通知
```

- 调用方只有我方适配服务一个；智能体（大模型）不直接调用提供方服务，也不能自己构造输入调用。
- 调用时机：每次研判中，预警等级达到橙色及以上且有受威胁人员时，对每组受威胁人员调用一次（目前接口只支持单终点，暂时是每组人员 × 每个候选终点各调用一次）。研判周期按小时计，调用量很小。
- 每次调用设超时（暂定 5 秒）。服务不可用、超时或报错时，研判照常完成，该组改用我方路线，并标明原因。

### 3.1 显示规则（外部为主、我方兜底）

逐组人员判断（同一次研判里，可能有的组用服务路线、有的组用我方路线）：

| 服务的情况 | 显示和撤人通知用 | 界面上的标注 |
| --- | --- | --- |
| 正常返回路线，且路线通过我方校验（首尾正确、巷道连续、都在网络里） | 服务的路线 | “外部路径规划服务”，附当量距离、烟中时间、暂时脱险时间；穿过有烟巷道时写明 |
| 正常返回空结果（`routes: []`） | 服务的结果：**无可行路线，需人工研判**（不改用我方路线） | “外部路径规划服务：无可行路线”；服务给出原因后照写原因（第 6 节第 1 条） |
| 不可用：没有配置、连不上、超时、返回非 200、返回格式不对或路线没通过校验 | 我方路线 | “本系统计算（外部服务不可用：原因）”，用不同的线型和颜色 |

- 两种路线**都计算并存档**；界面只显示选定的一种，另一种在记录里可以查到（复盘和改进算法用），不在图上画；
- 撤人通知写明路线来源（外部服务或本系统）；路线穿过有烟巷道时写明烟中时间；
- 撤人通知是预案撤人的补充，不替代、不延迟预案撤人（不变）。

## 4. 输入数据怎么来（快速接入阶段）

模拟矿井和当前演示图纸都没有服务需要的大部分数据（见第 5 节）。快速接入阶段按下表生成输入，**所有占位值都会在结果里标明“试验性”**，并列入我方待专家审定清单。

| 服务字段 | 快速接入阶段的来源 | 性质 |
| --- | --- | --- |
| `nodes` `[x, y, z]`（米） | 我方网络没有坐标。按固定方法生成平面占位坐标（附录 A.2），使每条巷道的折线长度等于该巷道的实际长度；**z 一律取 0**（不引入编造的坡度） | 占位 |
| `edges[].height` / `width` | 统一取占位值（暂定 3 m × 4 m，与我方现有的缺省断面 12 m² 一致） | 占位 |
| `edges[].windSpeed` | 设计风量 ÷ 60 ÷ 断面；方向按我方约定（风流从巷道起点流向终点），所以为正值；没有设计风量的巷道用缺省风速 | 由设计风量估算 |
| `edges[].smokeConcentration` | 我方算出的“受污染巷道”（沿风流下风侧）取一个固定占位值，其余为 0 | 占位 |
| `start` | 受威胁人员所在巷道的中点（把该巷道拆成两段，中间加一个节点） | 由我方数据得出 |
| `target` | 地面出口和避难硐室，逐个调用 | 由我方数据得出 |
| `walkSpeed` | 占位值（与我方路线使用的步行速度相同） | 占位 |
| `maxSmokeTime` | 占位值，暂定 900 s（示例值），待专家按自救器额定防护时间确定 | 占位 |

采空区漏风通道不作为可通行巷道传入。

## 6. 需要提供方确认或支持的事项

按对接的重要程度排序。服务的路线改为默认显示并写进撤人通知后，第 1–6 条直接影响能否这样使用，请优先答复。

**必须确认（外部结果为主后，影响能否使用）**

1. **结果为空时给出原因**：如 `reason: "unreachable" | "smoke_time_exceeded"`。按第 3.1 节，服务返回空结果时界面显示“无可行路线，需人工研判”、不改用我方路线，所以两种情况必须能区分：前者“没路”，后者“有路但烟中时间超过上限”，对指挥的含义完全不同。后者能否同时返回超限的那条路线和它的烟中时间？
2. **路线的含义和适用范围**：服务给出的路线能否直接作为撤人路线下发到井下？路线允许穿过有烟巷道（只要烟中时间不超过 `maxSmokeTime`），这一规则的依据是什么？计算方法是否经过验证或用于过实际矿井？有哪些情况结果不可信（如风速、烟雾浓度超出某个范围）？
3. **可用性**：服务能否 7×24 运行；重启后是否自动恢复；有没有计划停机，停机前如何通知；出现故障时联系谁。
4. **响应时间**：典型和最长响应时间，与节点数、巷道数的关系；节点数、巷道数的上限。我方暂定超时 5 秒，超时即改用我方路线。
5. **错误的含义**：哪些错误是输入问题（400，我方要修正输入）、哪些是服务内部问题（5xx，可以重试）；错误返回的格式是否固定（目前是 `{"error": "…"}`）。
6. **结果的确定性**：同一输入多次调用，结果是否总是相同（我方存档后复盘时要能重算）。

**希望支持（影响接入质量）**

7. **巷道可选的实际长度和高差**：如 `edges[].length`（米）、`edges[].rise`（终点相对起点的高差，米）。给出时优先于按坐标计算的结果。原因：通风网络通常是示意的，巷道是弯的，直线距离不等于巷道长度；没有可靠坐标时也能使用服务。
8. **多个终点**：如 `targets: [..]`，一次调用返回到最近（按服务的排序规则）终点的路线。这样不用逐个终点调用，排序也由服务统一给出。
9. **结果里带计算方法版本号**（如 `version`，系数表变化时变化），我方会存档，便于复盘时知道当时用的是哪一版方法。
10. **未知字段报错**（400），而不是静默忽略，避免字段名写错却得到看似正常的结果。
11. **鉴权**：至少支持一个固定令牌（如 `Authorization: Bearer <令牌>`），或在服务器上按 IP 白名单限制访问。

**需要说明（我方要据此决定怎么用、交给专家审定）**

12. 返回几条路线？按什么规则筛选？能否指定返回前 K 条？
13. 当量距离的计算公式和风速系数表（逆风、顺风、坡度如何折算）。
14. `smokeConcentration` 的单位和含义（体积分数？遮光度？），对通行速度或烟中时间的影响方式；“有烟”是否只按 >0 判断。（我方以后可能用火灾推演服务的结果作为这一输入。）
15. 巷道是否总是双向可通行；有没有办法标记不可通行的巷道（如已封闭、垮落），还是由我们不传入这些巷道。
16. 服务的日志在哪里；接口变更的通知方式。

# 第二部分：我方内部实现（附录，对外发送时可删去）

## 附录 A. 实现设计

### A.1 遵守的约定

- **数值只来自代码**（CLAUDE.md 约定 1）：占位输入由技能脚本生成，比较结论（一致/不一致、差多少）由脚本给出；智能体只引用记录。
- **技能脚本不访问网络**（`skills/README.md`）：脚本只负责“生成请求”和“比较结果”两个纯函数；网络调用在 MCP 服务里，由证据插件编排。
- **智能体不挂载 `route_planner`**：任何预设都不挂（`scripts/check_patches.py` 加检查）。否则智能体可以拿自己编的输入调用，得到不受记录约束的“路线”（验证清单 #34 的问题）。
- 参数放 `references/route_service.yaml`，`status: placeholder`，逐项加进 `docs/expert-review.md`。
- 不属于 rescue-mine 接口（`interface.py` 不变）：它是计算服务，不是矿井数据。

### A.2 占位坐标的生成方法

目标：平面上的折线长度等于巷道实际长度 `length_m`，z = 0，确定性（同一网络每次结果相同）。实现在 `route_request.py`。

1. 节点按编号排在单位圆上（不用 `spring_layout`：它要 numpy，技能脚本的依赖只有 pyyaml、networkx）；
2. 整体缩放，使每条巷道两端的直线距离 `d` 都不超过其长度 `L`；
3. **每条**巷道在中垂线上加一个中间节点 `<巷道编号>#mid`，偏移量 `h = sqrt((L/2)² − (d/2)²)`（`d = L` 时为 0），两段 `<巷道编号>#a`、`#b` 之和等于 `L`；
4. 人员所在巷道的中间节点就是起点（不另外拆分）；每条巷道都拆开还顺带消除了并行巷道（同一对节点之间多条巷道）在服务结果里分不清的问题；
5. 坐标保留到毫米，`-0.0` 换成 `0.0`（JSON 里 Python 写 `-0.0`、JS 写 `0`，记录哈希会对不上）；
6. 结果换回时去掉中间节点、分段合并成巷道（`_route.py`），路线按巷道编号表示，不含人员所在巷道本身（与我方路线一致）。

局限：图形本身没有意义（只保证长度）；z = 0 时服务的坡度折算不起作用，竖井也按平巷算（我方算法同样如此）。拿到真实坐标或提供方支持 `length`/`rise`（第 6 节第 7 条）后这一节作废。

| 结果比较脚本 | `skills/fire-assessment/scripts/route_compare.py` | 输入：`personnel` + 请求 + 服务结果。输出：每组的第二意见路线（巷道序列、当量距离、烟中时间、暂时脱险时间、终点）、与我方路线的比较（终点是否相同、巷道重合比例、我方“需人工研判”而服务给出路线等情况），全部由脚本计算 |
| 编排 | `dsh-bundle/src/fire-loop/assessment.ts` 在 `personnel` 之后加 `route_service` 步骤；证据插件新增 `collectRoutes(请求记录)`，调用 `route_planner` 并把原始输入输出存成证据记录 | 该步骤失败不中断研判（记 `failed`，报告写“第二意见不可用”） |
| 显示 | （R4 时）研判报告里“避灾路线第二意见”一节；地图另画一条蓝色细虚线“参考路线（外部服务，试验性）”，两者并列。**R8 起改为外部为主、我方兜底，见 A.7** | — |

实施时定下的细节：

- 研判流程的三步：`route_request`（结果记录）→ `route_service`（**证据**记录，`collect_kind: routes`，内容是每组的适配服务原始返回或错误，`parent_ids` 是请求记录）→ `route_compare`（结果记录）。没配置 route_planner（`RESCUE_MCP_ROUTE_PLANNER_URL` 为空）或 `personnel` 没有计算时整段跳过，不产生记录，报告里没有这一节（与第六版之前一样）；
- 某组调用失败（服务不可用、超时、输入被拒）记在证据的该组里，比较结果为 `service_unavailable`，报告写“第二意见不可用：原因”；脚本本身失败时研判照常完成，警告里写原因；
- 比较的情况（`route_compare.py` 的 `CASES`）：`same_route`、`same_target`、`different_target`、`ours_none_service_through_smoke`、`ours_none_service_clean`、`ours_route_service_none`、`both_none`、`service_unavailable`；另给巷道重合比例（交集 ÷ 并集）和长度差；
- 地图只认同一次研判的比较记录（`route_compare` 的输入 `personnel` 就是地图正在显示的那份 personnel 记录）。

### A.4 两种算法语义上的差别（比较时要注意）

- 我方：受污染巷道**一律不走**；不可达就“需人工研判”。
- 服务：允许穿过有烟巷道，只要烟中时间不超过 `maxSmokeTime`。

所以“我方需人工研判、服务给出穿烟路线”是预期中会出现的情况，比较结果要单独标出，不能显示成“服务找到了路”这样的结论；是否可以穿烟由人判断。

### A.5 测试

### A.7 外部为主、我方兜底（R8，2026-11-17）

用户决定：默认只显示外部服务的路线，外部服务不可用时才显示我方路线并标明；撤人通知里的路线同样按此取；服务正常返回空结果时照外部结果显示“无可行路线”（不改用我方路线）。

- **选择在技能脚本里做**：`route_compare.py`（1.1.0）每组多一个 `display`（字段与 `escape_route` 对齐：`reachable`、`target`、`target_name`、`nodes`、`roadways`、`length_m`、`note`，另有 `source`（`service`/`ours`）、`reason`（用我方路线的原因）；外部路线带 `escape_min`、`smoke_time_s`、`smoke_roadways`，我方路线带 `walk_min`、`walk_with_self_rescuer_min`）和报告整句 `text`；顶层多 `display_lines`、`display_counts`。原来的比较（`comparison`、`lines`）照旧存档，不再显示。
- **没有 route_compare 记录**（没配置服务、这一段研判失败）时，各处按我方路线显示，来源写“本系统计算”。
- **报告**：人员行只在 `route_from_compare` 为假时写我方路线（标“本系统计算”）；“避灾路线”一节列 `display_lines`（逐组标来源）。这一段失败时写“外部路径规划服务不可用：原因；避灾路线为上面的本系统计算”。
- **地图**：每组只画一条路线：外部服务的路线 `kind: route`（绿色流动虚线，标签“外部服务 · 约 N 米”），我方路线 `kind: route_local`（蓝色流动虚线，标签“本系统计算 · 约 N 分钟”）；原来的 `reference` 图元去掉。左栏每组写“路线：外部路径规划服务（试验性）”或“路线：本系统计算（原因）”。只认同一次研判的 route_compare 记录（与之前相同）。
- **撤人通知**（guard）：`validation.evacuation_routes` 按通知引用的 personnel 记录找同一次研判的 route_compare（`RecordStore.derived`：同一矿井时刻的结果记录里，`source.inputs.personnel` 是它的那份），取每组 `display` 的节点序列；通知正文写明去向和路线来源、穿烟的组“烟中通行约 N 秒，须佩戴自救器”、没有路线的人，依据里加 route_compare 记录编号；确认弹窗的“撤往”同样写来源。智能体的调用方式不变（`record_id` 仍照抄 `record_ids.personnel`）。
- **火灾推演**：`fire_sim_compare` 有 route_compare 时按每组显示的路线核对危险巷道（见第七版 A.8）。
- 测试：`route_compare` 自检样例重新生成（含 `display`）；`test_validation_records.py::test_evacuation_uses_routes_shown_by_route_compare`；一致性测试 `test_ts_flow_route_second_opinion` 加报告和撤人通知的检查；`map-evacuation.test.ts` 的“外部为主、我方兜底”一组。
