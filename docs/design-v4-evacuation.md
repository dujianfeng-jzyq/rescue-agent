# 第四版设计：地图上的撤人路线与受威胁人员

状态：**已实施**（E1–E5，2026-11-09，验证清单 #36；`docs/design-v4-map.md` 的 P3 余下部分）。第 10 节“需要你定的问题”是设计时的待定项，实施时按各条的建议做了（示意折线、先摆再核对、占位时效 2 小时变灰 / 6 小时清掉、只显示人数）。

## 1. 目标和边界

在通风图上自动显示：

- **受威胁范围**：有害气体沿风流蔓延到哪些巷道、多久到（污染巷道，按到达时间着色）；
- **受威胁人员**：哪些巷道里有多少人（人数，不画个人）；
- **撤人路线**：每一组人到最近的井口或避难硐室怎么走、多长、走多久；走不通的组明确标出“需人工研判”。

边界（和第四版其余部分一致）：

1. **只显示，不计算，不由智能体画。** 路线、人数、到达时间都由 `fire-assessment/personnel` 技能脚本算好、存成记录；地图只是把记录画出来。评测里智能体曾自己写出“主要避灾撤人通道”（验证清单 #34），所以智能体**不能**往图上画路线或写路线断言，`map_view` 不提供这个能力。
2. **不替代规程要求的避灾路线图。** 界面上固定写“按设计风量估算，仅供参考；撤人按预案立即执行，不等待本结果”（记录里已有这句 `method` 和 `note`，原样显示）。
3. **宁可不画，也不画错。** 图纸位置对不上、记录过期、路线走不通，都如实标出来，不补、不猜。

## 2. 现状：算法和数据已经有了

`skills/fire-assessment/scripts/personnel.py`（由第一版 ventnet 迁移，参数在 `references/personnel.yaml`，占位值）：

- `downstream`：沿风流从源头巷道找下风侧全部巷道和**到达时间**；
- `threatened`：按巷道分组统计受威胁人员，**人数、合计由脚本给出**（约定 1）；
- `escape_route`：从某巷道出发到**地面出口或避难硐室**的最短路线，**避开受污染巷道**，优先走进风巷道；给出长度、步行时间、佩戴自救器的步行时间；避开之后无路可走时给 `reachable: false` 和“需人工研判”。

预警等级达到橙色（`assessment.yaml` 的 `personnel_level_at_least`，占位值）时，`run_fire_assessment` 会自动算并存成记录。一份真实结果（s4 红色阶段）长这样：

```
source_roadway: R-1201-FACE   total_threatened: 11 / total_underground: 22
contaminated_roadways: [{R-1201-FACE, 0 分钟}, {R-1201-RET, 1.6}, {R-RET-MAIN, 13.6}, {R-RET-SHAFT, 16.3}]
threatened[0]: R-1201-FACE 9 人（C001…C009），arrival 0
    escape_route: nodes [N3, N2, N8] roadways [R-1201-IN, R-REFUGE]
                  target N8 “1201避难硐室”  length 1960 m  walk 32.7 min  自救器 46.7 min
threatened[1]: R-1201-RET 2 人，arrival 1.6
    escape_route: reachable=false  “避开受污染巷道后无可达出口或避难硐室，需人工研判”
```

所以**不需要新算法，也不需要新的矿井接口**：路线用的是 `get_network`（节点、巷道），人员用的是 `get_personnel`（按巷道的人数），这两个已经是 rescue-mine 的接口。

## 3. 真正的难题：图纸和矿井网络对不上

- 模拟矿井的网络是个玩具：10 个节点、11 条巷道，长度 50–1800 米，名字是“主井”“1201运输巷”“总回风巷”等。
- 图纸（采一区通风立体示意图）是真实巷道：44 个有名称的位置，**没有拓扑**（巷道是双线条带，不知道哪条接哪条），也没有和网络节点的对应。
- 路线是**一串巷道**，要画成折线，每条巷道需要一段几何。名称标注只给出一个点（标注位置），不是线。

### 方案比较

| | 做法 | 优点 | 缺点 |
|---|---|---|---|
| A | 路线按各巷道**名称锚点**依次连成折线 | 不用额外数据 | 折线会穿过不相干的巷道，看着像是走在没路的地方，误导；而且路线两端的连接点是猜的 |
| B | 从图纸**自动提取**巷道中心线、自动建拓扑 | 换图不用人工 | 图纸是示意图（双线、斜轴测、有断开和重叠），自动建拓扑做不准；做不准比不做更糟 |
| **C（推荐）** | 映射表里给每个**节点**一个图上位置，每条巷道可加几个**途经点**，巷道折线 = 起点节点 → 途经点 → 终点节点 | 连通性由构造保证（相邻巷道共用节点）；工作量与网络规模成正比（模拟矿井 10 个点）；人工把关，错了能看出来 | 每换一张图/一个矿要人工做一遍映射；图上的折线是“示意”，不是巷道的真实形状 |
| D | C，再加“拾点工具”（在网页上点几下，输出坐标）和一致性检查脚本 | C 的人工成本降到几分钟，且能自动查出缺漏 | 多写一点工具 |

**推荐 D（C + 工具）。** 和已有的地图包做法一致：提取配置 `extract.json`、映射表 `mine_map.yaml` 都是“对着具体图人工量一次”的数据，跟着地图包走、不进仓库。

## 4. 数据模型：扩展 `mine_map.yaml`

```yaml
status: placeholder          # 示意映射；人工核对并写上 reviewed_by 后才去掉“示意”标记
reviewed_by: null
nodes:                       # 矿井网络的节点 → 图上的位置（地图坐标）
  N0: {at: [512.3, 780.1], label: 主井口}
  N2: {at: [1010.0, 120.5]}
  N8: {at: [1060.2, 96.0]}   # 避难硐室
roadways:
  R-1201-IN:                 # 巷道 = 起点节点 → 途经点 → 终点节点（折线）
    name: 211016运输巷        # 已有的“名称锚点”，用于点选定位、标记
    via: [[1040.0, 60.0]]    # 可省；弯曲的巷道加几个点
  R-REFUGE: {}               # 没有途经点就是直线
```

规则：

1. **每条巷道的起止点取自 `get_network` 的 `from_node` / `to_node`**，位置取 `nodes`，所以相邻巷道在共用节点处必然连上；没有人能画出一条“断开的路线”。
2. **缺映射就不画。** 路线里任何一条巷道缺映射，整条路线不画折线，只在左栏列出文字（“该路线有 N 段在图上没有映射，未画出”）；污染巷道缺映射同理，单条不画、其余照画。
3. **一致性检查脚本** `scripts/map/check_mine_map.py`（要写）：读 `get_network`（或模拟矿井的网络）和映射表，查：节点是否都有位置、位置是否在图的范围内、巷道端点是否存在、孤立节点、折线总长与网络里的 `length_m` 的比例是否离谱（只警告，不拦）。**换图或换矿必须过这个检查。**
4. **拾点工具**（要写）：网页上加一个“量取模式”（开发开关），点几下就输出坐标，粘进映射表。没有它，要人工从 JSON 里读坐标，几乎不可能。

### 一个必须说清的不一致

模拟矿井的路线长度是 1960 米，图上画出来的折线长度和它**不成比例**（图是示意图，网络是模拟的）。所以：

- 界面上显示的长度、步行时间**一律用记录里的值**，不用图上量；
- 图上折线只表示“走哪几段、什么方向”，不表示距离；
- 在图例里写明“折线为示意，距离以文字为准”。

## 5. 数据流

```
fire-assessment/personnel 记录（RS-…，run_fire_assessment 自动生成，等级 ≥ 橙色）
        │  Node 侧读记录目录：取该事件工作面“最近一份 computed=true 的 personnel 记录”
        ▼
state.evacuation（src/map/state.ts 新增）：原样带出记录里的污染巷道、受威胁分组、路线、合计、method，
        │  再用映射表把“巷道 ID”换成折线、把“节点 ID”换成位置；缺映射的单独列出
        ▼
autopilot（src/map/autopilot.ts 扩展）：算出要画的图元，与当前图元对账（和现有 auto: 标记同一套机制）
        ▼
指令中心（hub）新增图元：line（折线）、人数标记   ──SSE──▶  浏览器：Three.js 画线、左栏列出
```

- **用哪份记录**：该事件工作面最近一份 `source.script == personnel` 的结果记录。`computed: false`（等级没到、没要求）时不画，左栏写 `note`。
- **时效**：记录的 `as_of` 比当前矿井时间早超过阈值（占位 2 小时，与 guard 的“记录时效”一致）时，图元变灰并标“已过期 N 小时”，不删；超过更长阈值才清掉。
- **更新**：每次新的研判生成新记录，自动换；事件关闭、等级回落到记录 `computed: false`，自动清掉。
- 智能体**不参与**这条链路，`map_view` 不变；智能体可以 `focus` 到某条路线的起点，在回答里照抄记录里的文字。

### 图元（client）

| 图元 | 画法 | 数据 |
|---|---|---|
| 污染巷道 | 沿巷道折线加粗描红，按到达时间着色（越早越红，在当前全部污染巷道里整批算相对位置），入口一端（风流上游）往里一点写“约 N 分钟到达”：N 是烟气到这条巷道入口的时间，不是到整条巷道或末端的时间 | `contaminated_roadways[].arrival_min`（记录原值） |
| 受威胁人员 | 巷道中点一个人形标记，数字是该组人数；点击定位 | `threatened[].count`（记录原值，不自己数） |
| 撤人路线 | 绿色虚线沿折线流动到终点；终点图标（出口/避难硐室）；路线按长度的中点写“约 N 分钟”（正常步行） | `escape_route.walk_min`、`target_name`（记录原值） |
| 走不通 | 该组标记变灰，旁边写“无可达路线，需人工研判” | `escape_route.reachable == false` + `note` |

## 6. 界面：左栏新增“受威胁人员与撤离”

```
┌ 受威胁人员与撤离 ──────────────┐
│ 受威胁 11 人（井下共 22 人）      │   ← total_threatened / total_underground
│ 记录：RS-…（矿井时间 11-04 20:00）│   ← 点击打开记录
│ ▌1201工作面          9 人        │   ← 点击定位到该组
│    → 1201避难硐室  1960 m  约 33 分钟（自救器约 47 分钟）│
│ ▌1201回风巷          2 人        │
│    ✕ 无可达路线，需人工研判       │
│ 按设计风量估算，仅供参考；        │
│ 撤人按预案立即执行，不等待本结果。 │   ← 记录里的 method / note 原文
└────────────────────────────────┘
```

所有数字、名称都是记录里的原值，不在前端或 Node 侧加减、取整、改写（约定 1）。

## 7. 安全与失败模式

| 风险 | 处理 |
|---|---|
| 映射错了：图上的折线不是那条巷道 | 映射表人工做、必须过检查脚本；`status: placeholder` 时图上和左栏都标“示意映射”；换图/换矿重做并写 `reviewed_by`；缺映射不画 |
| 记录过期 | 变灰、标“已过期 N 小时”，不继续当现状显示 |
| 路线走不通 | 不画线，明确写“需人工研判”；不由前端另找路线 |
| 污染范围是估算 | 原样显示 `method`（“设计风量估算，未做风量解算，仅供参考”）；风量解算（Hardy Cross）是已知待办，不在这里做 |
| 智能体在回答里编路线 | 人设已要求数值只来自工具；评测增加一个用例检查回答里的路线是否出自记录 |
| 图上折线长度和网络长度不成比例 | 文字显示记录里的长度，图例说明“折线为示意” |
| 真实矿井的网络节点没有位置 | 映射表对真实矿井同样要做；没做完整就只画有映射的部分并如实列出缺的 |

## 8. 实施步骤

| 步 | 内容 | 验收 |
|---|---|---|
| E1 | 映射表扩展（`nodes`、`via`）、读取与校验（`mapping.ts`）；一致性检查脚本；量取模式 | 单元测试；检查脚本能查出缺节点、端点不存在、位置出界 |
| E2 | `state.evacuation`：读记录、选记录、时效、缺映射的处理 | 单元测试用 `skills/fire-assessment/tests/cases/personnel/` 的样例（s4 红色阶段）：9 人一组有路线、2 人一组走不通 |
| E3 | hub 增加折线和人数图元，autopilot 对账；客户端画污染巷道、路线（流动虚线）、人数标记 | 注入 s4 到红色后，图上自动出现；事件关闭后清掉；页面截图 |
| E4 | 左栏“受威胁人员与撤离”区块，点击定位 | 数字与记录逐项一致（测试比对） |
| E5 | 内部演示的映射表（10 个节点）、文档、验证清单 | 演示环境里整条故事线走通 |

估算：E1–E2 约一天，E3–E4 约一天，E5 半天。**不需要跑模型评测**（智能体不参与），只需要页面验证。

## 9. 不做的事

- 风量解算（Hardy Cross）：已有待办，换算法会改变到达时间；
- 智能体画路线或写路线断言；
- 从图纸自动提取巷道拓扑；
- 实时人员轨迹、个人定位（只按巷道显示人数）；
- 修改 `personnel` 技能的算法或参数（占位值待专家审定，与本方案无关）。

## 10. 需要你定的问题

1. **接受“示意折线”吗？** 图上的路线是节点之间的折线，不是巷道的真实形状，距离以文字为准。这是 C 方案的代价；想要真实形状只能手工描每条巷道。我的建议：接受，并在图例里写明。
2. **内部演示的映射谁来做？** 模拟矿井的 10 个节点要对到这张图上。我可以先按图上的位置摆出一版（标“示意映射”），你核对；或者你给我指定每个节点放在哪个名称附近。我的建议：我先摆，你核对。
3. **现场演示（客户的图）**：映射表要等客户的图和网络数据，并重新做一遍。要不要现在就向客户提需求：矿井网络（节点、巷道、名称）要和图纸上的名称一致，避难硐室和出口位置要标明？我的建议：要，越早越好，否则这一块现场演示做不出来。
4. **时效阈值**：记录过期多久变灰、多久清掉？占位 2 小时变灰、6 小时清掉，待专家审定。
5. **图元范围**：是否先只画“撤人路线 + 污染巷道 + 人数”，受威胁人员的人员编号（C001…）不显示？我的建议：不显示编号，只显示人数。
