# 演示知识库迁移方案（RAGFlow API）

> **已执行（2026-11-02），仅作记录**：演示用的三个 dataset 已建好，id 在 `.env`；条文索引由 `scripts/kb/` 离线生成（见 `docs/progress-log.md` 第二版 P2）。需要为新环境重建演示知识库时才按本文执行。

本文档给执行迁移的智能体使用：从现有 3 个知识库中挑选文档，通过 RAGFlow HTTP API 迁移到 3 个新建的演示知识库。
新知识库只服务于本项目 `kb` 服务的三个工具，所以文档少而准，比多而杂更好。

- 编写日期：2026-11-02；文档 id、切片数取自当天的 RAGFlow。
- 背景：现有法规库 113 个文档里混有大量与煤矿无关的内容（消防装备、防汛地震预案、安全标志等），
  检索“火区启封条件”时排在前面的全是 GB 2894 安全标志表。

## 0. 执行约束（必须遵守）

1. **只新建、只读旧库。** 不删除、不修改、不重新解析任何已有知识库和文档（包括下文列出的源库，以及“瓦斯”“通风”“粉尘”“测控-*”等无关库）。
2. **密钥只从仓库根目录的 `.env` 读取**：`RAGFLOW_BASE_URL`、`RAGFLOW_API_KEY`。不要把密钥写进日志、文件或报告。
   `.env` 里值后面可能跟 `  # 注释`，读取时去掉。
3. **RAGFlow 会偶发直接断开连接**（空响应，curl 报 `Empty reply from server`）。每个请求都要重试（建议 6 次、间隔 1–2 秒）。
   上传不是幂等的：上传失败重试前，先按文件名列出目标库文档，已存在就不要再传。
4. **整个过程可以重复执行**：同名知识库已存在就复用（不要建第二个），同名文档已存在就跳过。
   名称一律**完全相等**才算同名，不能用前缀或包含匹配：新库名“应急救援-法规-演示”以源库名“应急救援-法规”开头，
   匹配错了会把文档传进源库。复用前再核对一次 dataset id 不是第 3 节列出的三个源库 id。
5. 完成后按第 6 节给出报告；不要改 `.env`，也不要重启服务，由人确认后再做。

## 1. 三个新知识库

| 键 | 名称 | 对应 `.env` 变量 | kb 工具 | 切片方法 |
|---|---|---|---|---|
| `regulations` | 应急救援-法规-演示 | `KB_DATASETS_REGULATIONS` | `search_regulations`、`get_article` | 库默认 `laws`；技术标准逐个改 `naive`（见第 3 节“切片”列） |

| `cases` | 应急救援-案例-演示 | `KB_DATASETS_CASES` | `search_cases` | `naive` |

公共设置：

- **嵌入模型与现有库一致**：`qwen3-05b-embedding-2@baidu-remote-models@OpenAI-API-Compatible`
  （现有库的 `embedding_model_name`；执行前用 `GET /api/v1/datasets` 再确认一次）。
- `language`：`Chinese`；`permission`：`team`（与现有库一致）。
- `naive` 的 `parser_config`：`{"chunk_token_num": 512, "delimiter": "\n", "layout_recognize": "DeepDOC"}`。
- 不开 RAPTOR、GraphRAG、自动关键词、自动问题（保持默认关闭）。

为什么法规库用 `laws`：kb 从切片内容里用正则 `第[0-9一二三四五六七八九十百零]+条` 取条号，
按条切分后每个切片以“第X条”开头，条号准确、Agent 能整条照抄。技术标准（KA/T、AQ、GB、MT/T）按 5.2.1 这种编号分条，
`laws` 切不好，改用 `naive`；它们没有“第X条”，引用时只有文档名和原文，这可以接受。

## 2. API 速查

所有请求带 `Authorization: Bearer $RAGFLOW_API_KEY`。返回体 `{"code": 0, "data": ...}`，`code != 0` 为失败，看 `message`。

| 操作 | 请求 |
|---|---|
| 列知识库 | `GET /api/v1/datasets?page_size=50`（可加 `&name=<名称>`） |
| 建知识库 | `POST /api/v1/datasets`，JSON：`{"name", "embedding_model", "chunk_method", "language", "permission", "parser_config"}` |
| 列文档 | `GET /api/v1/datasets/{dataset_id}/documents?page=1&page_size=100`（`page_size` 最大 100；可加 `&name=<文件名>` 或 `&id=<文档id>`） |
| 下载原文件 | `GET /api/v1/datasets/{dataset_id}/documents/{document_id}`，返回文件字节（响应头里的文件名是乱码，**不要用**，用第 3 节的目标文件名） |
| 上传 | `POST /api/v1/datasets/{dataset_id}/documents`，`multipart/form-data`，字段名 `file`，**multipart 里的文件名就是文档名**，用第 3 节的目标文件名 |
| 改文档 | `PUT /api/v1/datasets/{dataset_id}/documents/{document_id}`，JSON：`{"chunk_method": "naive", "parser_config": {...}}` 或 `{"meta_fields": {...}}` |
| 开始解析 | `POST /api/v1/datasets/{dataset_id}/chunks`，JSON：`{"document_ids": [...]}` |
| 看解析状态 | 列文档，看每个文档的 `run`（`UNSTART`/`RUNNING`/`DONE`/`FAIL`/`CANCEL`）、`progress`、`progress_msg`、`chunk_count` |
| 看切片 | `GET /api/v1/datasets/{dataset_id}/documents/{document_id}/chunks?page_size=30&keywords=<词>` |
| 检索 | `POST /api/v1/retrieval`，JSON：`{"question", "dataset_ids": [...], "page_size", "similarity_threshold": 0.2, "keyword": true}` |

建库时如果 `embedding_model` 被拒（各版本写法不同），去掉该字段重试（租户默认嵌入模型就是同一个），
建好后 `GET` 一次，核对 `embedding_model_name` 与上面一致；不一致就停下报告，不要继续。

## 4. 步骤

1. **准备**：读 `.env`；`GET /api/v1/datasets` 确认 3 个源库存在、嵌入模型名称与第 1 节一致。
   按第 3 节逐个 `GET .../documents?id=<源文档id>` 确认源文档存在；不存在的记入报告并跳过，不要换成别的文档。
2. **建库**：按第 1 节建 3 个知识库（已存在同名库则复用），记下 3 个 dataset id。
3. **下载**：把源文件下载到临时目录（如 `var/kb-migration/<库键>/<目标文件名>`；`var/` 不进 git），
   校验文件头：pdf 以 `%PDF-` 开头，docx 以 `PK` 开头；大小与源文档 `size` 一致。
4. **上传**：按目标文件名上传。上传后在返回的文档对象里核对 `name`。
5. **元数据（可选但建议）**：把源文档的 `meta_fields` 原样写到新文档（`PUT ... {"meta_fields": ...}`），
   再加一项 `"migrated_from": "<源库id>/<源文档id>"`，方便以后追溯版本和效力状态。
6. **切片方法**：法规库里第 3.1 节“切片”列为 `naive` 的文档，逐个 `PUT` 成 `naive`（带第 1 节的 `parser_config`）。
7. **解析**：每个库一次 `POST .../chunks` 提交全部文档；每 15 秒列一次文档看 `run`，直到全部 `DONE` 或 `FAIL`。
   单个文档 30 分钟没结束算超时。`FAIL` 的看 `progress_msg`，可以重新提交一次；仍失败就记入报告。
8. **核对**：按第 5 节做检查。

## 6. 报告格式

执行完给出：

1. 3 个新知识库的名称和 dataset id，以及可直接粘贴进 `.env` 的三行：
   ```
   KB_DATASETS_REGULATIONS=<id>
   KB_DATASETS_PLANS=<id>
   KB_DATASETS_CASES=<id>
   ```
2. 每个文档：目标文件名、新文档 id、`run`、`chunk_count`、原切片数、切片方法；失败或跳过的写原因。
3. 第 5 节 A、B、C 每项的结果（通过/不通过，不通过的贴返回内容摘要）。
4. 执行中遇到的 RAGFlow 错误（断开、超时、`code != 0`）次数和处理方式。

人确认后再做（不属于本次迁移）：把三行写进 `.env`，在仓库根目录执行
`scripts/mcp-down.sh kb && scripts/mcp-up.sh kb` 重启 kb，然后跑智能体评测
`make eval-agent ARGS="--url '<DSH 地址带 token>' --model deepseek-official/deepseek-flash --repeat 3 --case s4-escalate-1201"`。
