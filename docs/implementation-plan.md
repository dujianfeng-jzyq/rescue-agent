## 项目概述

本项目以 DeepSeek Harness（DSH）为底座，开发煤矿应急救援智能体，为火灾、水灾、坍塌等事故提供灾情研判、物资调度和处置方案三项辅助决策能力。

建设路线是**先做通一个闭环，再横向扩展**。第一期只做采空区煤自燃，把预警、防灭火处置、应急响应、火区管理和复盘全流程跑通。验证可行后，复用同一套数据底座、MCP 服务和智能体框架，依次扩展到带式输送机巷道火灾、水灾和坍塌。

**推进方式**：在没有真实矿井可用的情况下，先建设一座模拟矿井，用模拟数据把闭环跑通并向客户演示；客户认可后再接入真实矿井，按模块把模拟数据源逐个替换为真实系统，没有现成系统的模块新开发。开发、演示、部署共用同一套智能体。

- **定位**：辅助决策。所有调度和处置指令由指挥员确认后执行，系统不直接下达指令。
- **部署**：矿区内网私有化部署，模型由其他部门在本地部署，数据不出网；开发阶段使用 DeepSeek API，只处理模拟数据和公开资料。
- **试点范围**：先建 1 座模拟矿井，客户认可后接入 1 座真实矿井；1 类场景（采空区煤自燃）。
- **一期周期**：约 6 个月完成模拟矿井闭环和客户演示；接入真实矿井的周期视客户条件而定。

## 为什么选 DSH 作为底座

DSH 是 DeepSeek 于 2026 年 8 月开源的 agent 运行时框架（MIT 协议，TypeScript/Node.js），基于 Cordis 插件框架，所有组件都是插件。救援业务以插件、MCP 服务器和技能的形式开发，不改 DSH 源码。

| DSH 特性 | 对本项目的价值 |
| --- | --- |
| 一切皆插件：模型适配器、工具注册表、agent 循环都可替换 | 数据接入、专业模型、知识库各自独立开发、测试、升级 |
| agent 循环是公开的事件协议（如 `agent/pre-step`、`step/end`） | 在事件上挂钩子，实现人工确认节点和合规拦截 |
| 只追加的执行日志 | 每条研判和建议都有完整依据链，用于审计和事故复盘 |
| 技能（SKILL.md + 脚本） | 专家经验和算法以技能为载体，专家能直接审阅和修改 |
| 插件可调用工具、运行固定的工作流脚本、登记后台任务 | 典型场景按固定步骤执行；持续检测在后台运行，发现异常时唤醒智能体询问操作员 |
| Agent 预设：打包身份、规则、工具 | 一个总指挥预设承担全部交互，权限集中、可审计 |
| 模型无关 | 开发用 DeepSeek API，部署时切换为本地部署的任意模型 |

**注意**：DSH 仍处于开发者预览阶段，官方提示会有不兼容变更。项目必须锁定版本，以 bundle 方式扩展 DSH、不 fork，对 DSH 接口的引用集中在一个适配文件里（见风险与对策）。

## 总体架构

系统分四层：数据层采集矿井实时数据和台账，能力层用确定性模型计算（第二版中算法以技能脚本为载体，由证据插件在服务端运行），智能体层在 DSH 上理解提问、调用固定流程和回答开放问题，交互层把建议交给指挥人员确认。

所有数值结论在能力层产生；智能体层只做理解、编排和文字生成，并通过事件钩子实现人工确认和合规拦截。

## 三大功能模块（全灾种总体设计）

三个模块对所有灾种通用，差异只在数据源和专业模型。一期只实现火灾部分，其余灾种按此框架扩展。

### 灾情研判

| 灾种 | 主要输入 | 研判内容 | 依托模型 |
| --- | --- | --- | --- |
| 火灾 | CO、CO₂、O₂、CH₄、C₂H₄、温度、烟雾、风速、皮带综保 | 火源位置、火势阶段、烟流影响范围、瓦斯爆炸危险性 | 标志气体分析、格雷哈姆系数、爆炸三角形、通风网络解算 |
| 水灾 | 水位、涌水量、水文观测孔、采掘工程图 | 突水水源、淹没范围与时间、被困人员可能位置 | 水化学判别、巷道容积-涌水量淹没推演 |
| 坍塌/冒顶 | 矿压、支架阻力、微震、人员定位 | 冒落范围、二次垮塌风险、被困区域供氧通风状态 | 矿压预警、经验与数值模型 |
| 通用 | 人员定位、视频、避险硐室状态 | 受困人数与位置、灾区边界 | 人员定位、视频识别 |

输出为结构化研判报告：事故等级建议、影响范围图层、危险源清单、置信度、数据依据，随监测数据滚动更新。

### 物资调度

1. 维护应急物资、装备、救护队、医疗和外部救援力量台账（位置、数量、状态、响应时间）。
2. 根据研判结果生成需求清单。
3. 用运筹优化（车辆路径问题、整数规划）计算从哪调、调多少、走哪条路、多久到，考虑井下运输条件和灾区封锁。
4. 生成调度单，经确认后推送，并跟踪到位情况。

### 处置方案

1. 以本矿应急预案和《煤矿安全规程》《矿山救援规程》《煤矿防治水细则》为依据，用检索增强（RAG）调取相关条款。
2. 结合研判结果生成方案：撤离与避灾路线、通风调整、灭火/封闭/排水措施、救护队行动、警戒和外部联动。
3. 每条措施标注依据条款和数据来源。
4. 合规审核逐条校验（第二版中是方案固定流程里的一个阶段），违反硬性规定的措施直接拦截并说明原因；规则引擎再用代码兜底一次。
5. 支持方案对比、人工修改，修改过程记入日志。

**核心原则**：大模型负责理解、编排和生成文字；所有数值结论（气体是否具有爆炸性、烟流多久到达、调度路线）必须由确定性模型计算，不能由大模型估算。

## 首个闭环场景：采空区煤自燃

一期选择采空区煤自燃作为闭环场景。它是目标客户最常见的火灾类型，而且从早期预警、防灭火处置到封闭火区、启封的全过程都能覆盖。

- **最常见**：目标客户的火灾以采空区遗煤自燃为主，演示这个场景最能引起客户共鸣；公开文献和实验数据也较丰富，便于构建模拟矿井。
- **预警期长，智能体价值大**：自燃从缓慢氧化发展到明火有一个过程，标志气体逐步出现。早发现、早处置，多数情况下能避免演变成事故。
- **数据条件较好**：开采容易自燃煤层的矿井一般建有束管监测和上隅角、回风隅角气体监测，部分矿有分布式光纤测温。
- **可扩展**：标志气体分析、爆炸危险性判定、火区管理模型和应急响应部分（撤人、指挥部研判）可直接复用到下一个场景：带式输送机巷道火灾。

**场景边界**：模拟矿井（及之后接入的客户矿井）内一个正在回采的综采工作面及其采空区，覆盖从早期预警到封闭火区、启封的全过程；不含外因火灾和其他区域。

闭环流程依据《矿山救援规程》和本矿防灭火要求设计：左侧是处置阶段与决策人，右侧是智能体的支持。与外因火灾不同，自燃闭环的重心在前段的预警和防灭火处置，多数情况下在第 2 阶段就能收住，只有恶化时才进入应急响应。

> 图：采空区煤自燃闭环 · 6 个阶段、6 个人工确认点（Markdown 无法保留图，见在线文档（链接见文首）；第一版的带图快照 PDF 已于 2026-11-10 删除（图已过时），需要时用 `git log -- docs/implementation-plan.pdf` 从提交历史取）

智能体不改变现有指挥体系，只为各阶段的决策人提供建议；一旦进入应急响应，撤人和报告由调度员按预案立即执行，不等待智能体。各阶段的具体做法见下一节。

## 采空区自燃闭环详细设计（按真实处置流程）

闭环分 6 个阶段：前 3 个阶段是日常防灭火管理中的预警和处置，后 3 个阶段是自燃恶化为火灾后的应急救援和火区管理。每个阶段先明确决策人，智能体只提供支持；规程中保障人员安全的硬性条款由合规审核校验、规则引擎强制执行。条号指《矿山救援规程》；预警指标和防灭火措施在模拟矿井阶段参照行业通行做法和文献设定，接入真实矿井后以该矿的自然发火预测预报制度和防灭火设计为准。

### 阶段划分与智能体支持

| 阶段 | 依据 | 决策人 | 智能体做什么 | 输出 |
| --- | --- | --- | --- | --- |
| 0 监测与预警分级 | 本矿自然发火预测预报制度 | 通风部门、调度员 | 跟踪标志气体浓度和比值、温度的变化趋势，判断自燃发展阶段和预警等级，推断可能的高温区域 | 预警等级建议及依据 |
| 1 预警处置 | 本矿防灭火设计 | 总工程师（或通风副总） | 推荐防灭火措施组合（注氮、注浆、喷洒阻化剂、堵漏、均压）及用量，生成作业和物资安排 | 防灭火方案建议、物资调度单 |
| 2 效果评估 | 本矿防灭火设计 | 总工程师 | 对比措施前后的指标，判断已受控、需继续处置还是在恶化；受控则回到第 0 阶段常态监测 | 评估报告、是否升级的建议 |
| 3 应急响应与先期处置 | 第 39、40 条 | 调度员、带班领导 | 计算受威胁人员、撤人范围、避灾路线和通知清单 | 初报、补充撤人名单 |
| 4 指挥部研判与救援方案 | 第 73、83–87、98 条 | 指挥部 + 救护队带队指挥员 | 汇总第 73 条六类情况；评估瓦斯爆炸危险性；给出封闭范围、密闭位置、注惰抑爆方案和物资调度 | 研判报告、封闭方案建议 |
| 5 火区管理与启封 | 第 87、164 条 | 指挥部、通风部门 | 持续分析密闭内气体、温度、压差和漏风；判断是否满足启封条件；启封时监测复燃征兆 | 火区状态报告、启封建议、复盘报告 |

**设计约束**：一旦进入应急响应，撤人和报告由调度员按预案立即执行，不等待智能体。智能体在这一阶段只做补充（例如提示预案之外的受威胁人员），绝不能成为撤人的前置条件。

| 节点 | 阶段 | 确认人 |
| --- | --- | --- |
| 预警等级 | 0 | 通风部门负责人 |

### 红线规则库

| 规则 | 条号 | 智能体动作 |
| --- | --- | --- |
| 采空区或冒落带火灾，保持通风系统稳定，防止瓦斯涌入火区 | 第 98 条 | 拦截可能破坏通风稳定的建议 |
| 封闭有爆炸危险的火区，先注入惰性气体等抑爆，再在安全位置建进、回风密闭 | 第 85 条 | 方案缺少抑爆步骤则拦截 |
| 封闭时先建临时密闭，确认无爆炸危险后再建永久或防爆密闭 | 第 84 条 | 校验步骤顺序 |
| 封闭过程中可燃气体浓度迅速增加，所有人员立即撤离 | 第 85 条 | 实时报警 |
| 甲烷超过 2% 且上升、风量突变或出现风流逆转征兆，立即撤出 | 第 75 条 | 实时报警 |
| 火区封闭后进入检查一般在 24 小时后；密闭被爆炸破坏的，严禁派救护队探察或恢复 | 第 87 条 | 提醒并拦截 |
| 启封前检查温度、气体和支护并撤出回风侧人员；启封后 3 日内每班检查，发现复燃征兆立即重新封闭 | 第 164 条 | 校验启封方案，实时报警 |
| 反风或风流短路前，必须先撤出受影响区域人员 | 第 77 条 | 方案缺少撤人步骤则拦截 |
| 进入灾区每队不少于 6 人并设待机小队；温度超过 40℃ 不得佩用氧气呼吸器作业 | 第 57、53、88 条 | 校验涉及进入灾区的建议 |

规则库还需并入本矿防灭火设计和预案中的要求，并由通风部门和救护队审定后才能上线。

## 模拟矿井设计

模拟矿井是一期的开发、演示和评测环境。它通过与真实系统相同的数据接口为智能体供数；接入真实矿井时按模块替换数据源，智能体本身不需要修改。

> 图：模拟矿井 · 按模块替换为真实系统（Markdown 无法保留图，见在线文档（链接见文首）；第一版的带图快照 PDF 已于 2026-11-10 删除（图已过时），需要时用 `git log -- docs/implementation-plan.pdf` 从提交历史取）

### 设计原则

1. **数据契约先行**：先定义统一的测点模型、数据格式和事件格式，模拟和真实数据源都按契约输出。模拟器尽量按真实监控平台的数据输出方式供数，让对接变成"换一个数据源"。
2. **数据要像真的**：矿井模型基于典型矿井布局（设计院或高校的脱敏图纸），巷道网络参数真实；自燃过程依据文献和程序升温实验数据；注入传感器噪声、漂移、断线、缺数和误报。
3. **能响应处置**：模拟器接收注氮、注浆、堵漏、均压、封闭等处置输入，指标随之变化。否则第 2 阶段的效果评估无法演示，闭环就不成立。
4. **场景脚本化**：每个场景可重复、可加速播放，几十分钟演完几天的过程。

### 模块组成

| 模块 | 模拟实现 | 接入真实矿井时替换为 |
| --- | --- | --- |
| 矿井与通风模型 | 典型矿井巷道网络、风量风压、漏风通道 | 客户矿图和通风系统数据 |
| 自燃过程模型 | 采空区氧化升温与标志气体演化 | 无需替换，真实矿井直接用监测数据 |
| 束管与安全监控 | 按测点生成气体和温度数据，含脏数据 | 客户束管监测和安全监控平台 |
| 测温 | 采空区温度测点或分布式光纤 | 客户测温系统；没有则不启用 |
| 人员定位 | 按班次和作业计划生成人员分布 | 客户人员定位系统 |
| 防灭火系统 | 注氮、注浆等系统能力和执行反馈 | 客户系统状态数据；多为人工记录，可能需新开发填报模块 |
| 生产数据 | 推进度、停采计划 | 客户生产管理系统或人工填报 |
| 物资与救援力量台账 | 示例台账 | 客户台账；多为表格，需开发导入工具 |
| 预案与规程 | 规程原文和编写的示例预案 | 客户真实预案和防灭火设计 |

### 标准场景

1. 正常回采：基线，检验误报率。
2. 缓慢氧化，及时处置后受控。
3. 加速自燃，处置有效。
4. 处置无效，恶化为火灾，进入应急响应和封闭。
5. 封闭后火区演化与启封，含复燃。
6. 传感器故障与误报。

这 6 个场景同时用作演示脚本、评测集和回归测试集。

### 可信度保障

- 请通风或防灭火方向的专家审核场景参数和智能体输出；考虑与有实验数据和矿井资源的高校或研究院合作，他们也可能帮助引荐第一个客户。
- 对外介绍时注明指标来自模拟环境，真实效果在接入真实矿井后验证。

### 演示方案

阶段 4 的交付物之一是一条约 20 分钟的标准演示线，基于标准场景 2、4、5 加速播放。每一步都同时展示依据（数据、计算过程、规程条号）和确认人。

1. **开场（2 分钟）**：模拟矿井总览，工作面、测点和人员分布叠加在矿图上。
2. **早期预警（4 分钟）**：标志气体缓慢上升，智能体给出预警等级、依据和可能的高温区，通风负责人确认等级。
3. **防灭火处置（4 分钟）**：智能体推荐注氮、注浆组合和用量并生成调度单；总工程师确认后模拟器响应处置，指标回落，展示效果评估。
4. **恶化与升级（5 分钟）**：切换到处置无效的场景，指标加速上升，智能体建议升级为应急响应；展示补充撤人名单和避灾路线，并说明撤人不等待智能体。
5. **封闭方案与合规拦截（3 分钟）**：智能体生成封闭方案；现场演示一条故意违规的修改（例如去掉注惰抑爆步骤）被规则引擎拦截，并给出对应条号。
6. **复盘（2 分钟）**：一键生成复盘报告，展示每条建议的依据链和确认记录。

另外准备一个互动环节：让客户现场调整场景参数（如推进速度、漏风量）重新运行，证明不是预先录好的结果。

第二版的第一次演示（Docker 部署）走一条更短的线：模拟矿井先常态运行，指挥人员要求持续检测；演示人员在控制台注入事故或设置某个测点的读数；持续检测发现异常后唤醒智能体询问操作员，随后研判、发布预警和升级、编制并下发封闭方案、复评效果。步骤见 `docs/design-v2.md` 第 6 节。演示环境要能完全离线运行，模型使用本地部署或演示前缓存的版本，避免现场网络问题。

### 接入真实矿井的三个步骤

1. **离线数据验证**：客户提供一段历史监测数据（可以脱敏），在模拟环境中回放，检验研判效果。只需提供数据，不涉及系统对接。
2. **只读旁路接入**：只从地面数据平台读取数据，不向井下系统写入任何东西，智能体只出建议、不推送。在这一步把模拟数据源逐个替换为真实数据源。
3. **试运行**：与人工指挥并行运行，按该矿制度完成预警指标、红线规则和确认流程的本地化。

## 在 DSH 上的落地方式

> 本章按第二版（2026-11-03，ADR 0007，完整设计见 `docs/design-v2.md`）改写。第一版的做法（5 个 Agent 预设、计算放在 7 个 MCP 服务里）和改动的原因见本章末尾“工程现状与调整”。

第二版取两种做法之长：**专家经验以技能（流程、脚本、模板）为载体，数据经 MCP 获取，知识经知识库插件检索，典型场景的多步流程由插件按固定步骤执行，对外生效的指令经人工确认。** DSH 侧的全部内容打包成一个 bundle（`dsh-bundle/`），用 `dsh plugin add` 装入 `rescue` 配置档，不 fork、不改 DSH 源码；对 DSH 类型的引用集中在 `dsh-bundle/src/adapter/dsh.ts`。

### 四种形式的分工

| 形式 | 放什么 | 为什么 |
| --- | --- | --- |
| 技能（`skills/<技能名>/`） | 流程（SKILL.md）、算法脚本、报告模板、参数和依据、自检样例 | 专家能直接审阅和修改；同一份脚本给模型试算、给系统权威计算，两边一致；自检样例在 CI 和镜像构建时运行 |
| DSH 插件 | 证据采集与记录、风险检测（含后台持续检测）、典型场景的固定流程、知识库、人工确认与红线预检、审计 | 只在 DSH 里使用，要读写会话工作区、登记后台任务、调用其他工具、交付文件、挂在工具管道上；安全控制必须在工具执行前用代码强制执行 |
| MCP 服务器（Python） | 矿井数据（模拟矿井 / 真实矿井适配器）、指令出口 actions | DSH 之外也要用（模拟器、评测、以后的其他系统）；模拟矿井换真实矿井只换地址；指令台账必须与 DSH 进程分开持有 |
| 契约（Python 包） | 数据模型（含记录）、红线引擎、方案校验 | 各服务共用；红线规则只写一份 |

MCP 工具接入后挂在同一个工具注册表里，所以人工确认钩子同样能拦截 MCP 工具的调用。

### 模块清单

| 模块 | 形式 | 职责 |
| --- | --- | --- |
| `rescue-evidence` | DSH 插件 | 按技能的采集清单经自带 MCP 客户端读矿井数据，运行技能脚本，存记录；风险检测 `check_mine`（一次性、后台持续检测） |
| 固定流程（`fire-loop`） | DSH 插件 | `run_fire_assessment`（研判）、`draft_sealing_plan`（方案编写 → 红线预检 → 合规审核）、`review_effect`（效果复评）；模型只在指定阶段做选择和撰写说明，报告由模板生成 |
| `rescue-knowledge` | DSH 插件 | `kb_search`（RAGFlow 语义检索）、`kb_get_articles`（按条文索引取完整条文）；设置页配置 RAGFlow |
| `rescue-approval` | DSH 插件 | 指令类工具执行前先调 actions 的红线预检（预检不可达也拒绝），通过后发起人工确认，弹窗内容由结构化的审批说明生成 |
| `rescue-audit` | DSH 插件 | 记录每次指令类工具调用的结果（已发布、被拦截、失败），供复盘 |
| `rescue-entry` | DSH 插件（本次只定接口） | 统一的会话入口，以后的界面按钮、对外接口（rescue-api、SubAgent 接口）都经它 |
| `contract` | Python 库 | 数据契约、记录模型、红线引擎、方案校验、mine-data 客户端库和一致性测试 |
| `mine-data-sim` | MCP 服务器（Python） | 模拟矿井：矿井与通风模型、自燃过程模型、传感器仿真、场景脚本；第二版增加常态连续运行、事故注入、读数设置和演示控制台 |
| `mine-data-<矿名>` | MCP 服务器 | 真实矿井适配器，接入时开发，实现与 `mine-data-sim` 相同的接口 |
| `actions` | MCP 服务器（Python） | 唯一的指令出口：发布预警、下发方案和调度单、撤人通知、升级、启封审批；按引用的记录核对、服务端再校验一次、写指令台账；起草期红线自查 `precheck_plan`；模拟环境下把确认后的处置转发给模拟矿井 |

第一版的 `fire-model`、`ventnet`、`dispatch`、`kb`、`workflow` 服务和值守进程，按阶段迁入技能和插件后停用（`docs/architecture.md` 第 8 节）。

### 记录：把计算和指令串起来

证据插件采集的数据、技能脚本的结果、按模板生成的报告都存为**记录**：不可变、带编号，结果记录写明技能版本、脚本和输入的哈希。记录只有 DSH 进程能写，智能体的 bash 沙箱写不了。发布预警、下发方案、升级响应都引用记录编号，actions 发布前按编号核对现场条件、等级和时效，对不上就拒绝。这样“数值只来自代码”不靠提示词约束，而由代码强制检查。

### 知识库：RAGFlow + 条文索引

知识库使用其他部门本地部署的 RAGFlow，前面是知识库插件 `rescue-knowledge`：智能体只调用插件，不直接连接 RAGFlow。

| 事项 | 由谁负责 |
| --- | --- |
| 语义检索 `kb_search`：法规规程、矿井预案、文献案例；检索参数、查询改写（如“密闭”↔“封闭”）、结果整理、标注条号 | 知识库插件 |
| 查条 `kb_get_articles`：按文档和条号批量返回完整条文（含全部款、项），从条文索引直接取，毫秒级 | 知识库插件 |
| 条文索引：规程入库时按“章—节—条—款—项”切分，专家抽查后发布 | 离线脚本（开发）+ 专家抽查 |
| 降级：RAGFlow 不可用时检索退回本地条文关键词检索并标明来源；查条不依赖 RAGFlow | 知识库插件 |
| RAGFlow 地址、数据集、凭据：在 DSH 设置页配置和测试连接，凭据放 DSH 凭据服务 | 知识库插件 |
| 文档上传、解析和切片方式、嵌入模型、知识库创建与授权 | RAGFlow 管理方 |

条文要照抄进方案、审核意见和台账，所以由代码按索引给出原文，不交给模型检索后拼接。第一版的 `get_article` 每次在 RAGFlow 切片里现查，单次 15–65 秒，跨切片的条文会被截断，这是改为索引的原因。

- **账号**：为智能体单独申请一个只读、只授权救援知识库的 RAGFlow 账号。
- **知识库划分**：法规规程库、矿井预案库（模拟阶段放示例预案，接入后换成客户真实预案）、文献案例库。预案、案例不按条切分，只走检索。

### 火灾闭环用到的技能

| 技能 | 脚本 | 内容 |
| --- | --- | --- |
| `fire-assessment` 采空区自燃研判 | 风险检测、预警等级、自燃阶段、趋势、实时报警、受威胁人员 | 标志气体解读、预警分级方法、何时做一次性或持续检测；采集清单和持续检测的判据 |
| `explosion-triangle` 爆炸三角形 | 多组分、温度补偿、分区、风险图 | 爆炸危险性判定方法 |

| `sealing-plan` 封闭方案 | 现场条件与必备步骤、密闭材料、注氮量、注浆量 | 封闭火区的步骤与注意事项、方案格式 |
| `plan-compliance` 方案合规审核 | — （红线由 actions 的红线引擎检查） | 人工复核项清单、审核意见格式 |
| `effect-review` 处置效果复评 | 效果评估 | 复评方法和报告格式 |

### Agent 预设

只有一个预设 `rescue-commander`（总指挥协调）：技能、bash 和文件工具（沙箱，只能写会话工作区）、向人提问、待办、文件交付、后台任务，以及上述插件和 actions。它是唯一挂载 actions、能发出指令的 Agent。第一版的方案编写、合规审核两个专业 Agent 改为 `draft_sealing_plan` 里的两个阶段：阶段指令取相应技能的正文，只能从给定清单里选择，合规审核引用的条文由代码事先查好。

### 配置与代码示意

技能脚本是纯函数，文件进、文件出，不访问网络和凭据：

```bash
python skills/explosion-triangle/scripts/explosion_triangle.py \
  --input-file EV-…json --output-file RS-…json --svg-out chart.svg
```

证据插件在 DSH 进程里起子进程运行它（环境变量按白名单传、设超时），结果连同脚本和输入的哈希存为记录；模型也可以在沙箱里对导出的记录运行同一个脚本做试算，但那个结果只作参考。

actions 仍以 MCP 接入主预设，地址和令牌从环境变量读取：

```yaml
# dsh-bundle/presets/commander.patch.yml 片段
- id: mcp-actions
  name: '@deepseek-ai/dsh-mcp-client'
  config:
    serverName: actions
    transport: streamable-http
    url: !!js "process.env.RESCUE_MCP_ACTIONS_URL ?? 'http://127.0.0.1:8106/mcp'"
    headers: !!js "process.env.RESCUE_MCP_ACTIONS_TOKEN ? { Authorization: 'Bearer ' + process.env.RESCUE_MCP_ACTIONS_TOKEN } : {}"
    toolCallTimeoutMs: 60000
```

接入真实矿井时，只把证据插件连接的 mine_data 地址换成该矿的适配器，智能体和技能都不用改。

指令统一走 `actions` 服务，设三道防线：

1. **红线预检**：`rescue-approval` 在工具调用执行前的 `tools/pre-execute` 事件上挂钩子，把调用发给 actions 的 `/redlines/check`：按引用的记录核对，再查红线；不通过直接拒绝并给出条号，预检服务不可达也拒绝。
2. **人工确认**：预检通过后弹出确认（显示要做什么、引用的记录、核对结果、人工确认项），指挥员确认后才放行。
3. **服务端终检**：actions 收到调用后，用同一套红线引擎和记录核对再查一次，不信任调用方；通过才写指令台账。

红线规则只在 `rescue_contract.redlines` 实现一次，固定流程里的起草期自查（`precheck_plan`）、插件预检和服务端终检共用；规则说明技能与规则表有同步测试。

### 这种方式的代价

- **依赖 DSH 插件接口更深**：后台任务、插件运行固定脚本、工作区、唤醒等接口在 0.2.1-rc.4 上逐项验证过（验证清单 #19–#23）；升级 DSH 时必须重跑。
- **持续检测依赖 DSH 进程**：DSH 重启后后台任务消失；演示可以接受，生产的无人值守要另加恢复服务。
- **技能脚本是受信代码**：插件起的子进程不在沙箱里，脚本只能经评审和 CI 进入技能库，部署时技能目录只读挂载。
- **两份采集实现**：不经 DSH 的确定性基线评测用 Python 小工具按同一份采集清单取数，与插件的 TS 实现用一致性测试约束。
- **认证**：DSH 的 MCP 客户端只发送静态请求头；矿区内网用静态令牌，按服务和调用方拆分。

### 工程现状与调整

第一版已完成（2026-11-02）：契约、红线引擎、模拟矿井（6 场景）、7 个 MCP 服务、DSH bundle、技能草稿、基线评测、智能体端到端评测；真实 DSH 0.2.1-rc.4 验证清单 #1–#20、#22、#23 通过。研判类评测改为代码工作流后（ADR 0006）各 3/3，每次约 5–7 万 token。第二版在 `v2` 分支上按 P0–P6 实施（`docs/design-v2.md` 第 9 节）。

搭建中对初版方案的调整（理由见 `docs/decisions/`）：

| 调整 | 初版 | 现在 | 原因 |
| --- | --- | --- | --- |
| DSH 扩展方式 | fork DSH，插件放 `plugins/` | 一个 bundle（`dsh-bundle/`）装入 `rescue` 配置档 | 升级不用合并上游代码 |
| 适配层 | 独立插件 `rescue-adapter` | 一个文件 `src/adapter/dsh.ts` | 只需集中类型引用 |
| 指令出口 | 分散在各模块，确认只在 DSH 侧 | `actions` 服务，三道防线 | 绕过 DSH 也有保护，指令有统一台账 |
| 红线引擎 | 在 `rescue-approval` 里 | Python 契约包 `rescue_contract`，三处共用 | 规则只写一份，不会漂移 |
| MCP 连接 | stdio，FastMCP | streamable-http，地址走环境变量；SDK 2.x 的 `MCPServer` | 服务可分机部署、独立测试 |
| 确定性流程 | 由总指挥 Agent 委派专业 Agent 编排 | 第一版：代码工作流（`mcp/workflow`）；第二版：技能脚本 + 固定流程插件 | 红线输入不能由模型填写；同一研判每次做法不同、token 高（ADR 0006、0007） |
| 算法与判据 | 计算类 MCP 服务的 Python 代码 | 技能脚本和参数文件，带自检样例 | 专家能直接审阅和修改（ADR 0007） |
| Agent 预设 | 5 个专业 Agent | 1 个主预设，方案编写、合规审核改为固定流程的阶段 | 封闭方案流程由模型编排时单次 170–340 万 token，结果不稳定（ADR 0007） |
| 知识库 | kb MCP，现查 RAGFlow 切片取条文；方案自查在 kb | 知识库插件 + 条文索引；方案自查移到 actions | 查条慢且可能不完整；自查不属于知识库（ADR 0007） |
| 持续监测 | — | 第一版：独立值守进程；第二版：插件登记 DSH 后台任务，发现异常唤醒智能体询问操作员 | 检测期间不花 token，按矿井时钟，异常能送到会话里（验证清单 #20） |

## 大模型接入

智能体与具体模型解耦：开发阶段使用 DeepSeek API；部署阶段改为其他部门在本地部署的模型，在 DSH 中配置为自定义模型提供方即可，不限于 DeepSeek 模型。

### 分阶段使用

| 阶段 | 模型来源 | 数据要求 |
| --- | --- | --- |
| 开发与模拟演示 | DeepSeek API | 只处理模拟矿井数据和公开规程、文献 |
| 客户离线数据验证 | 本地部署的模型 | 客户数据原则上不出内网；本地模型尚未就绪时，须经客户书面同意并脱敏后才能使用 API |
| 只读接入与试运行 | 本地部署的模型 | 矿区内网，数据不出网 |

### 对本地模型的要求

以下要求在阶段 0 提给模型部署部门：

- **接口**：采用 DSH 自定义模型提供方支持的协议（通常是 OpenAI 兼容接口）。
- **工具调用**：必须稳定支持工具调用（function calling）。智能体的所有数值结论都靠调用工具获得，这是硬性要求。
- **上下文长度**：建议不低于 64K，以容纳研判数据摘要、规程检索结果和多轮对话。
- **并发**：能支撑主 Agent 与固定流程阶段同时调用，以及演示和多人同时使用；具体容量按评测结果与部署部门确定。
- **稳定性**：约定服务可用性要求，模型版本变更提前通知。

### 模型准入测试

任何模型上线前，包括更换模型和升级版本，都要跑同一套准入测试：工具调用正确率、结构化输出格式合规率、6 个标准场景的端到端结果、红线违规建议的比例。各项指标不低于开发阶段 DeepSeek API 的基线，才能切换。

本地模型能力可能弱于开发时用的 API。由于人工确认和红线拦截都在代码里，模型变弱只会影响建议质量，不会突破安全底线；必要时可以通过调整技能内容或 Agent 分工来弥补。

### 模型不可用时的降级

模型服务中断时，确定性部分照常运行：监测数据、计算模型和红线报警不依赖大模型，告警直接推送给值班人员。文字研判和方案生成暂停，并在界面上明确提示，人员按纸质预案处置。

## 实施步骤与里程碑

一期约 6 个月完成模拟矿井闭环和客户演示，设 3 个门槛；客户确定后分三步接入真实矿井，时长视客户条件而定。之后再按带式输送机巷道火灾、水灾、坍塌的顺序扩展场景。

> 图：实施路线图 · 模拟闭环与演示，之后分三步接入真实矿井（Markdown 无法保留图，见在线文档（链接见文首）；第一版的带图快照 PDF 已于 2026-11-10 删除（图已过时），需要时用 `git log -- docs/implementation-plan.pdf` 从提交历史取）

各阶段交付物：

1. **阶段 0 准备**：组建团队（AI/软件 + 通风、防灭火专家顾问）；锁定 DSH 版本（以 bundle 扩展，不 fork），跑通本地模型；定义数据契约；与 RAGFlow 管理方约定知识库划分、切片方式和只读账号；向模型部署部门提出本地模型要求；收集规程、文献、实验数据和典型矿井图纸。
2. **阶段 1 模拟矿井**：`mine-data-sim` 实现矿井与通风模型、自燃过程模型、传感器仿真（含脏数据）、处置响应接口和 6 个标准场景；预案和规程导入 RAGFlow；建立示例台账。
3. **阶段 2 专业模型**：标志气体趋势与预警分级、高温区推断、防灭火用量计算、爆炸三角形、通风网络解算与漏风分析、避灾路径，用模拟场景和文献数据验证，并请专家评审。
4. **阶段 3 编排与指挥界面**：主预设、技能（含脚本和自检）、证据与固定流程插件、人工确认和合规拦截钩子、结构化输出模板、叠加矿图的指挥界面。
5. **阶段 4 模拟评测与演示**：跑评测集，专家评审，打磨演示版本和演示脚本（见"演示方案"）。
6. **真实矿井接入**：离线数据验证、只读旁路接入、试运行三步（见"模拟矿井设计"）。

**扩展顺序**：带式输送机巷道火灾复用气体分析、通风网络和应急响应部分，只需补充综保数据和烟流蔓延模型，增量最小，放在第一位；水灾需新增水文数据和淹没推演模型；坍塌依赖矿压和微震数据，放在最后。每个新场景只新增数据接入和相应技能（含脚本），必要时加一个固定流程；证据、确认、审核、日志直接复用。

### 团队配置（草拟）

一期（6 个月到演示）核心团队约 8–12 人，另配 2 名兼职的外部领域专家。

| 角色 | 人数 | 主要工作 | 主要投入阶段 |
| --- | --- | --- | --- |
| 项目负责人 / 产品 | 1 | 需求、进度、客户沟通、演示 | 全程 |
| 智能体与平台开发（TypeScript） | 1–2 | DSH 插件（证据、固定流程、知识库、确认与审计）、预设、技能运行和自检 | 0、3 |
| 算法与计算模型（Python） | 2–3 | 技能脚本（通风解算、预警分级、爆炸三角形、调度用量）、条文索引 | 1、2 |
| 模拟矿井与数据工程 | 1–2 | 数据契约、`mine-data-sim`、传感器仿真、场景脚本 | 0–2 |
| 前端（指挥界面） | 1–2 | 矿图态势、确认界面、演示界面 | 3、4 |
| 测试与评测 | 1 | 评测集、回归测试、模型准入测试、演示验证 | 2–4 |
| 运维（可兼职） | 0.5–1 | 容器编排、环境部署，对接模型和 RAGFlow 部署部门 | 全程 |
| 领域专家顾问（外部兼职） | 2 | 通风/防灭火、矿山救护各 1 人：审核场景、技能和红线规则 | 全程按需 |

- **人员紧张时**：可以合并角色（例如模拟矿井与算法合并、测试由开发轮值），最小可行团队约 6 人，周期相应延长到 8–9 个月。
- **接入真实矿井时**：视客户系统数量增加 1–2 名对接开发，负责编写真实矿井适配器和填报、导入工具。
- **领域专家不能省**：场景参数、技能内容和红线规则都需要专家把关，这直接决定演示的可信度。

## 测试评估与验收标准

分两步验收：模拟阶段以评测集成绩和专家评审为准，用于客户演示；接入真实矿井后以离线数据验证和试运行结果为准。指标目标值为建议值，需与客户和救护队共同确定。

### 评测集

- **模拟场景**：模拟矿井的 6 个标准场景及其参数变体。
- **专家想定**：由通风、救护专家编写的场景，覆盖不同自燃发展速度、高温区位置、瓦斯条件和人员分布，并包含误报场景（传感器故障、粉尘干扰）。
- **文献案例重建**：根据公开的事故调查报告和文献案例重建的过程数据。
- **客户历史数据**：接入阶段由客户提供的历史监测数据回放。
- **演练实测**：试运行阶段结合客户矿井的应急演练，系统与人工指挥并行运行。

### 指标

| 指标 | 说明 | 建议目标 |
| --- | --- | --- |
| 预警等级判定准确率 | 预警等级与专家判定一致的比例 | 待与客户确定 |
| 提前预警时间 | 预警时间早于现行人工判定的时长 | 待与客户确定 |
| 初报出具时间 | 升级为应急响应到初报生成 | 3 分钟以内 |
| 受威胁人员召回率 | 应撤离人员被识别出的比例 | 100%（不允许漏报） |
| 方案合规率 | 方案措施通过规程校验的比例 | 100% |
| 关键措施遗漏率 | 专家清单中关键措施未出现的比例 | 0 |
| 专家综合评分 | 研判、调度、方案的可用性打分 | 待定评分表 |

受威胁人员召回率、方案合规率、关键措施遗漏率为一票否决项。

## 风险与对策

最大的风险是错误建议被采纳，因此对策的核心是人工确认、确定性计算和独立审核三道防线。

| 风险 | 对策 |
| --- | --- |
| 错误建议被直接执行 | 系统只做辅助决策；所有指令经指挥员确认；始终保留回退到纸质预案的通道 |
| 大模型幻觉 | 数值结论只来自技能脚本计算并存为记录，指令按记录核对；典型场景按固定流程执行；条文由代码按索引给出；低置信度时明确提示"需人工判断" |
| 灾后数据失真 | 传感器损坏、断电时做数据质量检测，标注数据缺失区域；支持人工录入现场侦察信息 |
| DSH 版本不兼容变更 | 锁定版本，以 bundle 扩展、不 fork；对 DSH 接口的引用集中在 `src/adapter/dsh.ts`；第二版用到的插件接口（后台任务、固定脚本、唤醒）都在验证清单里，升级前全部重跑 |
| 接口对接困难 | 接入真实矿井前摸清各系统厂家协议；优先使用监控系统已有的数据汇聚平台 |
| 网络与部署 | 矿区内网私有化部署；考虑信创硬件与等保要求；指挥中心关键节点冗余 |
| 与现行制度冲突 | 尽早与集团安全部门和救护队对接，明确系统在应急指挥流程中的角色 |
| 模拟与真实差距大 | 模拟器注入脏数据；坚持数据契约和适配层；对接阶段工作量留足余量 |
| 模拟结果被误当作真实效果 | 对外注明指标来自模拟环境；真实效果在离线数据验证和试运行中确认 |
| RAGFlow 由其他部门运维 | 通过知识库插件隔离接口和配置变化；查条走本地条文索引，不依赖 RAGFlow；检索不可用时降级到本地条文；与对方约定变更通知和服务可用性要求 |
| 本地模型能力弱于开发时的 API | 上线前跑模型准入测试；安全控制和典型场景的步骤都在代码中，不依赖模型能力；必要时调整技能内容 |
| 技能脚本被误改或越权 | 脚本是受信代码，只经评审和 CI 进入技能库；运行时环境变量按白名单传；部署时技能目录只读挂载、容器出站白名单 |
