# 第一部分：对接方案

## 1. 背景和目标

煤矿应急救援智能体（一期场景：采空区煤自燃）在研判时估算有害气体的蔓延范围：从源头巷道沿风流向下风侧找出全部巷道，按**设计风量**估算到达时间（未做风量解算），据此找出受威胁人员和撤离路线。这个估算没有浓度，也不考虑火灾对风流的影响。

提供方的火灾推演服务（`MineFireSimulation`）按风阻解算风量，模拟巷道内火源的燃烧，给出每条巷道各时刻的风速和沿巷道的 CO 浓度。本方案的目标：

1. **以推演结果为准**：服务可用时，界面（通风图、研判报告）的有害气体蔓延范围和到达时间**只显示推演结果**；**服务不可用时才改用我方估算**，并明确标出“本系统估算（外部服务不可用：原因）”（显示规则见第 3.1 节）；
2. 先用占位参数**快速打通**全流程（演示用模拟矿井），再随真实矿井数据到位逐步替换；
3. 两种结果照常都计算并存档，便于比较和复盘；
4. 明确需要提供方和矿方各自提供什么。

因为推演结果会直接作为指挥人员看到的蔓延范围，第 6 节里关于**火灾对风流的影响、燃料参数、采空区火源和可用性**的问题需要优先答复。

**边界**：推演结果只是辅助参考，不替代应急预案和现场判断；撤人按预案立即执行，不等待推演结果。界面上始终写明这一点。

**适用范围**：服务模拟的是**巷道内的明火**（给定燃烧面积、燃料种类和质量），我方一期场景是**采空区内的阴燃**，两者不同。我方在预警等级达到**橙色**时就开始请求推演（从橙色起要计算受威胁人员和撤离路线，蔓延范围是其依据），此时自燃多半还在阴燃阶段，按明火模拟是更粗的近似；火源位置按“采空区漏风通道靠上隅角一端”近似（第 4 节）。这两项近似待专家确认，也请提供方给出建议（第 6 节第 3 条）。

## 2. 分工

| 方 | 负责 |
| --- | --- |
| 提供方 | 部署并运行火灾推演服务，保证可用性；提供稳定的接口地址、接口说明和版本；接口变更和停机维护提前通知；说明模型依据和适用范围；回答第 6 节的问题 |
| 我方 | 编写适配服务，把我方通风网络和火源参数转换成服务的输入，调用服务，校验结果并换回我方巷道编号、压缩；保存每次调用的输入和结果摘要（复盘依据）；判读结果，按第 3.1 节的规则显示，服务不可用时用我方估算兜底 |
| 矿方 | 提供真实通风网络数据（第 7 节），用于替换占位参数 |

## 3. 调用方式

```
救援智能体（研判流程，预警等级达到橙色及以上时）
   │  ① 我方技能脚本：通风网络 + 火源参数 → 服务输入（我方编号）
   ▼
我方适配服务 fire_sim（只读，内网）
   │  ② 编号 ↔ 数组下标转换、输入校验、超时；结果校验并压缩成每条巷道的时间序列
   ▼
提供方服务  POST http://<地址>:5079/FireSimulation/GetMineFireSimulationResult
   │  ③ 返回各时刻风速和 CO 浓度（按巷道网格）
   ▼
我方适配服务 → 换回巷道编号 → 我方技能脚本判读（CO 到达、危险时刻）并与我方估算比较、选定显示哪一种 → 保存结果并显示
```

- 调用方只有我方适配服务一个；智能体（大模型）不直接调用提供方服务，也不能自己构造输入调用。
- 调用时机：每次研判中，预警等级达到橙色及以上时调用一次（推演时长 1 小时、每分钟一帧）。研判周期按小时计，调用量很小。
- 超时暂定 60 秒。服务不可用、超时或报错时，研判照常完成，改为显示我方估算，并标明原因。

### 3.1 显示规则（外部为主、我方兜底）

| 服务的情况 | 显示 | 界面上的标注 |
| --- | --- | --- |
| 正常返回推演结果，且通过我方校验（巷道齐全、时间步一致、数值非负有限） | 推演结果：CO 达到“到达”浓度的巷道、到达和危险时刻，可按时间回放 | “外部火灾推演服务” |
| 正常返回，但推演时长内没有巷道达到“到达”浓度 | 推演结果：推演时长内无巷道达到到达浓度（不改用我方估算） | 同上，写明推演时长和浓度 |
| 不可用：没有配置、连不上、超时、返回非 200（含部分火源巷道报 500）、返回格式不对或没通过校验 | 我方估算：下风侧巷道和按设计风量估算的到达时间 | “本系统估算（外部服务不可用：原因）”，用不同的线型和颜色 |

- 两种结果**都计算并存档**；界面只显示选定的一种，另一种在记录里可以查到，不在图上画；
- 受威胁人员名单仍由我方按人员定位和蔓延范围计算（推演结果里推演会到达、我方未列入的人员，单独列出提示人核对）。

## 4. 输入数据怎么来（快速接入阶段）

模拟矿井和当前演示图纸都没有服务需要的大部分数据。快速接入阶段按下表生成输入，**所有占位值都会在结果里标明“试验性”**，并列入我方待专家审定清单。

| 服务字段 | 快速接入阶段的来源 | 性质 |
| --- | --- | --- |
| `nodes` 的 `x`/`y`/`z`（米） | 我方网络没有坐标。按固定方法生成平面占位坐标，使每条巷道的折线长度等于该巷道的实际长度（每条巷道拆成两段，中间加一个节点）；**z 一律取 0**（不引入编造的高差，因此火风压不起作用） | 占位 |
| `branches[].resistance` | 我方网络里的风阻（拆成两段各取一半）；没有风阻的巷道（如避难硐室联络巷）取占位值 | 我方数据 / 占位 |
| `branches[].area` | 统一取占位值 12 m²（与我方估算的缺省断面一致）；采空区漏风通道取等效断面占位值 2 m² | 占位 |
| `branches[].boundaryMarker` | 从地面出口出发的巷道为进风边界，到达地面出口的巷道为出风边界 | 由我方数据得出 |
| `ventBoundary` | 压入式；进风量 = 从各地面出口出发的巷道的设计风量之和 | 由我方数据得出 |
| `fireSource.branchId` / `position` | 采空区漏风通道，位置 0.9（靠上隅角一端） | 占位，待专家确认 |
| `fireSource` 其他字段 | 煤，燃烧面积 10 m²，燃料 90 kg，氧气 21%，推演 3600 s，每 60 s 一帧 | 占位 |

采空区漏风通道作为通风网络的一条分支传入（它影响风量分配）；比较结果时不把它当作人员通行的巷道。

## 6. 需要提供方确认或支持的事项

按对接的重要程度排序。推演结果改为默认显示、并从橙色预警起请求后，第 1–9 条直接影响能否这样使用，请优先答复。

**必须说明或修正（外部结果为主后，影响能否使用）**

1. **火灾对风流的影响**：大火（5000 kg、300 m²）时各巷道风速变化不超过 0.012 m/s、没有风流反转。火风压和节流效应是否已计入通风网络解算？是否需要给出 z 坐标才会体现（示例里有 z）？风流紊乱（反转、停风）是火灾时撤人最关心的结果之一。
2. **燃料质量的作用**：10–500 kg 的结果完全相同，5000 kg 时 CO 反而大幅下降。燃料质量、燃烧面积在模型里分别起什么作用？5000 kg 的结果是否正常？
3. **采空区火源和阴燃阶段**：能否模拟采空区内的火源（漏风通道上的阴燃、低氧燃烧）？我方从橙色预警起请求，此时多半还是阴燃，用明火模型推演是否合适？如果合适，燃烧面积、燃料质量、氧气浓度该怎样取；如果不合适，有没有建议的做法？
4. **部分巷道作火源时报 500**（第 5 节列出的 9 条）。原因是什么？能否修正，或改为 400 并说明哪些巷道不能作火源。按第 3.1 节，报错时我方只能改用自己的估算。
5. **CO 浓度的精度**：结果保留 3 位小数（vol%），即分辨率 10 ppm，而《煤矿安全规程》CO 最高允许浓度是 24 ppm。能否多保留几位，或直接给 ppm？
6. **结果的适用范围**：推演结果能否直接作为指挥人员看到的蔓延范围？模型是否经过验证或用于过实际矿井？有哪些情况结果不可信？燃烧模型（热释放速率曲线、CO 生成率）和烟流模型的依据；`fuelType` 各种燃料的参数。
7. **可用性**：服务能否 7×24 运行；重启后是否自动恢复；有没有计划停机，停机前如何通知；出现故障时联系谁。
8. **响应时间**：典型和最长响应时间，与节点数、巷道数、推演时长的关系；规模上限。我方暂定超时 60 秒，超时即改用我方估算。
9. **错误的含义**：哪些错误是输入问题（400，我方要修正输入）、哪些是服务内部问题（5xx，可以重试）；错误返回的格式能否统一（目前请求体不是合法 JSON 时格式不同）。

**希望支持（影响接入质量）**

10. **健康检查接口**（如 `GET /healthz`）：我方据此提前知道服务不可用。
11. **结果里带计算方法版本号**（如 `version`），我方会存档，便于复盘时知道当时用的是哪一版方法。
12. **巷道可选的实际长度和高差**（如 `branches[].length`、`branches[].rise`）：通风网络通常是示意的，没有可靠坐标时也能使用服务。
13. **其他输出**：除 CO 外，烟雾（能见度）、温度、O₂ 浓度是否能输出。烟雾结果可以直接作为路径规划服务的烟雾浓度输入。
14. **未知字段报错**（400），而不是静默忽略。
15. **鉴权**：至少支持一个固定令牌（如 `Authorization: Bearer <令牌>`），或在服务器上按 IP 白名单限制访问。
16. **输出规模**：能否只返回每条巷道每帧的最大值（或指定网格间距），减少传输量。真实矿井网络的结果可能有几十 MB。

**需要说明（我方要据此决定怎么用、交给专家审定）**

17. `fixedFlow`（强制分风量）、`closed`（风门）与抽出式（`mode = 2`）的用法，能否用来推演处置措施（关闭风门、反风、调风）的效果。
18. 服务的日志在哪里；接口变更的通知方式。

# 第二部分：我方内部实现（附录）

## 附录 A. 实现设计

### A.1 遵守的约定

- **数值只来自代码**（CLAUDE.md 约定 1）：占位输入由技能脚本生成；判读（到达、危险时刻）和比较结论由脚本给出；智能体只引用记录。适配服务只做数据整理（换单位、取每帧最大值），**不做判读、没有阈值**。
- **技能脚本不访问网络**（`skills/README.md`）：脚本只负责“生成请求”和“判读比较”两个纯函数；网络调用在 MCP 服务里，由证据插件编排。
- **智能体不挂载 `fire_sim`**：任何预设都不挂（`scripts/check_patches.py` 检查）。否则智能体可以拿自己编的火源和网络调用，得到不受记录约束的“推演结果”。
- 参数放 `references/fire_sim.yaml`，`status: placeholder`，逐项加进 `docs/expert-review.md`（第十节）。
- 不属于 rescue-mine 接口（`interface.py` 不变）：它是计算服务，不是矿井数据。

### A.2 输入生成（`fire_sim_request.py`）

- 占位坐标与第六版相同（`scripts/_layout.py`，从 `route_request.py` 移出共用，`route_request` 的输出不变）：节点排单位圆、整体缩放、每条巷道在中垂线上加中间节点 `<巷道编号>#mid`，两段 `#a`、`#b` 之和等于巷道长度，z = 0。
- 与第六版不同：**采空区漏风通道也传入**（它是通风网络的一条分支，影响风量分配；路径规划不传它，因为人不能走）。
- 火源：`fire_source_kind` 类型、名称含工作面编号的巷道上，相对位置 `fire_position`；落到拆开后的哪一段、段内位置按比例换算（0.9 → `#b` 段的 0.8）。
- 进风边界：从地面出口出发的巷道的 `#a` 段，风量 = 设计风量之和 ÷ 60（m³/s）；出风边界：到达地面出口的巷道的 `#b` 段。进风巷道没有设计风量时报错（不猜）。
- 预警等级未达到 `level_at_least`（2026-11-17 起为橙色，原为红色）时 `needed: false`，不调用服务。

### A.4 两种方法的差别（比较时要注意）

- 我方：源头取工作面巷道（`assessment.yaml` 的 `personnel_source_kind`），沿风流向下风侧全部算受污染，没有浓度，到达时间按设计风量。
- 推演：火源在漏风通道（`fire_sim.yaml`），按风阻解算风量，有浓度；推演时长内浓度没达到阈值的不算到达。

所以“我方列为受污染、推演未达到”（如工作面本身：火源在漏风通道，CO 从上隅角直接进回风巷）是两边源头假设不同的预期结果，报告首句写明两边的源头。“推演中会到达、我方未列为受污染”和“我方判为不受威胁、推演中 CO 会到达”是需要人重点核对的情况（可能是风流变化，也可能是占位参数造成的），单独列出。

### A.5 测试

- `fire_sim`：用本地假服务测编号转换、结果压缩（branchIds 乱序、全零压缩成数字 0、ppm 换算、反转、停风）、校验（10 种不合法输入不发给提供方）、7 种服务失败、4 种格式错误的返回、未配置、状态检查、提供方示例的往返（26 项）。真实服务的检查放一致性检查，不进 CI。
- 两个脚本：`tests/cases/` 自检样例。`fire_sim_request` 2 组（红色需要、橙色不需要）；`fire_sim_compare` 5 组：s4 红色第 60 小时对提供方服务的实测返回、提供方 500、插件调用失败、不需要、人为改写的倒灌（覆盖 `extra_people`、避灾路线危险、风流反转）。样例由 `scripts/make_fire_sim_cases.py` 生成（会调用提供方服务）。报告模板样例 `s4-fire-sim-opinion`。
- 编排：TS `evidence-fire-sim.test.ts`（调用、失败不抛错、未配置、记录类型校验）；一致性测试 `test_ts_flow_fire_sim_second_opinion`（TS 研判流程 + 真实的 fire_sim 进程 + 假提供方，以及 fire_sim 不可用两种，记录与 Python 侧逐条一致）。
- `make eval` 基线不受影响（基线不经过外部服务）。
